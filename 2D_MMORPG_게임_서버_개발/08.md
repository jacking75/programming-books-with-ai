# 8주차 — 프로젝트 최적화 & 마무리

## 0. 이번 주에 풀고 싶은 문제

7주차까지 우리는 "동작은 한다"는 코드를 만들었다. 한 명, 두 명까지는 잘 돌고, 학습용으로는 충분하다. 그러나 "친구 100명을 같이 들여보내자"라는 욕심이 생기면 즉시 무너진다. 8주차의 목표는 그 욕심을 감당할 수 있게 만드는 것이다.

이번 주의 작업은 코드의 "겉모양"보다는 "운영 가능성"을 늘린다. 아래 다섯 영역에 손을 댄다.

1. **측정**: 우리가 무엇을 얼마나 빨리, 무엇을 자주 만드는지 일단 본다.
2. **패킷/메모리**: ArrayPool, 패킷 묶기, 비동기 송신 큐.
3. **DB**: write-behind 큐, 주기 저장.
4. **안정성**: graceful shutdown, 예외 처리, 연결 끊김 복구.
5. **로그/모니터링**: 운영자가 사고를 인지할 수 있는 최소 조건.

## 1. 측정 — 일단 보고 가자

### 1.1 BenchmarkDotNet 한 번

마이크로 벤치마크는 작은 코드 조각의 핫 포인트를 정확히 짚는다. 우리 시스템에서는 다음 두 곳이 의심된다.

- `PacketEncoder.Encode<T>(T body)` — 직렬화 + 새 byte[] 할당.
- `AoiGrid.Neighbors(...)` — lock + 9칸 dictionary lookup.

```csharp
[MemoryDiagnoser]
public class EncodeBench
{
    private readonly NtfPlayerMove _ntf = new() { Id = 1, X = 100, Y = 100 };
    [Benchmark] public byte[] CurrentEncode() => PacketEncoder.Encode(PacketId.NtfPlayerMove, _ntf);
}
```

`MemoryDiagnoser`가 보여 주는 값 — Allocated가 매번 50바이트 정도 — 가 핵심이다. 1초에 10,000번 호출되면 500KB/s가 가비지로 돌아간다. 중간 GC 정지가 100ms를 넘으면 게임 느낌이 깨진다.

### 1.2 서버 자체의 메트릭

운영 코드에서는 `System.Diagnostics.Metrics`로 다음 지표를 항상 수집한다.

- `players_online` — 현재 접속 수
- `packets_received_total` (rate per type)
- `packets_sent_total`
- `tick_duration_ms` (히스토그램)

학습용에서는 1초마다 콘솔에 출력하는 것으로 시작한다.

이 한 가지만 있어도 "방금 무엇이 일어나는가"가 명확해진다.

## 2. 패킷/메모리 다듬기

### 2.1 ArrayPool 도입

매번 새 byte[]를 만들지 않고 풀에서 빌리고 돌려준다.

```csharp
public static byte[] Encode<T>(PacketId id, T body)
{
    // 1) MemoryPack 직렬화
    var bodyBytes = MemoryPackSerializer.Serialize(body);
    var total = HeaderSize + bodyBytes.Length;

    // 2) 풀에서 빌림
    var buf = ArrayPool<byte>.Shared.Rent(total);
    BinaryPrimitives.WriteUInt16LittleEndian(buf.AsSpan(0, 2), (ushort)total);
    BinaryPrimitives.WriteUInt16LittleEndian(buf.AsSpan(2, 2), (ushort)id);
    bodyBytes.CopyTo(buf.AsSpan(HeaderSize));

    // 3) 송신 후에는 누가 풀에 돌려주나?
    return buf;
}
```

여기서 중요한 점이 "풀에 돌려주는 책임"이다. SuperSocketLite의 `Send(byte[], offset, length)`는 호출이 끝나면 더 이상 그 버퍼를 쓰지 않는다(공식 보장). 그래서 송신 직후 `ArrayPool.Shared.Return(buf)`를 부르면 된다.

```csharp
public void SendPacket<T>(PacketId id, T body)
{
    var bytes = PacketEncoder.Encode(id, body);
    try { Send(bytes, 0, bytes.Length); }
    finally { ArrayPool<byte>.Shared.Return(bytes); }
}
```

이 한 줄 변경으로 GC 빈도가 절반 이하로 떨어지는 경우가 흔하다.

### 2.2 패킷 묶기 (batch)

NtfPlayerMove를 매 이동마다 따로 보내는 대신, tick(예: 100ms)마다 한 패킷에 합쳐 보낸다.

```csharp
[MemoryPackable]
public partial class NtfPlayerMoveBatch
{
    public Move[] Items { get; set; } = Array.Empty<Move>();
    [MemoryPackable]
    public partial struct Move { public long Id; public int X; public int Y; }
}
```

서버 tick 안에서 모든 변경을 모아 한 패킷으로. 헤더가 한 번이라 50명이 동시 이동해도 송신 횟수는 **각 클라이언트당 한 번** 이다. 4주차의 "AOI + tick rate"의 결합으로 진가를 발휘한다.

### 2.3 송신 큐를 별도 스레드로

`Send`를 핸들러 안에서 직접 부르면 그 스레드가 블로킹된다. 별도의 `Channel<byte[]>`을 두고 한 워커가 비우는 구조가 안전하다.

```csharp
public class SendQueue
{
    private readonly Channel<byte[]> _ch = Channel.CreateUnbounded<byte[]>();
    public SendQueue(GameSession s)
    {
        _ = Task.Run(async () =>
        {
            await foreach (var b in _ch.Reader.ReadAllAsync())
                s.Send(b, 0, b.Length);
        });
    }
    public void Enqueue(byte[] b) => _ch.Writer.TryWrite(b);
}
```

큐가 무한이면 메모리 폭발 위험이 있다. 일정 한도를 넘으면 가장 오래된 것을 떨궈 버리거나 연결을 끊는다. 학습용에서는 일단 `BoundedChannel`로 한도를 두고, 가득 차면 끊는 정책을 쓴다.

## 3. DB 최적화

### 3.1 영속화 큐

지금 우리 코드는 SessionClosed 시점에 DB에 한 번 저장한다. 사용자가 수시로 들어왔다 나갔다 하면 좋지만, 한 사용자가 5시간을 버티면 그 동안 영속화가 0번이다. 서버가 죽으면 5시간이 손실된다.

```csharp
public class PersistQueue
{
    private record Job(long CharId, Action<dynamic> Apply);
    private readonly Channel<Job> _ch = Channel.CreateUnbounded<Job>();
    public PersistQueue(string conn) { _ = Task.Run(() => Worker(conn)); }
    private async Task Worker(string conn)
    {
        await foreach (var j in _ch.Reader.ReadAllAsync())
            try { /* DB UPDATE */ }
            catch (Exception ex) { Logger.Error("persist", ex); }
    }
}
```

- **Producer**: 게임 코드는 PersistQueue.Enqueue만 부른다.
- **Consumer**: 워커 한 개가 직렬로 처리. 한 캐릭터의 update는 순서가 지켜져야 한다.

이 패턴을 학습 단계에 도입할지는 강사 판단인데, 한 번 만들어 두면 그 뒤로 거의 모든 영속화에 재활용된다.

### 3.2 주기 저장

5분마다 모든 접속자의 좌표/HP/exp를 일괄 저장.

```csharp
new Timer(async _ =>
{
    foreach (var p in World.Default.All())
        Persist.Enqueue(SaveCharacterFor(p));
}, null, 5 * 60_000, 5 * 60_000);
```

**모든 사용자가 한 timer tick에서 일제히 트리거** 되면 DB에 순간 부하가 몰린다. 시간 분산을 더하면 부드러워진다.

```csharp
new Timer(async _ =>
{
    var bucket = (DateTime.UtcNow.Minute / 5) % 12;  // 분 단위 분산
    foreach (var p in World.Default.All())
        if (Math.Abs(p.CharacterId.GetHashCode()) % 12 == bucket)
            Persist.Enqueue(SaveCharacterFor(p));
}, null, 60_000, 60_000);
```

### 3.3 인덱스 점검

7주차까지 만든 모든 SELECT 쿼리에 EXPLAIN을 한 번씩 돌려 본다. `inventory`의 `idx_inv_char` 같은 인덱스가 빠져 있으면 문제가 된다. 학습용에서는 EXPLAIN 한 번씩 돌리는 것 자체가 좋은 실습이다.

## 4. 안정성

### 4.1 Graceful shutdown

```csharp
var shutdown = new CancellationTokenSource();
Console.CancelKeyPress += (_, e) => { e.Cancel = true; shutdown.Cancel(); };
AssemblyLoadContext.Default.Unloading += _ => shutdown.Cancel();

while (!shutdown.IsCancellationRequested) await Task.Delay(1000);

Logger.Info("graceful shutdown begin");
foreach (var s in server.GetSessions(_ => true))
{
    s.SendPacket(PacketId.NtfLeaveGame, new NtfLeaveGame { Reason = 1 });
    s.Close();
}
await Task.Delay(2000);
server.Stop();
await Persist.FlushAsync();
Logger.Info("graceful shutdown done");
```

- **NtfLeaveGame**으로 클라이언트에 미리 알린다.
- **2초 대기**: 클라이언트가 화면에 알림을 띄우고, 핵심 패킷이 send 큐에서 빠질 시간.
- **`Persist.FlushAsync()`**: 큐에 남은 작업을 끝낸 뒤 종료.

이 한 절차의 유무로 사용자가 "서버 점검이다"라고 인지하느냐 "갑자기 튕겼다"라고 인지하느냐가 결정된다.

### 4.2 비정상 종료 대비

서버 프로세스가 OutOfMemoryException 같은 이유로 갑작스레 죽으면 graceful shutdown은 안 일어난다. 그래서 **주기 저장**이 안전망이 된다. 두 가지를 모두 두는 것이 정석이다.

### 4.3 핸들러 예외 격리

PacketHandler.Dispatch에 이미 try/catch가 있지만, **무엇을 잡고 무엇을 위로 던질지** 가 더 중요하다.

- `MemoryPackSerializationException`: 클라이언트 패킷이 깨진 것. 세션을 끊는다.
- `OperationCanceledException`: shutdown 중. 조용히 빠진다.
- `Exception`: 알 수 없음. 로그를 남기고 세션을 끊는다.

세 종류로 분기하면 디버깅의 신호 대 잡음이 좋아진다.

### 4.4 연결 끊김 복구

클라이언트가 와이파이가 끊겼다 다시 들어왔을 때, 토큰이 살아 있다면 그대로 게임에 돌아갈 수 있게 만든다.

- **세션은 새로 만든다.** 옛 세션은 그대로 종료.
- **PlayerCharacter는 재사용**이 가능하다면 좋다. 옛 위치 그대로 들어가게 한다.
- **Redis 세션 TTL**을 다시 설정한다.

학습용에서 이 모든 것을 만드는 것은 부담이지만, "세션과 도메인 객체 분리"의 가치를 다시 한 번 느끼는 부분이다.

## 5. 로깅과 모니터링

### 5.1 ZLogger

`Console.WriteLine`은 학습용으로 좋지만 운영에는 너무 느리다. ZLogger 같은 zero-allocation 비동기 로거를 쓰면 핫 패스에서 로그 비용이 거의 사라진다.

```csharp
ZLog.Info($"player {playerId} moved to ({x},{y})");
```

문법은 같지만 내부적으로 string interpolation을 하지 않고 binary message로 구조화한다.

### 5.2 카테고리/레벨

레벨 두는 정책을 명확히 하면 운영자가 "이 로그는 진짜 사고인가"를 빨리 안다.

- **DEBUG**: 핸들러 진입/탈출 (운영에서는 끄는 것이 보통)
- **INFO**: 입장/퇴장/사망/저장
- **WARN**: 미인증 패킷, 알 수 없는 PacketId, 인벤토리 가득
- **ERROR**: DB 실패, 직렬화 실패
- **FATAL**: 서버 시작 실패, OOM

INFO 미만은 운영 환경에서 끈다. WARN 이상이 1분에 100개 이상 나오면 알람을 친다.

### 5.3 trace id

한 사용자의 한 행동(예: ReqAttack → 처리 → NtfHpChange)에 같은 ID를 붙여 두면 사고 분석이 쉽다.

```csharp
using (Logger.WithTraceId(Guid.NewGuid()))
{
    // 이 블록 안의 모든 로그에 같은 trace_id 붙음
}
```

분산 추적까지 가지 않더라도, 한 패킷 처리 안에서 trace_id를 일관되게 유지하는 것만으로 디버깅이 비약적으로 쉬워진다.

## 6. 코드 정리

### 6.1 attribute 기반 핸들러

지금까지 우리는 `handler.Register(PacketId.X, OnX)`을 매번 적었다. 패킷이 30개를 넘으면 이 등록 코드가 길어진다. attribute로 자동 등록하는 패턴이 흔하다.

```csharp
[PacketHandler(PacketId.ReqAttack)]
public static void OnReqAttack(GameSession s, byte[] body) { ... }
```

```csharp
public class PacketHandler
{
    public void RegisterFromAssembly(Assembly asm)
    {
        foreach (var m in asm.GetTypes().SelectMany(t => t.GetMethods()))
        {
            var attr = m.GetCustomAttribute<PacketHandlerAttribute>();
            if (attr != null)
                Register(attr.Id, (Handle)Delegate.CreateDelegate(typeof(Handle), m));
        }
    }
}
```

리플렉션이 한 번만 도는(서버 시작 시) 코드라 비용은 무시할 수 있다.

### 6.2 namespace 정리

7주차까지 우리는 `Game/`, `Handlers/`, `Net/`로 나누었다. 8주차 정리에서는 도메인 단위로 한 번 더 묶는 것을 시도해 본다.

```
GameServer/
├── Combat/
├── Inventory/
├── Movement/
├── Monster/
└── Auth/
```

도메인이 한 폴더에 모이면 새 기능을 추가할 때 어디를 보아야 하는지가 명확해진다. 이 리팩토링은 학습 차원에서 한 번 시도하는 것 자체에 가치가 있다.

## 7. 부하 테스트

### 7.1 봇 클라이언트

100명을 친구에게 부탁할 수는 없으니, 봇 클라이언트를 쓴다. 우리 콘솔 클라이언트를 약간만 수정하면 된다.

```csharp
var tasks = new List<Task>();
for (int i = 0; i < 100; i++)
{
    int id = i;
    tasks.Add(Task.Run(async () =>
    {
        var api = new ApiClient(...);
        await api.RegisterAsync($"bot{id}", "1234");
        await api.LoginAsync($"bot{id}", "1234");
        var chars = await api.ListCharactersAsync();
        // ... GameNetClient 로 들어가서 무작정 W A S D 반복
    }));
}
await Task.WhenAll(tasks);
```

### 7.2 측정 항목

- **지연**: ResMove 응답까지 얼마나 걸리는가 (p50, p95, p99).
- **CPU**: 게임 서버 프로세스의 CPU 사용률.
- **메모리**: 서버 프로세스의 RSS, GC frequency.
- **Tick rate**: 우리가 의도한 10Hz가 실제로 유지되는가.

100봇이 동시 이동해도 p99 지연이 100ms 이내, CPU 50% 이내라면 좋은 신호이다.

### 7.3 봇이 없으면 못 보이는 문제

- 동시성 사고: 한두 명일 때 보이지 않다가 100명에서 한 번씩 터지는 race.
- 메모리 누수: 한 시간 부하 후 RSS가 계속 오르면 누수.
- 락 경합: AoiGrid의 단일 lock이 진짜 병목인지가 여기서 드러난다.

이 단계의 발견이 8주차 이후 자체 학습의 출발점이다.

## 8. 8주차 마무리 체크리스트

- [ ] 1초마다 [stats] 로그가 콘솔에 찍힌다.
- [ ] PacketEncoder.Encode가 ArrayPool을 쓴다.
- [ ] 5분마다 캐릭터/인벤토리가 자동 저장된다.
- [ ] Ctrl+C로 종료할 때 NtfLeaveGame이 모든 세션에 가고, 큐가 flush된 뒤 종료된다.
- [ ] 100봇이 5분간 무작위 이동을 해도 서버가 안 죽는다.
- [ ] 100봇 환경에서 사람 한 명이 들어가서 정상 플레이할 수 있다.

## 9. 연습 문제

1. **AoiGrid의 단일 lock을 셀 단위 lock으로 쪼개라.** 100봇 환경에서 p99 지연이 어떻게 변하는지 측정.
2. **`[PacketHandler]` attribute** 기반 자동 등록을 도입하라. 7주차의 모든 핸들러 등록 코드가 한 줄로 줄어든다.
3. **하트비트(ping/pong) 패킷**을 추가하라. 서버는 30초 동안 클라이언트로부터 어떤 패킷도 받지 못하면 세션을 닫는다. 와이파이가 끊겨 클라이언트가 사라진 경우의 비정상 세션을 정리한다.

각 주차에서 한 번 본 패턴은 다음 주차에 재사용되었다. 1주차의 "패킷 헤더 + Body" 구조는 8주차까지 한 줄도 안 바뀌었다. 4주차의 AOI 격자는 6주차의 몬스터, 7주차의 아이템 모두에 그대로 쓰였다. 5주차의 데미지/사망/보상 패턴은 6주차에서 그대로 재사용되었다.

이 "재사용"이 시스템 설계의 핵심이다. 처음에 잘 정의된 추상화는 이후의 모든 변경을 가벼운 한 줄짜리 변경으로 만들어 준다. 8주가 끝난 시점에 이것을 손과 머리로 동시에 느꼈다면, 이 책의 목적은 달성된 것이다.

이제 본인의 게임을 만들 차례이다. 직업 시스템, 스킬, 파티, 채팅, 던전, 업적, 친구 목록, 길드, 경매장... 끝없는 주제가 기다린다. 이 책의 코드 위에 한 가지씩 직접 얹어 보면 된다. 그게 진짜 공부의 시작이다.
