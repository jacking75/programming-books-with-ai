# 부록 E. 확률 설계 체크리스트 (뜯어서 쓰는 한 장짜리)

가챠 시스템을 만들 때, 배포 전에, 그리고 라이브 운영 중에 점검할 항목을 한 페이지로 정리했다. 사내 위키나 PR 템플릿에 붙여서 쓰면 좋다.

---

## E-1. 기획 단계 체크리스트

```
[가챠 종류 결정]
[ ] 일반 가챠 / 박스 가챠 / 스텝업 / 컬렉션 — 어느 형태인가
[ ] 결정한 가챠 형태가 컨텐츠 목적에 부합하는가
[ ] 비슷한 게임의 사례를 분석했는가

[확률 설계]
[ ] 등급별 확률이 명확히 정의됐는가 (SSR/SR/R)
[ ] 등급 확률 합이 정확히 100%인가
[ ] 같은 등급 안에서 가중치가 균등 또는 명시적으로 차이 나는가
[ ] 픽업 캐릭터의 처리 방식이 결정됐는가 (50/50 또는 가중치 변경)

[천장 시스템]
[ ] 하드 천장 회차 결정 (예: 90)
[ ] 소프트 천장 시작 회차 결정 (예: 74)
[ ] 50/50 보장 적용 여부
[ ] 천장 카운터 승계 규칙 (배너 끝나면 리셋? 다음 배너로 승계?)

[재화 설계]
[ ] 1회 비용 / 10연 비용 / 할인 정책
[ ] 사용 가능한 재화 종류 (유료/무료/티켓)
[ ] 일일/주간 횟수 제한 여부

[법규]
[ ] 한국 확률 공시 의무 검토
[ ] 해외 출시 예정 시 현지 법규 검토
[ ] 콤플리트 가챠 형태가 아닌지 확인 (일본 출시 시)
[ ] 미성년자 결제 한도 시스템 적용
```

## E-2. 개발 완료 후 배포 전 체크리스트

```
[데이터 검증]
[ ] DB에 모든 배너·아이템·가중치가 입력됐는가
[ ] 가중치 0 이하 아이템이 없는가
[ ] 등급 확률 합이 1.0인가 (오차 1e-6 이내)
[ ] 픽업 플래그가 정확히 1개 아이템에만 켜져 있는가

[알고리즘 테스트]
[ ] 룰렛/이진/별칭 — 풀 크기에 맞는 알고리즘을 선택했는가
[ ] 단위 테스트 — 모든 등급이 적어도 한 번씩 나오는가
[ ] 단위 테스트 — 천장 90회에서 SSR이 보장되는가
[ ] 단위 테스트 — 자연 SSR 발생 시 카운터가 리셋되는가
[ ] 단위 테스트 — 50/50 미스 후 다음 SSR이 픽업인가

[몬테카를로 시뮬레이션]
[ ] 100만 회 시뮬레이션 통과
[ ] 카이제곱 p-value ≥ 0.01
[ ] 모든 아이템이 등장 (0% 버그 없음)

[서버 통합]
[ ] 트랜잭션이 차감-추첨-지급-천장갱신을 묶고 있는가
[ ] 멱등성 키가 작동하는가 (같은 키 재요청 시 같은 결과)
[ ] 분산락이 동시 요청을 차단하는가
[ ] FOR UPDATE 행 잠금이 적용됐는가
[ ] 서버 재시작 후 박스 상태가 유지되는가

[모니터링 / 알림]
[ ] 실시간 대시보드에 배너 등장률이 표시되는가
[ ] 3시그마 알람이 슬랙으로 전송되는가
[ ] 추첨 이력 테이블이 정상 적재되는가
[ ] 일일 통계가 자정에 집계되는가

[법규 / 공시]
[ ] 공시 페이지가 DB와 일치 (자동 생성)
[ ] 게임 내에서 1~2클릭으로 확률 정보 도달
[ ] 광고/홍보에 확률 표기 가이드 적용

[부하 / 카나리]
[ ] 부하 테스트 (초당 1000건 이상) 통과
[ ] 카나리 5% 배포 가능 (피처 플래그 또는 배너 ID 분기)
[ ] 롤백 계획 작성 (DB 복구, 보상 발송 절차)
```

## E-3. 라이브 서비스 중 이상 감지 대응 체크리스트

```
[알람 수신 시 ~ 10분]
[ ] 어떤 배너인가 확인
[ ] 어떤 등급/아이템에 이상이 있는가
[ ] 표본 크기는 충분한가 (≥ 200, 가능하면 ≥ 1000)
[ ] 시간대별 추이 — 갑자기 시작됐는가, 점진적인가

[원인 분석 ~ 20분]
[ ] DB 확률 값 직접 확인 (어드민 도구로 즉시 조회)
[ ] 최근 변경 이력 확인 (banner_change_log)
[ ] 코드 배포 이력 확인 (CD 파이프라인)
[ ] 전체 영향 범위 산정 (얼마나 많은 유저가 받았나)

[1차 조치 ~ 30분]
[ ] DB 데이터 수정 또는 피처 플래그 OFF
[ ] 즉시 동기화 (Redis 캐시 무효화)
[ ] 대시보드에서 정상화 확인
[ ] 운영팀에 사고 알림 (대외 공지 검토)

[복구 후 ~ 2시간]
[ ] 영향 받은 유저 목록 추출
[ ] 보상 안 정의 (다이아 / 픽업 캐릭 / 무료 추첨권)
[ ] 보상 자동 발송 도구 실행
[ ] 발송 확인 로그 적재

[사후 작업 ~ 24시간]
[ ] 임시 공지 → 정식 사과 공지로 갱신
[ ] Postmortem 보고서 작성
[ ] 재발 방지 대책 수립
[ ] CI에 추가 테스트 케이스
[ ] 모니터링 임계값 조정 (필요 시)

[일주일 내]
[ ] 같은 패턴이 다른 배너에도 있는지 점검
[ ] 가챠 관련 모든 문서 업데이트
[ ] 신규 입사자가 같은 실수를 반복하지 않도록 가이드 추가
[ ] 자동화 가능한 검증 항목을 코드로 구현
```

## 한 장 요약 — 책상 위에 붙여두기

```
╔══════════════════════════════════════════════════╗
║       가챠 확률 구현 — 잊지 말아야 할 7가지        ║
╠══════════════════════════════════════════════════╣
║ 1. 모든 추첨은 서버에서 한다 (클라는 표시만)        ║
║ 2. Random.Shared를 쓴다 (System.Random new 금지)  ║
║ 3. 차감-추첨-지급-천장은 한 트랜잭션 안에 둔다     ║
║ 4. 멱등성 키로 중복 차감을 막는다                  ║
║ 5. 분산락 + FOR UPDATE 둘 다 쓴다                 ║
║ 6. 자연 SSR 발생 시 카운터 리셋을 빠뜨리지 않는다   ║
║ 7. 공시 페이지는 DB에서 자동 생성한다              ║
╚══════════════════════════════════════════════════╝
```

이 7가지만 지키면 라이브에서 일어나는 가챠 사고의 90%를 막을 수 있다. 이 책의 핵심을 한 장으로 줄이면 이게 전부다.

---

## 책을 마치며

이 책은 신입 게임 프로그래머가 **첫 가챠 시스템을 만들 때 사고 없이 출시**할 수 있도록 쓰였다. 이론보다 실전을 중시하고, 모든 코드는 그대로 .NET 10 게임 서버에 붙일 수 있다.

가챠는 단순한 추첨 알고리즘 같지만, 실제로는 **수학·DB·동시성·법규·운영**이 모두 얽힌 시스템이다. 책의 한 장이라도 빼먹으면 라이브에서 사고로 돌아온다.

다행히도 한 번 잘 만들어둔 가챠 시스템은 두고두고 재사용할 수 있다. 다음 게임에서, 다음 회사에서도. 이 책이 그 첫 번째 좋은 가챠 시스템을 만드는 데 도움이 되길 바란다.

가챠는 게임 서버 개발의 좋은 입문이기도 하다. 여기서 배운 트랜잭션·락·캐시·모니터링은 인벤토리, 길드, 거래, 랭킹 등 모든 시스템에 그대로 적용된다.

좋은 게임을 만들어주기 바란다.
