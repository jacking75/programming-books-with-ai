## 16.1 0% 버그 — 특정 아이템이 절대 안 나오는 이유

### 사고

배너가 1주일 진행됐는데, 특정 SR 캐릭터(이름 가칭 "Aoi")가 단 한 번도 등장하지 않았다. 데이터마이닝 커뮤니티가 먼저 알아냈다.

### 원인

```csharp
// 풀 로딩 시 가중치 정규화 코드
var totalWeight = items.Sum(i => i.Weight);
foreach (var item in items)
{
    item.NormalizedRate = item.Weight / totalWeight;
}
```

여기까지는 멀쩡했다. 문제는 **DB 데이터**였다.

```sql
-- 누군가 야간 패치로 가중치를 0으로 설정
UPDATE banner_item_pool SET weight = 0 WHERE item_id = 'AOI';
```

가중치 0인 아이템은 누적 확률 테이블에서 **건너뛰어진다**. 알고리즘 자체는 정상이지만 **결과적으로 0%**로 나온 것이다.

### 어떻게 잡았어야 했나

1. **풀 로드 시 검증**: 가중치가 0 이하인 아이템이 있으면 예외 발생
2. **공시 페이지 자동 생성**: DB → 공시가 자동 생성되면 0%로 표시 → 사람이 확인 가능
3. **모니터링**: 24시간 동안 0회 등장한 아이템에 알람

### 코드 수정

```csharp
public static List<GachaItem> ValidatePool(IEnumerable<GachaItem> items)
{
    var list = items.ToList();
    var zero = list.Where(i => i.WeightInTier <= 0).ToList();
    if (zero.Count > 0)
        throw new InvalidOperationException(
            $"가중치가 0 이하인 아이템: {string.Join(",", zero.Select(i => i.Code))}");
    return list;
}
```

## 16.2 정수 오버플로우로 확률이 뒤집어진 사건

### 사고

이벤트 보스 드롭 테이블에서, **레전더리 아이템이 도리어 가장 자주 나오는 사건**.

### 원인

```csharp
// 누군가가 가중치를 가독성 위해 큰 숫자로 입력
items = new[]
{
    (Item.Common,    1_000_000),     // 일반
    (Item.Rare,        100_000),
    (Item.Epic,         10_000),
    (Item.Legendary,     1_000),
};

// 룰렛 휠 코드 (int 사용)
public static int Pick(IList<(Item, int)> items, Random rng)
{
    int total = items.Sum(x => x.Item2);  // ← 여기서 오버플로우
    int roll = rng.Next(total);
    ...
}
```

`Sum`이 `int.MaxValue (2^31 - 1)`를 넘어 음수가 되거나, **합 자체가 잘못 계산**되어 가중치가 뒤바뀌었다.

### 교훈

- **가중치는 `double` 또는 `long`을 써라**.
- 어드민 도구에서 입력값 범위 검증.
- 단위 테스트에 큰 가중치 케이스 추가.

### 안전한 코드

```csharp
public sealed class SafePicker<T>
{
    private readonly List<(T Item, double Weight)> _items;
    private readonly double _total;

    public SafePicker(IEnumerable<(T, double)> items)
    {
        _items = items.ToList();
        _total = _items.Sum(x => x.Weight);
        if (double.IsInfinity(_total) || double.IsNaN(_total))
            throw new InvalidOperationException("가중치 합이 비정상");
    }
}
```

## 16.3 천장 카운터가 리셋되지 않아 SSR이 쏟아진 사건

이건 6장에서 자세히 다뤘다. 핵심만 다시.

### 사고

출시 1주일 후 데이터 분석에서 SSR 등장률이 의도(0.7%)의 **약 2배**로 측정됐다.

### 원인

```csharp
// 자연 SSR 발생 시 카운터 리셋이 빠짐
public GachaItem Draw(PityState state)
{
    state.Counter++;
    if (state.Counter >= 90)
    {
        state.Counter = 0;
        return PickSsr();
    }
    return _baseService.Draw();
    // ← 여기서 자연 SSR 떠도 카운터 안 줄어듬
}
```

### 패턴 정리

| 어디에 있는 카운터 | 언제 리셋해야 하나 |
|------------------|-----------------|
| 하드/소프트 천장 카운터 | **모든 SSR 등장 시** |
| 50/50 보장 플래그 | 픽업 SSR 등장 시 |
| 박스 잔여 | 박스 비었을 때 (리필) |
| 컬렉션 진행도 | 보상 수령 시 |

라이프사이클이 다른 카운터를 같이 관리하면 헷갈린다. 클래스로 분리해두면 안전하다.

## 16.4 확률 공시와 실제 확률이 달라 소송까지 간 사례

### 사고

공시 페이지: SSR 0.7%
실제 DB:    SSR 0.07%

### 원인

운영 도구에서 확률을 **퍼센트(%)** 단위로 입력하는데, 코드는 **소수점(0~1 사이)** 단위를 기대했다.

```
운영 입력: "0.7" (% 의미였음)
DB 저장:   0.7 (소수점으로 인식 → 70%? 또는 0.7%? 혼란)
실제 적용: 0.007 (운영 도구가 자동 100으로 나눔)
공시 페이지: 0.7% (운영 도구가 그대로 표시)
```

운영 도구가 일관성 없이 작동했다. **저장은 100으로 나누고 표시는 그대로**.

### 결과

- 시정명령
- 손해배상 청구 소송 (집단소송으로 확대)
- 합의금 + 게임 내 보상 + 사과문

### 교훈

1. 단위는 명확히 — DB·코드·UI 모두 같은 단위(소수 0~1)로 통일
2. 어드민 도구에서 변경 직후 자동으로 공시 페이지 미리보기를 보여줌
3. **공시와 DB 일치 자동 검증 테스트** (CI에서 매 PR마다)

```csharp
[Fact]
public async Task PublicDisclosure_Matches_LiveDatabase()
{
    var liveData = await _bannerRepo.LoadAllAsync();
    var publishedHtml = await _http.GetStringAsync("https://game.example.com/disclosure");

    foreach (var banner in liveData)
    {
        var generated = _generator.Generate(banner);
        publishedHtml.Should().Contain(generated.Trim());
    }
}
```

## 16.5 [패턴 정리] 사고 유형별 원인·탐지·해결 방법 한눈에 보기

├────────────────────┼───────────────────┼────────────────────┼────────────────────┤

### 마지막 조언

**모든 가챠 코드는 두 번 점검한다.**

1. 한 번은 만든 사람이 (단위 테스트, 카이제곱)
2. 한 번은 다른 사람이 (코드 리뷰, 공시 검증)

라이브 사고의 **80% 이상은 두 번째 점검에서 잡힌다**.

## 16장 요약

- 0% 버그는 풀 로드 검증으로 막는다.
- 정수 오버플로우는 `double`/`long` 사용으로 막는다.
- 천장 카운터 리셋은 자연 SSR 시에도 항상 한다.
- 공시와 실제 확률 단위는 통일하고, CI에서 자동 비교한다.
- 모든 가챠 코드는 코드 리뷰가 필수다.
