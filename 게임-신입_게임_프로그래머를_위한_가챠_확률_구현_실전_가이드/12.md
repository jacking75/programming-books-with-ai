# 12장. 동시성 문제 — Race Condition 막기

11장에서 트랜잭션을 봤지만, 트랜잭션만으로 막을 수 없는 게 있다. **같은 유저가 동시에 두 요청을 보낼 때**다. 이 장에서는 분산락, 낙관적 락, 비관적 락을 비교하고, Redis 분산락 구현까지 다룬다.

---

## 12.1 [사고 사례] 두 요청이 동시에 들어와서 재화가 두 번 차감된 경우

### 시나리오

```
유저 A: 잔액 200원, 추첨 비용 100원

T0:  요청1 도착
T1:  요청2 도착 (네트워크 지연으로 거의 동시)

스레드1                          스레드2
───────                         ───────
SELECT currency = 200            
                                 SELECT currency = 200
UPDATE currency = 100            
                                 UPDATE currency = 100  ← 둘 다 차감 1회만
COMMIT                           COMMIT

결과: 200원 → 100원 (한 번 차감만)
지급: 아이템 2개 (둘 다 추첨 성공)
손해: 게임사가 100원 손해
```

### 왜 트랜잭션만으론 안 되는가

기본 격리 수준 `REPEATABLE READ`에서는 두 트랜잭션이 같은 행을 동시에 SELECT할 수 있다. UPDATE 충돌만 막을 뿐이다.

`FOR UPDATE`를 쓰면 행 잠금이 걸려서 막을 수 있다. 다만 **네트워크 라운드트립 + DB 잠금 시간이 길어지는 비용**이 있다.

---

## 12.2 분산락 / 낙관적 락 / 비관적 락 — 각각 언제 쓰나

### 비관적 락 (Pessimistic Lock)

> "다른 요청이 절대 못 끼어들게 미리 잠근다."

```sql
-- MySQL InnoDB 행 잠금
SELECT counter FROM user_gacha_pity 
WHERE user_id=? AND banner_id=? FOR UPDATE;
```

**언제 쓰나**: 충돌이 자주 발생할 가능성이 있을 때. 가챠가 그렇다.

**비용**: 락 대기 시간. 같은 유저가 동시에 10번 호출하면 10번이 순차 처리된다.

### 낙관적 락 (Optimistic Lock)

> "충돌이 없을 거라 가정하고 진행하다가, 마지막에 검증하고 실패면 재시도."

```sql
-- 버전 컬럼 사용
SELECT counter, version FROM user_gacha_pity WHERE user_id=? AND banner_id=?;

-- (메모리에서 처리)

UPDATE user_gacha_pity 
   SET counter=?, version = version + 1
 WHERE user_id=? AND banner_id=? AND version=?;
-- 영향 받은 행 = 0 → 재시도
```

**언제 쓰나**: 충돌이 거의 없을 때. 추첨은 그렇지 않다.

**비용**: 충돌 시 재시도. 가챠는 충돌이 자주 일어나서 비효율.

### 분산락 (Distributed Lock)

> "여러 서버에 걸쳐 같은 유저는 한 번에 한 명만 처리."

```csharp
using var lockToken = await _redis.AcquireLockAsync($"gacha:{userId}", TimeSpan.FromSeconds(5));
if (lockToken is null) throw new TooManyRequests();

// 안전 구역
await ProcessGachaAsync(...);
```

**언제 쓰나**: 게임 서버가 여러 인스턴스에 나뉘어 있을 때 (대부분 그렇다).

**비용**: Redis 호출 비용 (1ms 미만).

### 비교표

| 락 종류 | 충돌 빈도 | 동시성 | DB 부하 | 사용 위치 |
|--------|---------|-------|--------|----------|
| 비관적 락 (FOR UPDATE) | 높음 | 낮음 | 높음 | DB |
| 낙관적 락 (version) | 낮음 | 높음 | 낮음 | DB |
| 분산락 (Redis) | 모든 빈도 | 단일 유저 직렬화 | 매우 낮음 | 외부 |

### 가챠는 어떤 조합?

```
[권장 조합]
1. Redis 분산락 (유저 단위)        ← 같은 유저 동시 요청 차단
2. MySQL FOR UPDATE                  ← DB 안전망
3. 멱등성 키                         ← 네트워크 재시도 대응
```

세 가지 모두 쓰는 게 정석이다. 비용보다 사고 비용이 훨씬 크다.

## 12.3 [실습] Redis 분산락으로 중복 추첨 방지하기

### CloudStructures를 이용한 분산락

CloudStructures 자체는 락을 직접 제공하지 않지만, `RedisString`의 `SetAsync(value, expiry, when: When.NotExists)` 패턴으로 만들 수 있다.

### 락 인터페이스

```csharp
public interface IDistributedLock
{
    Task<IAsyncDisposable?> AcquireAsync(
        string key,
        TimeSpan ttl,
        CancellationToken ct = default);
}
```

### 구현

```csharp
using CloudStructures;
using CloudStructures.Structures;
using StackExchange.Redis;

public sealed class RedisDistributedLock : IDistributedLock
{
    private readonly RedisConnection _conn;

    public RedisDistributedLock(RedisConnection conn) => _conn = conn;

    public async Task<IAsyncDisposable?> AcquireAsync(string key, TimeSpan ttl, CancellationToken ct = default)
    {
        var token = Guid.NewGuid().ToString("N");
        var redisKey = $"lock:{key}";
        var redisString = new RedisString<string>(_conn, redisKey, ttl);

        // SET key value NX PX ttl
        var ok = await redisString.SetAsync(token, ttl, when: When.NotExists);
        if (!ok) return null;

        return new LockHandle(_conn, redisKey, token);
    }

    private sealed class LockHandle : IAsyncDisposable
    {
        private readonly RedisConnection _conn;
        private readonly string _key;
        private readonly string _token;

        public LockHandle(RedisConnection conn, string key, string token)
        {
            _conn = conn; _key = key; _token = token;
        }

        public async ValueTask DisposeAsync()
        {
            // 다른 사람의 락을 풀어버리지 않도록 토큰 검증 후 삭제
            const string releaseScript = @"
                if redis.call('get', KEYS[1]) == ARGV[1] then
                    return redis.call('del', KEYS[1])
                else
                    return 0
                end";

            var db = _conn.GetConnection().GetDatabase();
            await db.ScriptEvaluateAsync(releaseScript,
                new RedisKey[] { _key },
                new RedisValue[] { _token });
        }
    }
}
```

### 사용

```csharp
public sealed class LockedGachaService
{
    private readonly IDistributedLock _lock;
    private readonly SafeGachaService _service;

    public async Task<DrawResponse> DrawAsync(long userId, DrawRequest req, CancellationToken ct = default)
    {
        await using var token = await _lock.AcquireAsync(
            $"gacha:{userId}", TimeSpan.FromSeconds(5), ct);

        if (token is null)
            throw new GachaException("동시 요청이 너무 많습니다");

        return await _service.DrawAsync(userId, req, ct);
    }
}
```

### 락 재시도 로직 (선택)

```csharp
public async Task<IAsyncDisposable?> AcquireWithRetryAsync(
    string key, TimeSpan ttl, int maxRetries = 3, CancellationToken ct = default)
{
    for (int i = 0; i < maxRetries; i++)
    {
        var token = await AcquireAsync(key, ttl, ct);
        if (token is not null) return token;
        await Task.Delay(TimeSpan.FromMilliseconds(50 * (i + 1)), ct);
    }
    return null;
}
```

### 함정 1 — TTL 만료 후에도 처리 중

```
T0:    락 획득 (TTL 5초)
T6:    아직 처리 중인데 TTL 만료
T6.1:  다른 요청이 새 락 획득 → 동시 처리 발생
```

**해결**: TTL을 충분히 길게(추첨 평균 시간의 5배) 잡는다. 또는 락 갱신(Watchdog) 패턴을 쓴다. 가챠는 보통 100ms 이내라 5초로 충분하다.

### 함정 2 — 락 키 너무 좁거나 너무 넓음

| 키 | 동시성 | 충돌 |
|---|------|-----|
| `gacha:global` | 직렬화 (매우 느림) | 충돌 0 |
| `gacha:user:{userId}` | 유저 단위 직렬화 | 같은 유저 동시 요청 차단 ✓ |
| `gacha:user:{userId}:banner:{bannerId}` | 더 세밀 | 다른 배너 동시 가능 |

가챠는 **유저 단위**가 표준이다. 같은 유저가 두 배너에 동시에 뽑는 일은 거의 없다.

### 함정 3 — 락 안에서 외부 호출

```csharp
// ❌ 나쁨
await using var token = await _lock.AcquireAsync(...);
await SomeSlowExternalApiAsync();  // ← 락 잡은 채 외부 호출 = 다른 유저 영향?
                                    //  여기는 사용자별이라 영향 없지만, 락 만료 위험.
await ProcessGachaAsync();

// ✅ 좋음
await PrepareDataAsync();  // 락 밖에서 사전 준비
await using var token = await _lock.AcquireAsync(...);
await ProcessGachaAsync();   // 락 안에서는 짧고 단순한 작업만
```

### Redlock(여러 Redis 노드)는?

이론상 더 안전하지만, 가챠 정도의 도메인에서는 단일 Redis로도 충분하다. Redis가 다운되면 게임 자체가 중단되므로, 락의 가용성보다 **DB 트랜잭션의 무결성**이 우선이다.

---

## 12장 요약

- 가챠는 충돌 빈도가 높아 비관적 락이 적합하다.
- 분산락(Redis) + 비관적 락(MySQL FOR UPDATE) + 멱등성 키 — 세 겹으로 막는다.
- CloudStructures와 StackExchange.Redis로 토큰 기반 분산락을 구현한다.
- 락 키는 유저 단위(`gacha:user:{userId}`), TTL은 평균 처리 시간의 5배가 권장이다.

여기까지가 3부 서버 구현이다. 다음 4부에서는 운영, 즉 **배포 후 확률을 어떻게 검증·모니터링·법규 준수할 것인가**를 다룬다.
