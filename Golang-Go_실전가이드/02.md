# Chapter 02: 동기 프리미티브
## — Mutex, RWMutex, WaitGroup, Once, sync.Map 등 공유 리소스를 안전하게 처리하는 방법

---

**들어가며:**

Chapter 01에서 우리는 goroutine과 channel을 통해 Go의 병행 처리 모델을 경험했습니다. Go의 설계 철학은 **"메모리를 공유하여 통신하지 말고, 통신함으로써 메모리를 공유하라"** 이며, channel이 그 이상을 구현하는 가장 우아한 도구입니다. 그러나 현실의 프로그램은 항상 이상적으로 설계될 수 없습니다. 여러 goroutine이 **동일한 데이터 구조**를 공유해야 하거나, 초기화 로직을 단 한 번만 실행해야 하거나, 수천 개의 goroutine이 완료되기를 기다려야 하는 상황은 언제나 존재합니다.

이런 상황에서 channel만으로 모든 것을 해결하려 하면 오히려 코드가 복잡해지고, 성능이 저하되며, 버그가 숨어들 여지가 생깁니다. Go의 `sync` 패키지는 이러한 **공유 상태 관리**를 위한 저수준 도구들, 즉 **동기 프리미티브(Synchronization Primitives)** 를 제공합니다.

이 챕터에서는 `sync.Mutex`, `sync.RWMutex`, `sync.WaitGroup`, `sync.Once`, `sync.Cond`, `sync.Map`, 그리고 `sync/atomic` 패키지까지 Go의 동기화 도구 전반을 체계적으로 탐구합니다.

**2.1 데이터 레이스 — 모든 문제의 시작점:**

동기 프리미티브를 배우기 전에, 왜 이것들이 필요한지를 먼저 이해해야 합니다. 핵심 개념은 **데이터 레이스(Data Race)** 입니다.

**2.1.1 데이터 레이스란?**

두 개 이상의 goroutine이 동일한 메모리 위치에 **동시에 접근**하고, 그 중 적어도 하나가 **쓰기** 작업일 때, 그리고 아무런 동기화가 없을 때 데이터 레이스가 발생합니다. 데이터 레이스는 프로그램의 결과를 예측 불가능하게 만들고, 최악의 경우 조용히 잘못된 값을 사용하게 되어 디버깅이 매우 어렵습니다.

```go
// ❌ 데이터 레이스 예제 — 실행할 때마다 결과가 달라짐
package main

import (
	"fmt"
	"sync"
)

func main() {
	counter := 0
	var wg sync.WaitGroup

	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			counter++ // ❌ 여러 goroutine이 동시에 읽고 씀
		}()
	}

	wg.Wait()
	// 기대값: 1000, 실제값: ???  (780, 991, 1000 ... 매번 다름)
	fmt.Println("counter:", counter)
}
```

`counter++`는 단순해 보이지만 실제로는 세 단계로 분리됩니다.

```
counter++ 의 실제 실행 단계:

  1. READ  : 메모리에서 counter 값 읽기        → register = counter
  2. ADD   : 레지스터에 1 더하기               → register = register + 1
  3. WRITE : 결과를 다시 메모리에 쓰기          → counter = register

  레이스 시나리오:
  
  goroutine A          goroutine B
  ─────────────        ─────────────
  READ  → 5            
                       READ  → 5    ← A가 쓰기 전에 같은 값을 읽음!
  ADD   → 6            
  WRITE → 6            
                       ADD   → 6
                       WRITE → 6    ← 6이 두 번 쓰임 (7이 되어야 함)
  
  결과: 둘 다 더했는데 1만큼만 증가함!
```

**2.1.2 Go Race Detector — 레이스 탐지 도구**

Go는 빌트인으로 **레이스 탐지기(Race Detector)** 를 제공합니다. `-race` 플래그로 쉽게 활성화할 수 있습니다.

```bash
# 실행 시 레이스 탐지
go run -race main.go

# 테스트 시 레이스 탐지 (CI/CD 파이프라인에 필수!)
go test -race ./...

# 빌드 시 레이스 탐지 포함
go build -race -o myapp .
```

레이스가 탐지되면 아래와 같은 상세한 리포트가 출력됩니다.

```
==================
WARNING: DATA RACE
Write at 0x00c0000b4010 by goroutine 7:
  main.main.func1()
      /tmp/main.go:15 +0x44

Previous write at 0x00c0000b4010 by goroutine 6:
  main.main.func1()
      /tmp/main.go:15 +0x44

Goroutine 7 (running) created at:
  main.main()
      /tmp/main.go:12 +0x84
==================
```

> **💡 실무 팁:** `-race` 플래그는 런타임 오버헤드(메모리 5~10배, 속도 2~20배 느림)가 있으므로 프로덕션 빌드에는 사용하지 않습니다. 그러나 **개발 중과 CI 단계**에서는 항상 활성화하는 것이 강력히 권장됩니다.

**2.2 sync.Mutex — 상호 배제의 기초:**

**Mutex(Mutual Exclusion Lock)** 는 가장 기본적인 동기화 도구입니다. 한 번에 하나의 goroutine만이 특정 코드 구역(Critical Section, 임계 구역)에 진입할 수 있도록 보장합니다.

```
Mutex 동작 원리:

  goroutine A    goroutine B    goroutine C
  ─────────────  ─────────────  ─────────────
  Lock() ✅      Lock() 🔒      Lock() 🔒
  [임계 구역]     [대기 중...]    [대기 중...]
  Unlock()
                 Lock() ✅
                 [임계 구역]
                 Unlock()
                                Lock() ✅
                                [임계 구역]
                                Unlock()

  🔒 = 잠금이 걸려 있어 대기(블로킹)
  ✅ = 잠금 획득 성공, 임계 구역 진입
```

**2.2.1 Mutex 기본 사용법**

```go
package main

import (
	"fmt"
	"sync"
)

// SafeCounter는 Mutex로 보호되는 스레드 안전한 카운터입니다.
type SafeCounter struct {
	mu    sync.Mutex
	count int
}

// Increment는 카운터를 안전하게 증가시킵니다.
func (c *SafeCounter) Increment() {
	c.mu.Lock()
	defer c.mu.Unlock() // 함수 종료 시 자동으로 잠금 해제 (panic 상황에서도 안전)
	c.count++
}

// Value는 현재 카운터 값을 안전하게 반환합니다.
func (c *SafeCounter) Value() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.count
}

func main() {
	counter := &SafeCounter{}
	var wg sync.WaitGroup

	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			counter.Increment()
		}()
	}

	wg.Wait()
	fmt.Println("최종 카운터:", counter.Value()) // 항상 정확히 1000
}
```

> **⚠️ 중요 관례:** `sync.Mutex`는 반드시 **포인터**로 전달하거나, 구조체에 포함시켜야 합니다. 값으로 복사하면 잠금 상태도 함께 복사되어 예기치 않은 동작이 발생합니다. `go vet`은 이러한 실수를 탐지해 줍니다.

**2.2.2 Mutex의 올바른 설계 — 구조체 임베딩**

실무에서 Mutex는 보호하려는 데이터와 같은 구조체 안에 함께 두는 것이 좋은 설계입니다. 이렇게 하면 코드를 읽는 사람이 "이 구조체의 데이터는 Mutex로 보호된다"는 것을 즉시 알 수 있습니다.

```go
package main

import (
	"fmt"
	"sync"
)

// InventoryItem은 재고 항목을 나타냅니다.
type InventoryItem struct {
	Name     string
	Quantity int
}

// Inventory는 동시 접근에 안전한 재고 관리 구조체입니다.
// mu는 items를 보호하며, 항상 함께 다닙니다.
type Inventory struct {
	mu    sync.Mutex
	items map[string]*InventoryItem
}

// NewInventory는 새로운 Inventory를 생성합니다.
func NewInventory() *Inventory {
	return &Inventory{
		items: make(map[string]*InventoryItem),
	}
}

// AddItem은 재고에 새 항목을 추가합니다.
func (inv *Inventory) AddItem(name string, qty int) {
	inv.mu.Lock()
	defer inv.mu.Unlock()

	if item, exists := inv.items[name]; exists {
		item.Quantity += qty
	} else {
		inv.items[name] = &InventoryItem{Name: name, Quantity: qty}
	}
}

// Sell은 재고를 소비합니다. 재고 부족 시 오류를 반환합니다.
func (inv *Inventory) Sell(name string, qty int) error {
	inv.mu.Lock()
	defer inv.mu.Unlock()

	item, exists := inv.items[name]
	if !exists {
		return fmt.Errorf("상품 '%s'가 존재하지 않습니다", name)
	}
	if item.Quantity < qty {
		return fmt.Errorf("재고 부족: 필요 %d, 현재 %d", qty, item.Quantity)
	}
	item.Quantity -= qty
	return nil
}

// Stock은 특정 항목의 현재 재고량을 반환합니다.
func (inv *Inventory) Stock(name string) int {
	inv.mu.Lock()
	defer inv.mu.Unlock()

	if item, exists := inv.items[name]; exists {
		return item.Quantity
	}
	return 0
}

func main() {
	inv := NewInventory()
	inv.AddItem("사과", 100)
	inv.AddItem("바나나", 50)

	var wg sync.WaitGroup
	// 10개의 goroutine이 동시에 판매 시도
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			if err := inv.Sell("사과", 7); err != nil {
				fmt.Printf("[goroutine %d] 판매 실패: %v\n", id, err)
			} else {
				fmt.Printf("[goroutine %d] 사과 7개 판매 성공\n", id)
			}
		}(i)
	}

	wg.Wait()
	fmt.Printf("\n남은 사과 재고: %d개\n", inv.Stock("사과"))
}
```

**2.2.3 데드락 — 가장 위험한 함정**

Mutex의 가장 큰 위험은 **데드락(Deadlock)** 입니다. 두 goroutine이 서로가 가진 잠금을 기다리면 프로그램이 영원히 멈춥니다.

```go
// ❌ 데드락 시나리오
var mu1, mu2 sync.Mutex

go func() {
    mu1.Lock()
    // mu2를 기다리는 동안 mu1을 보유
    mu2.Lock() // ← goroutine B가 mu2를 잡고 있어서 영원히 대기
    defer mu2.Unlock()
    defer mu1.Unlock()
}()

go func() {
    mu2.Lock()
    // mu1을 기다리는 동안 mu2를 보유
    mu1.Lock() // ← goroutine A가 mu1을 잡고 있어서 영원히 대기
    defer mu1.Unlock()
    defer mu2.Unlock()
}()
```

```
데드락 다이어그램:

  goroutine A                 goroutine B
  ───────────                 ───────────
  mu1.Lock() ✅               mu2.Lock() ✅
  (mu1 보유)                  (mu2 보유)
       │                           │
       ↓                           ↓
  mu2.Lock() 🔒 ─── 대기 ──→ (mu2가 A 기다림)
  (mu2 기다림)                     │
       │                   mu1.Lock() 🔒
       │                   (mu1 기다림)
       └──────── 서로를 영원히 기다림 ──────────┘
                    💀 DEADLOCK
```

데드락을 방지하는 핵심 원칙은 **항상 동일한 순서로 잠금을 획득**하는 것입니다. 모든 goroutine이 `mu1 → mu2` 순서로만 잠금을 시도하면 데드락이 발생하지 않습니다.

**2.2.4 TryLock — 비블로킹 잠금 시도 (Go 1.18+)**

Go 1.18부터 `TryLock()` 메서드가 추가되었습니다. 잠금을 즉시 획득할 수 없으면 블로킹하지 않고 `false`를 반환합니다.

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func main() {
	var mu sync.Mutex

	// 잠금을 2초 동안 보유하는 goroutine
	go func() {
		mu.Lock()
		defer mu.Unlock()
		fmt.Println("[goroutine] 잠금 획득, 2초 보유")
		time.Sleep(2 * time.Second)
	}()

	time.Sleep(100 * time.Millisecond) // goroutine이 잠금을 획득할 시간

	// TryLock: 즉시 잠금 시도, 실패 시 대기 없이 반환
	if mu.TryLock() {
		defer mu.Unlock()
		fmt.Println("[main] TryLock 성공!")
	} else {
		// 잠금을 얻지 못했지만 프로그램은 계속 진행됨
		fmt.Println("[main] TryLock 실패 — 잠금 중, 다른 작업 수행")
	}
}
```

> **⚠️ TryLock 주의사항:** `TryLock`은 스핀락(spin-lock) 패턴과 조합하기 쉬워 보이지만, 실제로는 대부분의 상황에서 올바른 도구가 아닙니다. `TryLock`을 루프에서 반복 호출하면 CPU를 낭비하며, 특정 goroutine이 영원히 잠금을 얻지 못하는 기아(starvation) 문제가 생길 수 있습니다. 명확한 이유 없이는 사용을 피하십시오.

**2.3 sync.RWMutex — 읽기 많고 쓰기 적을 때의 최적화:**

많은 실무 시나리오에서 데이터를 **읽는 횟수**가 **쓰는 횟수**보다 압도적으로 많습니다. 예를 들어 설정값 캐시, 사용자 세션 저장소, DNS 캐시 등이 그러합니다. 이런 경우 `sync.Mutex`를 사용하면 읽기 goroutine들도 서로를 차단하게 되어 불필요한 성능 손실이 발생합니다.

`sync.RWMutex`는 이 문제를 해결합니다. **여러 goroutine이 동시에 읽을 수 있지만, 쓰기는 완전한 배타적 접근을 요구**합니다.

```
RWMutex 동작 원리:

  읽기 전용 모드 (RLock):
  ┌──────────┐  ┌──────────┐  ┌──────────┐
  │ Reader A │  │ Reader B │  │ Reader C │
  │ RLock ✅ │  │ RLock ✅ │  │ RLock ✅ │
  │ 동시접근 │  │ 동시접근 │  │ 동시접근 │
  └──────────┘  └──────────┘  └──────────┘
  (모든 Reader가 동시에 데이터 읽기 가능)

  쓰기 모드 (Lock):
  ┌────────────────────────────────────────┐
  │               Writer                  │
  │ Lock ✅ — 모든 Reader/Writer 차단      │
  │ (독점적 접근)                           │
  └────────────────────────────────────────┘

  전환 시 대기:
  Reader A (읽기 중) →  Writer (대기) → Reader B (대기)
  Reader A 완료 후 Writer 진입, Writer 완료 후 Reader B 진입
```

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// ConfigStore는 읽기가 훨씬 많은 설정 저장소입니다.
type ConfigStore struct {
	mu     sync.RWMutex
	config map[string]string
}

func NewConfigStore() *ConfigStore {
	return &ConfigStore{
		config: map[string]string{
			"host":    "localhost",
			"port":    "8080",
			"timeout": "30s",
		},
	}
}

// Get은 읽기 잠금만 사용하므로 여러 goroutine이 동시에 호출 가능합니다.
func (cs *ConfigStore) Get(key string) (string, bool) {
	cs.mu.RLock()         // 읽기 잠금: 다른 읽기와 동시 진행 가능
	defer cs.mu.RUnlock()
	val, ok := cs.config[key]
	return val, ok
}

// Set은 쓰기 잠금을 사용하므로 완전한 배타적 접근을 보장합니다.
func (cs *ConfigStore) Set(key, value string) {
	cs.mu.Lock()         // 쓰기 잠금: 모든 읽기/쓰기 차단
	defer cs.mu.Unlock()
	cs.config[key] = value
	fmt.Printf("[ConfigStore] 설정 업데이트: %s = %s\n", key, value)
}

// Snapshot은 현재 설정의 복사본을 반환합니다.
func (cs *ConfigStore) Snapshot() map[string]string {
	cs.mu.RLock()
	defer cs.mu.RUnlock()

	snapshot := make(map[string]string, len(cs.config))
	for k, v := range cs.config {
		snapshot[k] = v
	}
	return snapshot
}

func main() {
	store := NewConfigStore()
	var wg sync.WaitGroup

	// 100개의 읽기 goroutine (동시에 실행 가능)
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			if val, ok := store.Get("host"); ok {
				_ = val // 실제로는 val 사용
			}
		}(i)
	}

	// 3개의 쓰기 goroutine (배타적 접근 필요)
	for i := 0; i < 3; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			time.Sleep(time.Duration(id*10) * time.Millisecond)
			store.Set("timeout", fmt.Sprintf("%ds", 30+id*5))
		}(i)
	}

	wg.Wait()

	snapshot := store.Snapshot()
	fmt.Println("\n최종 설정:")
	for k, v := range snapshot {
		fmt.Printf("  %s: %s\n", k, v)
	}
}
```

**RWMutex vs Mutex 선택 가이드:**

```
성능 비교 (읽기 비율에 따른 처리량):

  읽기 100%, 쓰기 0%:
  RWMutex ████████████████████ 매우 빠름
  Mutex   ████                 병목 발생

  읽기 90%, 쓰기 10%:
  RWMutex ████████████████     빠름
  Mutex   █████████            보통

  읽기 50%, 쓰기 50%:
  RWMutex ████████             비슷하거나 약간 느림
  Mutex   ████████             (RWMutex 오버헤드)

  읽기 0%, 쓰기 100%:
  RWMutex ██████               느림 (오버헤드)
  Mutex   ████████             더 빠름

  결론: 읽기가 70% 이상 → RWMutex, 그 외 → Mutex 우선 고려
```

**2.4 sync.WaitGroup — Goroutine의 완료를 기다리는 카운터:**

`sync.WaitGroup`은 특정 수의 goroutine이 모두 완료될 때까지 기다리는 **카운터 기반 동기화** 도구입니다. Chapter 01에서 `time.Sleep`으로 임시방편 대기를 했던 문제를 `WaitGroup`으로 올바르게 해결합니다.

**2.4.1 WaitGroup 기본 동작 원리**

```
WaitGroup 내부 카운터:

  wg.Add(3)  →  counter: 3
  
  goroutine 1 시작    goroutine 2 시작    goroutine 3 시작
       │                    │                   │
       ↓                    ↓                   ↓
   작업 수행            작업 수행             작업 수행
       │                    │                   │
  wg.Done()           wg.Done()            wg.Done()
  counter: 2          counter: 1           counter: 0
                                                │
                                          wg.Wait() 해제!
                                         (counter == 0)

  wg.Wait() ← 메인 goroutine이 counter가 0이 될 때까지 블로킹
```

**2.4.2 올바른 WaitGroup 사용 패턴**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// DownloadResult는 다운로드 결과를 나타냅니다.
type DownloadResult struct {
	URL     string
	Size    int
	Elapsed time.Duration
	Err     error
}

// downloadFile은 파일 다운로드를 시뮬레이션합니다.
func downloadFile(url string) DownloadResult {
	start := time.Now()
	// 실제 다운로드 대신 지연으로 시뮬레이션
	time.Sleep(time.Duration(100+len(url)*10) * time.Millisecond)
	return DownloadResult{
		URL:     url,
		Size:    len(url) * 1024,
		Elapsed: time.Since(start),
	}
}

func main() {
	urls := []string{
		"https://example.com/file1.zip",
		"https://example.com/file2.tar.gz",
		"https://example.com/file3.iso",
		"https://example.com/file4.dmg",
		"https://example.com/file5.exe",
	}

	results := make([]DownloadResult, len(urls))
	var wg sync.WaitGroup

	start := time.Now()

	for i, url := range urls {
		wg.Add(1) // ✅ goroutine 시작 전에 Add 호출
		go func(idx int, u string) {
			defer wg.Done() // ✅ defer로 패닉 상황에서도 Done 보장
			results[idx] = downloadFile(u)
			fmt.Printf("  ✓ 완료: %s (%.2f KB, %v)\n",
				u, float64(results[idx].Size)/1024, results[idx].Elapsed)
		}(i, url) // ✅ 변수를 인자로 전달 (클로저 캡처 문제 방지)
	}

	wg.Wait() // 모든 다운로드가 완료될 때까지 블로킹
	elapsed := time.Since(start)

	fmt.Printf("\n전체 %d개 파일 병렬 다운로드 완료 (소요: %v)\n",
		len(urls), elapsed)
}
```

**2.4.3 WaitGroup 사용 시 주의사항**

```go
// ❌ 잘못된 패턴 1: goroutine 내부에서 Add 호출
var wg sync.WaitGroup
for i := 0; i < 5; i++ {
    go func() {
        wg.Add(1)        // ❌ Wait가 먼저 반환될 수 있음
        defer wg.Done()
        // 작업...
    }()
}
wg.Wait() // Add가 호출되기 전에 반환될 수 있음!

// ❌ 잘못된 패턴 2: Add와 Done 불일치
wg.Add(2)
go func() {
    defer wg.Done() // 1회만 Done → counter가 1에서 멈춤 → Wait 영원히 대기
    // 작업...
}()

// ❌ 잘못된 패턴 3: 음수 카운터 (panic 발생)
wg.Add(1)
wg.Done()
wg.Done() // panic: sync: negative WaitGroup counter

// ✅ 올바른 패턴: goroutine 시작 직전에 Add, 내부에서 defer Done
for i := 0; i < 5; i++ {
    wg.Add(1)          // goroutine 시작 전 Add
    go func(id int) {
        defer wg.Done() // defer로 항상 Done 보장
        // 작업...
    }(i)
}
wg.Wait()
```

**2.5 sync.Once — 단 한 번만 실행되는 초기화:**

`sync.Once`는 여러 goroutine이 동시에 호출하더라도 지정한 함수가 **정확히 한 번만 실행**되도록 보장합니다. 이는 지연 초기화(lazy initialization)나 싱글턴(singleton) 패턴에서 필수적입니다.

**2.5.1 Once의 내부 동작**

```
sync.Once 상태 전이:

  초기 상태: done = 0
       │
  goroutine A, B, C 동시에 once.Do(fn) 호출
       │
  ┌─────────────────────────────────────────┐
  │  내부적으로 atomic CAS 연산으로 경쟁     │
  │  done 0→1 성공한 goroutine만 fn() 실행  │
  └─────────────────────────────────────────┘
       │
  goroutine A: fn() 실행 (done = 1로 설정)
  goroutine B: done == 1이므로 fn() 건너뜀
  goroutine C: done == 1이므로 fn() 건너뜀
       │
  모든 goroutine: once.Do() 반환
  (fn()이 완료될 때까지 B, C는 대기함)
```

**2.5.2 Once를 활용한 싱글턴 패턴**

```go
package main

import (
	"database/sql"
	"fmt"
	"sync"

	_ "github.com/mattn/go-sqlite3" // 드라이버 임포트 예시
)

// DBConnection은 데이터베이스 연결 싱글턴을 나타냅니다.
type DBConnection struct {
	db  *sql.DB
	dsn string
}

var (
	dbInstance *DBConnection
	dbOnce     sync.Once
)

// GetDB는 DB 연결을 반환합니다. 최초 호출 시에만 연결을 생성합니다.
// 이후 호출은 동일한 인스턴스를 즉시 반환합니다.
func GetDB(dsn string) *DBConnection {
	dbOnce.Do(func() {
		fmt.Println("[DB] 데이터베이스 연결 초기화 중...")
		// 실제 연결 생성 (여기서는 시뮬레이션)
		dbInstance = &DBConnection{
			dsn: dsn,
		}
		fmt.Println("[DB] 데이터베이스 연결 완료!")
	})
	return dbInstance
}

func main() {
	var wg sync.WaitGroup

	// 10개의 goroutine이 동시에 DB 연결 요청
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			db := GetDB("postgres://localhost/mydb")
			fmt.Printf("[goroutine %d] DB 인스턴스 주소: %p\n", id, db)
		}(i)
	}

	wg.Wait()
	// "데이터베이스 연결 초기화 중..."은 정확히 한 번만 출력됨
	// 모든 goroutine이 동일한 인스턴스 주소를 출력
}
```

**2.5.3 Once를 이용한 지연 초기화 (Lazy Initialization)**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// ExpensiveResource는 초기화에 비용이 많이 드는 리소스입니다.
type ExpensiveResource struct {
	data  []byte
	ready bool
}

type LazyLoader struct {
	once     sync.Once
	resource *ExpensiveResource
}

// Get은 리소스를 반환합니다. 첫 호출 시에만 무거운 초기화를 수행합니다.
func (l *LazyLoader) Get() *ExpensiveResource {
	l.once.Do(func() {
		fmt.Println("[LazyLoader] 무거운 초기화 시작 (1초 소요)...")
		time.Sleep(1 * time.Second) // 무거운 초기화 시뮬레이션
		l.resource = &ExpensiveResource{
			data:  make([]byte, 1024*1024), // 1MB 할당
			ready: true,
		}
		fmt.Println("[LazyLoader] 초기화 완료!")
	})
	return l.resource
}

func main() {
	loader := &LazyLoader{}
	var wg sync.WaitGroup

	// 5개의 goroutine이 동시에 리소스 요청
	for i := 0; i < 5; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			res := loader.Get()
			fmt.Printf("[goroutine %d] 리소스 준비 상태: %v\n", id, res.ready)
		}(i)
	}

	wg.Wait()
}
```

> **⚠️ Once의 중요한 특성:** `sync.Once`는 리셋이 불가능합니다. 한 번 `Do`가 실행되면 이후에는 영원히 건너뜁니다. 만약 `fn()`이 패닉(panic)을 일으키더라도 `done` 상태가 `1`로 설정되므로, 이후 호출에서도 `fn()`은 실행되지 않습니다. 이 점을 반드시 염두에 두어야 합니다.

**2.6 sync.Cond — 조건 기반 대기와 신호:**

`sync.Cond`는 **조건 변수(Condition Variable)** 를 구현합니다. 특정 조건이 만족될 때까지 goroutine을 대기시키고, 조건이 변경되면 대기 중인 goroutine에게 신호를 보내는 저수준 동기화 도구입니다. OS의 `pthread_cond_wait`에 해당하는 개념입니다.

`sync.Cond`는 channel로 대체하기 어려운 상황, 특히 **여러 goroutine에게 브로드캐스트 신호**를 보내거나, **채널 없이 상태 변화를 감지**해야 할 때 유용합니다.

```
sync.Cond 동작 흐름:

  goroutine A (생산자)         goroutine B, C (소비자)
  ────────────────────         ────────────────────────
                               mu.Lock()
                               for !condition {
                                   cond.Wait()    ← 잠금 해제 후 대기
                               }
  mu.Lock()                    (블로킹 중...)
  condition = true
  cond.Signal()  or           ←── 신호 수신
  cond.Broadcast()             mu.Lock() 재획득
  mu.Unlock()                  조건 확인 후 작업
                               mu.Unlock()
```

**2.6.1 Cond를 활용한 작업 큐**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// BoundedQueue는 동기화된 크기 제한 큐입니다.
type BoundedQueue struct {
	mu       sync.Mutex
	notEmpty *sync.Cond // 큐가 비어있지 않음을 알리는 조건
	notFull  *sync.Cond // 큐가 가득 차지 않음을 알리는 조건
	items    []int
	capacity int
}

func NewBoundedQueue(capacity int) *BoundedQueue {
	q := &BoundedQueue{
		items:    make([]int, 0, capacity),
		capacity: capacity,
	}
	q.notEmpty = sync.NewCond(&q.mu)
	q.notFull = sync.NewCond(&q.mu)
	return q
}

// Enqueue는 큐에 값을 추가합니다. 큐가 가득 찬 경우 대기합니다.
func (q *BoundedQueue) Enqueue(val int) {
	q.mu.Lock()
	defer q.mu.Unlock()

	// ✅ 항상 for 루프로 조건 확인 (spurious wakeup 방어)
	for len(q.items) == q.capacity {
		fmt.Printf("  [Enqueue] 큐 가득 참 (%d/%d), 대기 중...\n",
			len(q.items), q.capacity)
		q.notFull.Wait() // 잠금 해제 후 신호 대기
	}

	q.items = append(q.items, val)
	fmt.Printf("  [Enqueue] %d 추가 (큐 크기: %d/%d)\n",
		val, len(q.items), q.capacity)
	q.notEmpty.Signal() // 대기 중인 Dequeue 하나에 신호
}

// Dequeue는 큐에서 값을 꺼냅니다. 큐가 비어 있으면 대기합니다.
func (q *BoundedQueue) Dequeue() int {
	q.mu.Lock()
	defer q.mu.Unlock()

	// ✅ for 루프로 조건 재확인 필수
	for len(q.items) == 0 {
		fmt.Println("  [Dequeue] 큐 비어 있음, 대기 중...")
		q.notEmpty.Wait()
	}

	val := q.items[0]
	q.items = q.items[1:]
	fmt.Printf("  [Dequeue] %d 꺼냄 (큐 크기: %d/%d)\n",
		val, len(q.items), q.capacity)
	q.notFull.Signal() // 대기 중인 Enqueue에 신호
	return val
}

func main() {
	q := NewBoundedQueue(3) // 최대 크기 3인 큐
	var wg sync.WaitGroup

	// 생산자: 6개의 값을 큐에 추가
	wg.Add(1)
	go func() {
		defer wg.Done()
		for i := 1; i <= 6; i++ {
			q.Enqueue(i * 10)
			time.Sleep(80 * time.Millisecond)
		}
	}()

	// 소비자: 6개의 값을 큐에서 꺼냄
	wg.Add(1)
	go func() {
		defer wg.Done()
		for i := 0; i < 6; i++ {
			time.Sleep(200 * time.Millisecond) // 생산자보다 느린 소비자
			q.Dequeue()
		}
	}()

	wg.Wait()
	fmt.Println("완료!")
}
```

> **💡 실무 조언:** `sync.Cond`는 강력하지만 올바르게 사용하기 까다롭습니다. `Wait()`를 반드시 `for` 루프 안에서 호출해야 하는 이유는 **가짜 깨어남(spurious wakeup)** 이 발생할 수 있기 때문입니다. 많은 경우 channel로 더 간단하게 같은 기능을 구현할 수 있으므로, `sync.Cond`는 정말 필요한 상황에서만 사용하십시오.

**2.7 sync.Map — 동시 안전한 맵:**

Go의 내장 `map`은 **스레드 안전하지 않습니다.** 여러 goroutine이 동시에 맵에 읽고 쓰면 프로그램이 패닉을 일으킵니다. `sync.Map`은 이를 해결하는 동시 안전한 맵 구현입니다.

**2.7.1 sync.Map의 내부 구조**

```
sync.Map 내부 구조:

  ┌─────────────────────────────────────────────────┐
  │                 sync.Map                        │
  │                                                 │
  │  read  (atomic.Value)                           │
  │  ┌───────────────────────────────┐              │
  │  │  읽기 전용 맵 (snapshot)       │ ← 잠금 없이  │
  │  │  key1 → value1                │   빠른 읽기   │
  │  │  key2 → value2                │              │
  │  └───────────────────────────────┘              │
  │                                                 │
  │  dirty (map + Mutex)                            │
  │  ┌───────────────────────────────┐              │
  │  │  쓰기 가능한 맵 (최신 데이터)  │ ← Mutex로    │
  │  │  key1 → value1 (updated)      │   보호된 쓰기 │
  │  │  key3 → value3 (new)          │              │
  │  └───────────────────────────────┘              │
  │                                                 │
  │  misses: dirty를 읽은 횟수 카운터               │
  │  (일정 횟수 초과 시 read를 dirty로 승격)         │
  └─────────────────────────────────────────────────┘

  최적화 시나리오:
  • 읽기 → read 맵에서 잠금 없이 즉시 반환 (빠름)
  • 쓰기 → dirty 맵에 잠금 후 저장 (약간 느림)
  • misses 임계값 초과 → dirty를 read로 승격 (프로모션)
```

**2.7.2 sync.Map 기본 사용법**

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var m sync.Map

	var wg sync.WaitGroup

	// 동시에 여러 goroutine에서 Store
	for i := 0; i < 5; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			key := fmt.Sprintf("user_%d", id)
			m.Store(key, fmt.Sprintf("Alice_%d", id))
		}(i)
	}
	wg.Wait()

	// 값 읽기 (Load)
	if val, ok := m.Load("user_1"); ok {
		fmt.Println("user_1:", val)
	}

	// 없으면 저장하고 반환 (LoadOrStore)
	actual, loaded := m.LoadOrStore("user_10", "New User")
	fmt.Printf("LoadOrStore: value=%v, alreadyExisted=%v\n", actual, loaded)

	// 삭제 (Delete)
	m.Delete("user_2")

	// 모든 키-값 순회 (Range)
	fmt.Println("\n전체 맵 내용:")
	m.Range(func(key, value any) bool {
		fmt.Printf("  %v: %v\n", key, value)
		return true // false 반환 시 순회 중단
	})

	// 읽고 삭제 (LoadAndDelete) — Go 1.15+
	if val, loaded := m.LoadAndDelete("user_3"); loaded {
		fmt.Printf("\nLoadAndDelete: user_3 = %v\n", val)
	}
}
```

**2.7.3 sync.Map vs map+Mutex 선택 기준**

```
사용 사례별 선택 가이드:

  sync.Map 을 사용해야 할 때:
  ✅ 키가 한 번 쓰여지고 이후 많이 읽히는 경우
  ✅ 여러 goroutine이 서로 다른 키에 읽기/쓰기하는 경우
  ✅ 예: 캐시, 세션 스토어, 서비스 레지스트리

  map + Mutex(RWMutex) 를 사용해야 할 때:
  ✅ 쓰기가 잦은 경우 (맵 내용이 자주 바뀜)
  ✅ 키의 개수를 알아야 할 때 (len() 필요)
  ✅ 타입 안전성이 필요할 때 (제네릭 맵)
  ✅ 복잡한 트랜잭션 처리가 필요할 때

  ⚠️ sync.Map의 단점:
  • 타입이 any (interface{})라 타입 단언 필요
  • len() 연산 불가
  • 쓰기 heavy한 경우 map+RWMutex보다 느림
  • 반드시 프로파일링 후 선택할 것
```

**2.8 sync/atomic — 락 없는 원자적 연산:**

`sync/atomic` 패키지는 CPU의 원자 명령(atomic instruction)을 직접 활용하여 **잠금 없이(lock-free)** 정수, 포인터 등을 안전하게 조작합니다. Mutex보다 훨씬 빠르지만, 적용 범위가 제한적입니다.

**2.8.1 atomic 기본 연산**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func main() {
	// Go 1.19+ 타입 안전한 원자 타입 사용 (권장)
	var counter atomic.Int64   // int64 원자 타입
	var flag    atomic.Bool    // bool 원자 타입
	var ptr     atomic.Pointer[string] // 포인터 원자 타입

	var wg sync.WaitGroup

	// 1000개의 goroutine에서 동시에 증가
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			counter.Add(1)  // 원자적 증가 (Mutex 없이 안전)
		}()
	}
	wg.Wait()

	fmt.Println("카운터:", counter.Load()) // 항상 1000

	// atomic.Bool 사용
	flag.Store(true)
	fmt.Println("flag:", flag.Load())

	// CAS (Compare-And-Swap): 기대값과 같으면 새 값으로 교체
	// 낙관적 락(optimistic locking) 패턴에 활용
	oldVal := counter.Load()
	swapped := counter.CompareAndSwap(oldVal, 9999)
	fmt.Printf("CAS 결과: swapped=%v, counter=%d\n",
		swapped, counter.Load())

	// atomic.Pointer 사용
	name := "초기값"
	ptr.Store(&name)
	fmt.Println("포인터 값:", *ptr.Load())

	newName := "업데이트된 값"
	ptr.Swap(&newName)
	fmt.Println("스왑 후:", *ptr.Load())
}
```

**2.8.2 atomic vs Mutex 선택 기준**

```
┌─────────────────────────────────────────────────────────────┐
│             atomic vs Mutex 비교                            │
├──────────────────────┬──────────────────────────────────────┤
│  특성                │  atomic            │  Mutex          │
├──────────────────────┼────────────────────┼─────────────────┤
│  성능                │  매우 빠름          │  보통           │
│  적용 범위           │  int, bool, ptr    │  모든 타입      │
│  복합 연산           │  ❌ 불가            │  ✅ 가능        │
│  코드 가독성         │  낮음              │  높음           │
│  오용 위험           │  높음              │  낮음           │
│  권장 사용처         │  카운터, 플래그     │  일반적 공유 상태│
└──────────────────────┴────────────────────┴─────────────────┘

실무 원칙:
• 단순 숫자 카운터/플래그 → atomic 고려
• 그 외 대부분의 경우 → Mutex가 더 안전하고 명확
• 먼저 Mutex로 구현하고, 프로파일링 후 필요시 atomic으로 최적화
```

**2.8.3 원자적 포인터를 이용한 무락(lock-free) 설정 교체**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

// Config는 애플리케이션 설정입니다.
type Config struct {
	MaxConnections int
	Timeout        time.Duration
	Debug          bool
}

// AtomicConfig는 무락으로 설정을 교체할 수 있는 래퍼입니다.
type AtomicConfig struct {
	ptr atomic.Pointer[Config]
}

func NewAtomicConfig(cfg *Config) *AtomicConfig {
	ac := &AtomicConfig{}
	ac.ptr.Store(cfg)
	return ac
}

// Load는 현재 설정을 락 없이 반환합니다. (읽기 경로 최적화)
func (ac *AtomicConfig) Load() *Config {
	return ac.ptr.Load()
}

// Update는 설정을 원자적으로 교체합니다.
func (ac *AtomicConfig) Update(cfg *Config) {
	ac.ptr.Store(cfg)
}

func main() {
	cfg := NewAtomicConfig(&Config{
		MaxConnections: 100,
		Timeout:        30 * time.Second,
		Debug:          false,
	})

	var wg sync.WaitGroup

	// 100개의 읽기 goroutine
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			c := cfg.Load() // 락 없이 즉시 반환
			_ = c.MaxConnections
		}()
	}

	// 설정 업데이트 (핫 리로드 시뮬레이션)
	go func() {
		time.Sleep(50 * time.Millisecond)
		cfg.Update(&Config{
			MaxConnections: 200, // 새 설정
			Timeout:        60 * time.Second,
			Debug:          true,
		})
		fmt.Println("[설정 업데이트] 새 설정 적용 완료")
	}()

	wg.Wait()
	fmt.Printf("최종 설정: MaxConn=%d, Debug=%v\n",
		cfg.Load().MaxConnections, cfg.Load().Debug)
}
```

**2.9 동기 프리미티브 선택 가이드:**

지금까지 배운 모든 도구들을 언제 어떻게 선택할지 정리합니다.

```
동기 프리미티브 선택 플로우차트:

  병행 goroutine 간 데이터 교환/통신이 필요한가?
            │
            ├── Yes → Channel 사용 (Go의 관용적 방법)
            │
            └── No → 공유 상태 보호가 필요한가?
                        │
                        ├── 단순 정수/bool/포인터 카운터? → atomic

                        │                └── 쓰기 heavy? → map + RWMutex

                        └── 일반적인 공유 상태 보호?

                                └── 그 외? → Mutex (가장 기본)
```

**2.10 응용 프로그램 — 스레드 안전한 인메모리 캐시 시스템:**

이 챕터에서 배운 모든 동기 프리미티브를 통합하여 **프로덕션 수준의 인메모리 캐시 시스템**을 구현합니다. TTL(Time To Live), 통계 수집, 자동 만료 제거, 동시 안전 접근을 모두 지원합니다.

```
캐시 시스템 아키텍처:

┌────────────────────────────────────────────────────────────────┐
│                    InMemoryCache                               │
│                                                                │
│  ┌─────────────────────────────────────────────────────────┐  │
│  │  items: map[string]*cacheItem (RWMutex 보호)             │  │
│  │  ┌──────────────────────────────────────────────────┐   │  │
│  │  │ key → { value, expiresAt, accessCount }          │   │  │
│  │  │ key → { value, expiresAt, accessCount }          │   │  │
│  │  └──────────────────────────────────────────────────┘   │  │
│  └─────────────────────────────────────────────────────────┘  │
│                                                                │
│  ┌─────────────────────────────────────────────────────────┐  │
│  │  stats: CacheStats (atomic 연산)                         │  │
│  │  • hits: atomic.Int64                                    │  │
│  │  • misses: atomic.Int64                                  │  │
│  │  • evictions: atomic.Int64                               │  │
│  └─────────────────────────────────────────────────────────┘  │
│                                                                │
│  ┌─────────────────────────────────────────────────────────┐  │
│  │  initOnce: sync.Once (초기화 보장)                        │  │
│  │  cleanupDone: chan struct{} (정리 goroutine 종료 신호)     │  │
│  └─────────────────────────────────────────────────────────┘  │
│                                                                │
│  정리 goroutine (백그라운드)                                    │
│  └── 주기적으로 만료된 항목 삭제 (WaitGroup으로 종료 대기)      │
└────────────────────────────────────────────────────────────────┘
```

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

// ─── 캐시 항목 ──────────────────────────────────────────────────────

// cacheItem은 캐시에 저장되는 개별 항목입니다.
type cacheItem struct {
	value       any
	expiresAt   time.Time // TTL 만료 시각 (zero = 영구)
	accessCount int64     // 접근 횟수
}

// isExpired는 항목이 만료되었는지 확인합니다.
func (item *cacheItem) isExpired() bool {
	if item.expiresAt.IsZero() {
		return false // TTL 없음 = 만료 없음
	}
	return time.Now().After(item.expiresAt)
}

// ─── 캐시 통계 ──────────────────────────────────────────────────────

// CacheStats는 캐시 운영 통계를 원자적으로 추적합니다.
type CacheStats struct {
	hits      atomic.Int64
	misses    atomic.Int64
	sets      atomic.Int64
	evictions atomic.Int64
}

func (s *CacheStats) recordHit()      { s.hits.Add(1) }
func (s *CacheStats) recordMiss()     { s.misses.Add(1) }
func (s *CacheStats) recordSet()      { s.sets.Add(1) }
func (s *CacheStats) recordEviction() { s.evictions.Add(1) }

// Summary는 통계 요약을 문자열로 반환합니다.
func (s *CacheStats) Summary() string {
	hits := s.hits.Load()
	misses := s.misses.Load()
	total := hits + misses
	hitRate := 0.0
	if total > 0 {
		hitRate = float64(hits) / float64(total) * 100
	}
	return fmt.Sprintf(
		"Hits: %d, Misses: %d, Sets: %d, Evictions: %d, HitRate: %.1f%%",
		hits, misses, s.sets.Load(), s.evictions.Load(), hitRate,
	)
}

// ─── 캐시 설정 옵션 ─────────────────────────────────────────────────

// CacheOptions는 캐시 설정 옵션입니다.
type CacheOptions struct {
	DefaultTTL      time.Duration // 기본 TTL (0 = 영구)
	CleanupInterval time.Duration // 만료 항목 정리 주기
	MaxItems        int           // 최대 항목 수 (0 = 무제한)
}

// DefaultCacheOptions는 기본 캐시 옵션을 반환합니다.
func DefaultCacheOptions() CacheOptions {
	return CacheOptions{
		DefaultTTL:      5 * time.Minute,
		CleanupInterval: 1 * time.Minute,
		MaxItems:        0,
	}
}

// ─── 인메모리 캐시 ──────────────────────────────────────────────────

// InMemoryCache는 TTL 지원 동시 안전 인메모리 캐시입니다.
type InMemoryCache struct {
	mu          sync.RWMutex      // items 맵 보호
	items       map[string]*cacheItem
	stats       CacheStats        // 원자적 통계 (별도 잠금 불필요)
	opts        CacheOptions
	initOnce    sync.Once         // 초기화 한 번만 실행
	cleanupDone chan struct{}      // 정리 goroutine 종료 신호
	wg          sync.WaitGroup    // 백그라운드 goroutine 종료 대기
}

// NewCache는 새로운 캐시 인스턴스를 생성합니다.
func NewCache(opts CacheOptions) *InMemoryCache {
	c := &InMemoryCache{
		items:       make(map[string]*cacheItem),
		opts:        opts,
		cleanupDone: make(chan struct{}),
	}
	// sync.Once로 백그라운드 정리 goroutine을 한 번만 시작
	c.initOnce.Do(func() {
		c.wg.Add(1)
		go c.cleanupLoop()
	})
	return c
}

// Set은 캐시에 값을 저장합니다. ttl=0이면 기본 TTL을 사용합니다.
func (c *InMemoryCache) Set(key string, value any, ttl time.Duration) {
	if ttl == 0 {
		ttl = c.opts.DefaultTTL
	}

	item := &cacheItem{
		value: value,
	}
	if ttl > 0 {
		item.expiresAt = time.Now().Add(ttl)
	}

	c.mu.Lock()
	// 최대 항목 수 초과 확인
	if c.opts.MaxItems > 0 && len(c.items) >= c.opts.MaxItems {
		// 간단한 LRU 정책: 첫 번째 키 삭제 (실무에서는 더 정교한 알고리즘 사용)
		for k := range c.items {
			delete(c.items, k)
			c.stats.recordEviction()
			fmt.Printf("[캐시] MaxItems 초과로 '%s' 강제 삭제\n", k)
			break
		}
	}
	c.items[key] = item
	c.mu.Unlock()

	c.stats.recordSet()
}

// Get은 캐시에서 값을 조회합니다.
// 두 번째 반환값: true=캐시 히트, false=캐시 미스 또는 만료
func (c *InMemoryCache) Get(key string) (any, bool) {
	// 먼저 읽기 잠금으로 빠르게 확인
	c.mu.RLock()
	item, exists := c.items[key]
	c.mu.RUnlock()

	if !exists {
		c.stats.recordMiss()
		return nil, false
	}

	if item.isExpired() {
		// 만료된 항목을 쓰기 잠금으로 삭제
		c.mu.Lock()
		delete(c.items, key)
		c.mu.Unlock()
		c.stats.recordMiss()
		c.stats.recordEviction()
		return nil, false
	}

	// 접근 횟수를 원자적으로 증가 (잠금 없이)
	atomic.AddInt64(&item.accessCount, 1)
	c.stats.recordHit()
	return item.value, true
}

// GetOrSet은 캐시에 값이 있으면 반환하고, 없으면 fn()을 실행하여 저장합니다.
// 동일한 키에 대해 fn()이 한 번만 실행됨을 보장합니다.
func (c *InMemoryCache) GetOrSet(
	key string,
	fn func() (any, error),
	ttl time.Duration,
) (any, error) {
	// 먼저 읽기 시도
	if val, ok := c.Get(key); ok {
		return val, nil
	}

	// 없으면 쓰기 잠금으로 확인 후 저장 (double-checked locking)
	c.mu.Lock()
	defer c.mu.Unlock()

	// 잠금 획득 사이에 다른 goroutine이 이미 저장했을 수 있음
	if item, exists := c.items[key]; exists && !item.isExpired() {
		atomic.AddInt64(&item.accessCount, 1)
		c.stats.recordHit()
		return item.value, nil
	}

	// 실제 값 계산 (잠금 보유 중이므로 오직 하나만 실행됨)
	val, err := fn()
	if err != nil {
		return nil, err
	}

	item := &cacheItem{value: val}
	if ttl == 0 {
		ttl = c.opts.DefaultTTL
	}
	if ttl > 0 {
		item.expiresAt = time.Now().Add(ttl)
	}
	c.items[key] = item
	c.stats.recordSet()

	return val, nil
}

// Delete는 캐시에서 특정 키를 삭제합니다.
func (c *InMemoryCache) Delete(key string) {
	c.mu.Lock()
	delete(c.items, key)
	c.mu.Unlock()
}

// Size는 현재 캐시에 저장된 항목 수를 반환합니다.
func (c *InMemoryCache) Size() int {
	c.mu.RLock()
	defer c.mu.RUnlock()
	return len(c.items)
}

// Stats는 현재 캐시 통계를 반환합니다.
func (c *InMemoryCache) Stats() string {
	return c.stats.Summary()
}

// cleanupLoop는 주기적으로 만료된 항목을 삭제하는 백그라운드 goroutine입니다.
func (c *InMemoryCache) cleanupLoop() {
	defer c.wg.Done()

	ticker := time.NewTicker(c.opts.CleanupInterval)
	defer ticker.Stop()

	for {
		select {
		case <-c.cleanupDone:
			fmt.Println("[캐시 정리기] 종료")
			return
		case <-ticker.C:
			c.evictExpired()
		}
	}
}

// evictExpired는 만료된 모든 항목을 삭제합니다.
func (c *InMemoryCache) evictExpired() {
	// 먼저 읽기 잠금으로 만료 키 수집
	c.mu.RLock()
	var expiredKeys []string
	for key, item := range c.items {
		if item.isExpired() {
			expiredKeys = append(expiredKeys, key)
		}
	}
	c.mu.RUnlock()

	if len(expiredKeys) == 0 {
		return
	}

	// 쓰기 잠금으로 실제 삭제
	c.mu.Lock()
	for _, key := range expiredKeys {
		// 재확인: 읽기 잠금 해제 후 다른 goroutine이 갱신했을 수 있음
		if item, exists := c.items[key]; exists && item.isExpired() {
			delete(c.items, key)
			c.stats.recordEviction()
		}
	}
	c.mu.Unlock()

	fmt.Printf("[캐시 정리기] %d개 만료 항목 삭제\n", len(expiredKeys))
}

// Close는 캐시를 종료하고 백그라운드 goroutine이 완전히 종료될 때까지 대기합니다.
func (c *InMemoryCache) Close() {
	close(c.cleanupDone) // 종료 신호 broadcast
	c.wg.Wait()          // 모든 백그라운드 goroutine 완료 대기
	fmt.Println("[캐시] 완전 종료")
}

// ─── 메인 함수 ────────────────────────────────────────────────────────

func main() {
	fmt.Println("══════════════════════════════════════════")
	fmt.Println("   🗄️  인메모리 캐시 시스템 시작")
	fmt.Println("══════════════════════════════════════════")

	opts := CacheOptions{
		DefaultTTL:      500 * time.Millisecond, // 데모용 짧은 TTL
		CleanupInterval: 300 * time.Millisecond,
		MaxItems:        10,
	}
	cache := NewCache(opts)
	defer cache.Close()

	var wg sync.WaitGroup

	// ── 시나리오 1: 동시 쓰기 ──
	fmt.Println("\n[시나리오 1] 20개 goroutine 동시 쓰기")
	for i := 0; i < 20; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			key := fmt.Sprintf("item:%d", id%10) // 10개 키에 중복 쓰기
			cache.Set(key, fmt.Sprintf("value_%d", id), 0)
		}(i)
	}
	wg.Wait()
	fmt.Printf("쓰기 완료 — 캐시 크기: %d\n", cache.Size())

	// ── 시나리오 2: 동시 읽기 ──
	fmt.Println("\n[시나리오 2] 50개 goroutine 동시 읽기")
	for i := 0; i < 50; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			key := fmt.Sprintf("item:%d", id%12) // 일부는 캐시 미스
			if val, ok := cache.Get(key); ok {
				_ = val
			}
		}(i)
	}
	wg.Wait()
	fmt.Println("읽기 완료")

	// ── 시나리오 3: GetOrSet 패턴 (중복 계산 방지) ──
	fmt.Println("\n[시나리오 3] GetOrSet — 중복 계산 방지")
	computeCount := atomic.Int64{}

	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			val, err := cache.GetOrSet("expensive_result", func() (any, error) {
				computeCount.Add(1)
				fmt.Println("  [비싼 계산] 실행 중...")
				time.Sleep(50 * time.Millisecond)
				return "계산 결과 42", nil
			}, 2*time.Second)
			if err == nil {
				_ = val
			}
		}(i)
	}
	wg.Wait()
	fmt.Printf("GetOrSet 완료 — 실제 계산 횟수: %d (10개 goroutine 중)\n",
		computeCount.Load())

	// ── 시나리오 4: TTL 만료 확인 ──
	fmt.Println("\n[시나리오 4] TTL 만료 확인")
	cache.Set("short_lived", "임시 데이터", 200*time.Millisecond)

	if val, ok := cache.Get("short_lived"); ok {
		fmt.Println("  200ms 전: 데이터 존재 →", val)
	}

	time.Sleep(300 * time.Millisecond) // TTL 만료 대기

	if _, ok := cache.Get("short_lived"); !ok {
		fmt.Println("  300ms 후: 데이터 만료됨 ✓")
	}

	// ── 최종 통계 출력 ──
	fmt.Println("\n══════════════════════════════════════════")
	fmt.Println("   📊 캐시 통계")
	fmt.Println("══════════════════════════════════════════")
	fmt.Println(" ", cache.Stats())
	fmt.Printf("  현재 캐시 크기: %d\n", cache.Size())
	fmt.Println("══════════════════════════════════════════")
}
```
