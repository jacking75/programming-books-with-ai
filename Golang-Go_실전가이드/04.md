## 4.1 Context란 무엇인가?

Go의 `context` 패키지는 Go 1.7에서 표준 라이브러리에 공식 편입된 이후, 현재까지 Go 동시성 프로그래밍에서 가장 핵심적인 도구로 자리매김하고 있습니다. 이름에서 알 수 있듯이 `Context`는 실행 "맥락(문맥)"을 담는 그릇입니다. 함수 호출 경계와 goroutine 사이를 넘나들며 **취소 신호(cancellation signal)**, **타임아웃/데드라인(timeout/deadline)**, 그리고 **요청 범위 값(request-scoped values)** 세 가지 핵심 정보를 전달하는 역할을 합니다.

Context가 왜 필요한지 직관적으로 이해하려면, Context 없이 발생하는 전형적인 문제들을 떠올려보면 됩니다. HTTP 요청을 처리하는 서버가 있다고 가정합니다. 클라이언트가 요청을 보내고, 서버는 데이터베이스 쿼리를 시작했습니다. 그런데 클라이언트가 갑자기 연결을 끊었습니다. 이 상황에서 Context가 없다면 데이터베이스 쿼리는 계속 실행되며 불필요한 CPU와 메모리를 소모하게 됩니다. Context가 있다면, 클라이언트 연결이 끊어지는 순간 해당 요청과 연관된 모든 하위 goroutine에 취소 신호가 자동으로 전파됩니다.

```
┌─────────────────────────────────────────────────────────────────┐
│                   Context가 해결하는 3가지 문제                    │
├──────────────────┬─────────────────────┬────────────────────────┤
│  취소 전파        │   타임아웃/데드라인   │  요청 범위 값           │
│  (Cancellation) │   (Timeout/Deadline) │  (Request-Scoped Value)│
├──────────────────┼─────────────────────┼────────────────────────┤
│  클라이언트 끊김  │  DB 쿼리 2초 제한    │  요청 ID 전달           │
│  → 모든 하위 작업│  → 초과 시 자동 취소  │  → 로그에서 추적 가능   │
│    자동 취소     │                     │                        │
└──────────────────┴─────────────────────┴────────────────────────┘
```

## 4.2 Context 인터페이스 해부

`context.Context`는 4개의 메서드로 이루어진 간결한 인터페이스입니다.

```go
type Context interface {
    // 이 Context가 취소될 예정 시각을 반환합니다.
    // 데드라인이 없으면 ok는 false입니다.
    Deadline() (deadline time.Time, ok bool)

    // 취소 신호를 받기 위한 채널입니다.
    // Context가 취소되면 이 채널이 닫힙니다.
    // 취소 불가능한 Context(Background, TODO)의 경우 nil을 반환합니다.
    Done() <-chan struct{}

    // Context가 취소된 이유를 반환합니다.
    // 아직 취소되지 않았으면 nil입니다.
    // context.Canceled 또는 context.DeadlineExceeded 중 하나입니다.
    Err() error

    // key에 연관된 값을 반환합니다.
    // 없으면 nil을 반환합니다.
    Value(key any) any
}
```

이 네 가지 메서드의 상호 작용 방식을 이해하는 것이 Context 마스터의 핵심입니다. `Done()` 채널은 취소 신호의 "알림창" 역할을 하며, `Err()`는 "왜 취소되었는가"를 알려줍니다. `Deadline()`은 "언제까지 살아있는가"를 확인할 수 있게 해주며, `Value()`는 요청 범위의 부가 정보를 꺼내는 창구입니다.

## 4.3 Context의 계층 구조 — 루트에서 잎으로

Context는 **불변(immutable)** 하며 **트리 구조**로 구성됩니다. 새로운 속성을 추가할 때마다 기존 Context를 부모로 삼아 자식 Context를 생성합니다. 부모 Context가 취소되면 모든 자식 Context도 연쇄적으로 취소됩니다. 반대 방향(자식 → 부모)으로는 전파되지 않습니다.

```
context.Background()  (루트 - 절대 취소되지 않음)
        │
        ▼
context.WithCancel(ctx)  ← 수동 취소 가능
        │
        ├──────────────────────────┐
        ▼                          ▼
context.WithTimeout(ctx, 5s)   context.WithValue(ctx, key, val)
        │                               │
        ▼                               ▼
context.WithValue(ctx, "reqID", id)  context.WithCancel(ctx)
        │
        ▼
  HTTP Handler / DB Query / gRPC Call ...

[부모 취소 → 모든 자식 자동 취소]
[자식 취소 → 부모에는 영향 없음]
```

## 4.4 루트 Context — Background와 TODO

모든 Context 트리는 루트에서 시작합니다. Go 표준 라이브러리는 두 가지 루트 Context를 제공합니다.

`context.Background()`는 비어있고, 절대 취소되지 않으며, 데드라인도 없고, 값도 없는 Context입니다. `main()` 함수, 초기화 코드, 최상위 요청의 시작점으로 사용합니다. `context.TODO()`는 기능적으로 `Background()`와 동일하지만 의미론적으로 다릅니다. "아직 어떤 Context를 사용해야 할지 결정하지 못했다"는 표시로, 리팩토링 중간 단계에서 임시로 사용하며, 코드 리뷰어나 정적 분석 도구에게 "이 부분은 나중에 다시 봐야 한다"는 신호를 줍니다.

```go
package main

import (
    "context"
    "fmt"
)

func main() {
    // 프로덕션 코드의 최상위 Context
    bg := context.Background()
    fmt.Println(bg)         // context.Background

    // 아직 결정 못한 Context (개발 중 임시 사용)
    todo := context.TODO()
    fmt.Println(todo)       // context.TODO

    // Deadline 없음 확인
    _, ok := bg.Deadline()
    fmt.Println(ok)         // false

    // Done 채널은 nil (절대 닫히지 않음)
    fmt.Println(bg.Done())  // <nil>
}
```

## 4.5 WithCancel — 수동 취소 제어

`context.WithCancel()`은 수동으로 취소할 수 있는 Context를 생성합니다. 반환되는 `cancel` 함수를 호출하면 해당 Context와 모든 자식 Context의 `Done()` 채널이 닫힙니다.

```go
package main

import (
    "context"
    "fmt"
    "time"
)

// longRunningTask는 ctx가 취소될 때까지 또는 작업이 끝날 때까지 실행됩니다.
func longRunningTask(ctx context.Context, id int) {
    for {
        select {
        case <-ctx.Done():
            // 취소 신호를 받으면 정리 후 종료
            fmt.Printf("Task %d: 취소됨 - 이유: %v\n", id, ctx.Err())
            return
        default:
            // 실제 작업 수행 (100ms 단위)
            fmt.Printf("Task %d: 작업 중...\n", id)
            time.Sleep(100 * time.Millisecond)
        }
    }
}

func main() {
    // 부모 Context에서 취소 가능한 Context 생성
    ctx, cancel := context.WithCancel(context.Background())

    // ★ 핵심 규칙: 항상 defer cancel()로 리소스 누수 방지
    defer cancel()

    // 3개의 goroutine 실행
    for i := 1; i <= 3; i++ {
        go longRunningTask(ctx, i)
    }

    // 300ms 후 모든 goroutine 취소
    time.Sleep(300 * time.Millisecond)
    fmt.Println("메인: 모든 작업 취소 요청")
    cancel() // 이 순간 모든 goroutine의 ctx.Done()이 닫힘

    // goroutine들이 정리할 시간 부여
    time.Sleep(50 * time.Millisecond)
    fmt.Println("메인: 종료")
}
```

실행 결과는 다음과 같습니다.

```
Task 1: 작업 중...
Task 2: 작업 중...
Task 3: 작업 중...
Task 1: 작업 중...
Task 2: 작업 중...
Task 3: 작업 중...
Task 1: 작업 중...
메인: 모든 작업 취소 요청
Task 1: 취소됨 - 이유: context canceled
Task 2: 취소됨 - 이유: context canceled
Task 3: 취소됨 - 이유: context canceled
메인: 종료
```

`cancel()`은 여러 번 호출해도 안전합니다. 첫 번째 호출만 효과가 있고 이후 호출은 무시됩니다. 이 점에서 채널의 `close()`(두 번 닫으면 패닉)보다 훨씬 안전합니다.

## 4.6 WithTimeout — 지속 시간 기반 타임아웃

`context.WithTimeout()`은 지정한 시간이 경과하면 자동으로 취소되는 Context를 생성합니다. 네트워크 요청, 데이터베이스 쿼리, 외부 API 호출 등 "이 작업은 N초 안에 끝나야 한다"는 제약을 표현할 때 사용합니다.

```go
package main

import (
    "context"
    "errors"
    "fmt"
    "time"
)

// simulateDBQuery는 데이터베이스 쿼리를 시뮬레이션합니다.
func simulateDBQuery(ctx context.Context, query string) (string, error) {
    // 실제로는 DB 드라이버가 ctx를 사용하여 쿼리를 실행합니다.
    // 여기서는 시뮬레이션을 위해 채널로 처리합니다.
    resultCh := make(chan string, 1)

    go func() {
        // DB 쿼리 처리 시간 시뮬레이션 (여기서는 2초)
        time.Sleep(2 * time.Second)
        resultCh <- "user: Alice"
    }()

    select {
    case result := <-resultCh:
        return result, nil
    case <-ctx.Done():
        // ctx.Err()는 context.DeadlineExceeded 또는 context.Canceled 반환
        return "", fmt.Errorf("쿼리 '%s' 실패: %w", query, ctx.Err())
    }
}

func main() {
    // 케이스 1: 타임아웃 내에 완료 (3초 타임아웃, 쿼리 2초)
    fmt.Println("=== 케이스 1: 타임아웃 내 완료 ===")
    ctx1, cancel1 := context.WithTimeout(context.Background(), 3*time.Second)
    defer cancel1()

    result, err := simulateDBQuery(ctx1, "SELECT * FROM users")
    if err != nil {
        fmt.Println("오류:", err)
    } else {
        fmt.Println("결과:", result)
    }

    // 케이스 2: 타임아웃 초과 (1초 타임아웃, 쿼리 2초)
    fmt.Println("\n=== 케이스 2: 타임아웃 초과 ===")
    ctx2, cancel2 := context.WithTimeout(context.Background(), 1*time.Second)
    defer cancel2()

    result, err = simulateDBQuery(ctx2, "SELECT * FROM large_table")
    if err != nil {
        // errors.Is()로 타임아웃 여부 확인
        if errors.Is(err, context.DeadlineExceeded) {
            fmt.Println("타임아웃 발생:", err)
        } else {
            fmt.Println("기타 오류:", err)
        }
    } else {
        fmt.Println("결과:", result)
    }

    // 데드라인 정보 확인
    fmt.Println("\n=== 데드라인 정보 ===")
    ctx3, cancel3 := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel3()

    deadline, ok := ctx3.Deadline()
    if ok {
        remaining := time.Until(deadline)
        fmt.Printf("데드라인까지 남은 시간: %.2f초\n", remaining.Seconds())
    }
}
```

실행 결과는 다음과 같습니다.

```
=== 케이스 1: 타임아웃 내 완료 ===
결과: user: Alice

=== 케이스 2: 타임아웃 초과 ===
타임아웃 발생: 쿼리 'SELECT * FROM large_table' 실패: context deadline exceeded

=== 데드라인 정보 ===
데드라인까지 남은 시간: 4.99초
```

## 4.7 WithDeadline — 절대 시각 기반 데드라인

`context.WithDeadline()`은 특정 `time.Time` 시각에 취소되는 Context를 생성합니다. `WithTimeout()`과의 차이는 "지금부터 N초 후" 대신 "오후 3시 정각"처럼 절대 시각을 지정한다는 점입니다. 내부적으로 `WithTimeout()`은 `WithDeadline()`을 래핑한 것에 불과합니다.

```go
// Go 표준 라이브러리 내부 구현
func WithTimeout(parent Context, timeout time.Duration) (Context, CancelFunc) {
    return WithDeadline(parent, time.Now().Add(timeout))
}
```

```go
package main

import (
    "context"
    "fmt"
    "time"
)

func main() {
    // 업무 시간 마감 (이번 예시에서는 500ms 후)
    businessDeadline := time.Now().Add(500 * time.Millisecond)

    ctx, cancel := context.WithDeadline(context.Background(), businessDeadline)
    defer cancel()

    deadline, ok := ctx.Deadline()
    if ok {
        fmt.Printf("마감 시각: %s\n", deadline.Format("15:04:05.000"))
        fmt.Printf("남은 시간: %v\n", time.Until(deadline).Round(time.Millisecond))
    }

    // 작업 시도
    select {
    case <-time.After(1 * time.Second): // 1초 걸리는 작업
        fmt.Println("작업 완료")
    case <-ctx.Done():
        fmt.Printf("마감 초과: %v\n", ctx.Err())
    }
}
```

실행 결과는 다음과 같습니다.

```
마감 시각: 14:30:05.123
남은 시간: 500ms
마감 초과: context deadline exceeded
```

## 4.8 부모-자식 Context의 타임아웃 상속 규칙

Context 계층에서 타임아웃은 **"더 엄격한 쪽이 항상 우선"** 합니다. 자식 Context는 부모의 타임아웃을 더 짧게 줄일 수 있지만, 더 길게 연장할 수는 없습니다.

```
부모 Context: WithTimeout 5초
    │
    ├── 자식 A: WithTimeout 2초  → 실효 타임아웃: 2초 (더 엄격)
    │
    ├── 자식 B: WithTimeout 10초 → 실효 타임아웃: 5초 (부모가 더 엄격)
    │
    └── 자식 C: WithCancel       → 실효 타임아웃: 5초 (부모 따라감)
```

```go
package main

import (
    "context"
    "fmt"
    "time"
)

func processWithContext(ctx context.Context, name string, workDuration time.Duration) {
    resultCh := make(chan struct{}, 1)
    go func() {
        time.Sleep(workDuration)
        resultCh <- struct{}{}
    }()

    select {
    case <-resultCh:
        fmt.Printf("[%s] 작업 완료\n", name)
    case <-ctx.Done():
        fmt.Printf("[%s] 취소됨: %v\n", name, ctx.Err())
    }
}

func main() {
    // 부모: 5초 타임아웃
    parentCtx, parentCancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer parentCancel()

    // 자식 A: 2초 타임아웃 (부모보다 엄격 → 2초 적용)
    childCtxA, cancelA := context.WithTimeout(parentCtx, 2*time.Second)
    defer cancelA()

    // 자식 B: 10초 타임아웃 (부모보다 느슨 → 부모의 5초 적용)
    childCtxB, cancelB := context.WithTimeout(parentCtx, 10*time.Second)
    defer cancelB()

    fmt.Println("=== 타임아웃 상속 테스트 ===")

    deadlineA, _ := childCtxA.Deadline()
    deadlineB, _ := childCtxB.Deadline()
    deadlineP, _ := parentCtx.Deadline()

    fmt.Printf("부모 데드라인:  %v 후\n", time.Until(deadlineP).Round(time.Millisecond))
    fmt.Printf("자식 A 데드라인: %v 후 (더 엄격)\n", time.Until(deadlineA).Round(time.Millisecond))
    fmt.Printf("자식 B 데드라인: %v 후 (부모 따라감)\n", time.Until(deadlineB).Round(time.Millisecond))

    fmt.Println("\n--- 3초 걸리는 작업 시도 ---")
    // 자식 A(2초 타임아웃)로 3초 작업 → 실패
    processWithContext(childCtxA, "자식A", 3*time.Second)
    // 자식 B(실효 5초 타임아웃)로 3초 작업 → 성공
    processWithContext(childCtxB, "자식B", 3*time.Second)
}
```

실행 결과는 다음과 같습니다.

```
=== 타임아웃 상속 테스트 ===
부모 데드라인:  5s 후
자식 A 데드라인: 2s 후 (더 엄격)
자식 B 데드라인: 5s 후 (부모 따라감)

--- 3초 걸리는 작업 시도 ---
[자식A] 취소됨: context deadline exceeded
[자식B] 작업 완료
```

## 4.9 WithCancelCause — 취소 원인 추적 (Go 1.20+)

기존의 `ctx.Err()`는 `context.Canceled` 또는 `context.DeadlineExceeded` 두 가지만 반환합니다. 하지만 실제 운영 환경에서는 "왜 취소되었는가"라는 더 구체적인 정보가 필요합니다. Go 1.20에 추가된 `context.WithCancelCause()`는 취소 원인을 커스텀 에러로 기록할 수 있게 해줍니다.

```go
package main

import (
    "context"
    "errors"
    "fmt"
)

// 도메인 특화 에러 정의
var (
    ErrUserLoggedOut    = errors.New("사용자 로그아웃")
    ErrQuotaExceeded    = errors.New("요청 할당량 초과")
    ErrUpstreamFailure  = errors.New("업스트림 서비스 오류")
)

func main() {
    fmt.Println("=== WithCancelCause 예시 ===\n")

    // 1. 기본 WithCancel: 이유를 알 수 없음
    ctx1, cancel1 := context.WithCancel(context.Background())
    cancel1()
    fmt.Printf("[기본 취소] ctx.Err()  = %v\n", ctx1.Err())
    fmt.Printf("[기본 취소] Cause(ctx) = %v\n\n", context.Cause(ctx1))

    // 2. WithCancelCause: 구체적인 원인 기록 가능
    ctx2, cancel2 := context.WithCancelCause(context.Background())
    cancel2(ErrUserLoggedOut) // 원인과 함께 취소
    fmt.Printf("[원인 취소] ctx.Err()  = %v\n", ctx2.Err())
    fmt.Printf("[원인 취소] Cause(ctx) = %v\n\n", context.Cause(ctx2))

    // 3. 실용 예시: 여러 goroutine 중 하나가 실패했을 때 원인 파악
    ctx3, cancel3 := context.WithCancelCause(context.Background())

    go func() {
        // 외부 API 호출 시뮬레이션 - 실패
        fmt.Println("goroutine: 외부 API 호출 실패 감지")
        cancel3(ErrUpstreamFailure)
    }()

    // 취소 신호 대기
    <-ctx3.Done()

    cause := context.Cause(ctx3)
    switch {
    case errors.Is(cause, ErrUpstreamFailure):
        fmt.Println("처리: 업스트림 서비스 재시도 로직 실행")
    case errors.Is(cause, ErrUserLoggedOut):
        fmt.Println("처리: 세션 정리 수행")
    case errors.Is(cause, ErrQuotaExceeded):
        fmt.Println("처리: 429 Too Many Requests 응답")
    default:
        fmt.Printf("처리: 알 수 없는 원인 - %v\n", cause)
    }
}
```

실행 결과는 다음과 같습니다.

```

[기본 취소] ctx.Err()  = context canceled
[기본 취소] Cause(ctx) = context canceled

[원인 취소] ctx.Err()  = context canceled
[원인 취소] Cause(ctx) = 사용자 로그아웃

goroutine: 외부 API 호출 실패 감지
처리: 업스트림 서비스 재시도 로직 실행
```

Go 1.21에는 `WithTimeoutCause()`와 `WithDeadlineCause()`도 추가되어 타임아웃 시 커스텀 원인을 지정할 수 있습니다.

```go
// Go 1.21+: 타임아웃 원인 지정
ctx, cancel := context.WithTimeoutCause(
    context.Background(),
    100*time.Millisecond,
    errors.New("외부 API SLA 초과"),
)
defer cancel()

// 타임아웃 발생 시 context.Cause(ctx) = "외부 API SLA 초과"
```

## 4.10 context.AfterFunc — 취소 시 콜백 실행 (Go 1.21+)

`context.AfterFunc()`는 Go 1.21에 추가된 기능으로, Context가 취소되는 순간 특정 함수를 별도의 goroutine에서 실행할 수 있게 해줍니다. 이를 통해 리소스 정리, 알림 전송 등의 후처리를 비침투적으로 등록할 수 있습니다.

```go
package main

import (
    "context"
    "fmt"
    "sync"
    "time"
)

func main() {
    fmt.Println("=== context.AfterFunc 예시 ===\n")

    // 1. 기본 사용법
    ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
    defer cancel()

    var wg sync.WaitGroup
    wg.Add(1)

    // 취소 시 실행될 함수 등록
    context.AfterFunc(ctx, func() {
        defer wg.Done()
        fmt.Println("AfterFunc: Context 취소됨 → 리소스 정리 실행")
        // 예: 임시 파일 삭제, 연결 해제 등
    })

    fmt.Println("작업 시작...")
    time.Sleep(300 * time.Millisecond) // 타임아웃 초과
    wg.Wait()
    fmt.Printf("Context 상태: %v\n\n", ctx.Err())

    // 2. 등록 취소 (stop 함수 사용)
    fmt.Println("=== 등록 취소 예시 ===")
    ctx2, cancel2 := context.WithTimeout(context.Background(), 500*time.Millisecond)
    defer cancel2()

    stopFn := context.AfterFunc(ctx2, func() {
        fmt.Println("이 메시지는 출력되지 않아야 합니다")
    })

    // 마음이 바뀌어 등록 취소
    stopped := stopFn()
    fmt.Printf("AfterFunc 등록 취소 성공: %v\n", stopped)

    time.Sleep(600 * time.Millisecond) // 타임아웃이 지나도 콜백 실행 안 됨
    fmt.Println("콜백이 실행되지 않았습니다 ✓")

    // 3. 여러 AfterFunc 독립 실행
    fmt.Println("\n=== 다중 AfterFunc 예시 ===")
    ctx3, cancel3 := context.WithCancel(context.Background())

    var mu sync.Mutex
    var cleanupLog []string

    for i := 1; i <= 3; i++ {
        i := i // 루프 변수 캡처
        context.AfterFunc(ctx3, func() {
            mu.Lock()
            cleanupLog = append(cleanupLog, fmt.Sprintf("정리 작업 %d 완료", i))
            mu.Unlock()
        })
    }

    cancel3() // 모든 AfterFunc 실행
    time.Sleep(50 * time.Millisecond) // goroutine 완료 대기

    mu.Lock()
    for _, log := range cleanupLog {
        fmt.Println(log)
    }
    mu.Unlock()
}
```

실행 결과는 다음과 같습니다.

```
=== context.AfterFunc 예시 ===

작업 시작...
AfterFunc: Context 취소됨 → 리소스 정리 실행
Context 상태: context deadline exceeded

=== 등록 취소 예시 ===
AfterFunc 등록 취소 성공: true
콜백이 실행되지 않았습니다 ✓

=== 다중 AfterFunc 예시 ===
정리 작업 2 완료
정리 작업 1 완료
정리 작업 3 완료
```

## 4.11 WithValue — 요청 범위 값 관리

`context.WithValue()`는 Context에 키-값 쌍을 저장하여 함수 호출 체인 전반에 걸쳐 요청 범위의 메타데이터를 전달합니다. 대표적인 사용 사례는 요청 ID, 사용자 인증 토큰, 분산 추적 ID 등입니다.

**키 타입에 대한 중요한 규칙:** 문자열이나 내장 타입을 키로 사용하면 다른 패키지와 충돌할 위험이 있습니다. 항상 패키지 전용 커스텀 타입을 정의하여 사용해야 합니다.

```go
package main

import (
    "context"
    "fmt"
    "log"
)

// ★ 패키지 전용 키 타입 정의 (외부 충돌 방지)
type contextKey string

const (
    keyRequestID  contextKey = "requestID"
    keyUserID     contextKey = "userID"
    keyUserRole   contextKey = "userRole"
    keyTraceID    contextKey = "traceID"
)

// RequestMetadata는 요청 메타데이터를 담는 구조체입니다.
type RequestMetadata struct {
    RequestID string
    UserID    int
    UserRole  string
    TraceID   string
}

// enrichContext는 요청 메타데이터를 Context에 주입합니다.
func enrichContext(ctx context.Context, meta RequestMetadata) context.Context {
    ctx = context.WithValue(ctx, keyRequestID, meta.RequestID)
    ctx = context.WithValue(ctx, keyUserID, meta.UserID)
    ctx = context.WithValue(ctx, keyUserRole, meta.UserRole)
    ctx = context.WithValue(ctx, keyTraceID, meta.TraceID)
    return ctx
}

// getRequestID는 Context에서 요청 ID를 추출합니다.
func getRequestID(ctx context.Context) string {
    val, ok := ctx.Value(keyRequestID).(string)
    if !ok {
        return "unknown"
    }
    return val
}

// getUserID는 Context에서 사용자 ID를 추출합니다.
func getUserID(ctx context.Context) int {
    val, ok := ctx.Value(keyUserID).(int)
    if !ok {
        return 0
    }
    return val
}

// ContextLogger는 Context 정보를 포함하여 로그를 출력합니다.
func ContextLogger(ctx context.Context, msg string) {
    reqID := getRequestID(ctx)
    userID := getUserID(ctx)
    traceID, _ := ctx.Value(keyTraceID).(string)
    log.Printf("[reqID=%s] [userID=%d] [trace=%s] %s", reqID, userID, traceID, msg)
}

// serviceLayer는 비즈니스 로직 레이어를 시뮬레이션합니다.
func serviceLayer(ctx context.Context) {
    ContextLogger(ctx, "서비스 레이어: 비즈니스 로직 실행")
    repositoryLayer(ctx)
}

// repositoryLayer는 데이터 접근 레이어를 시뮬레이션합니다.
func repositoryLayer(ctx context.Context) {
    ContextLogger(ctx, "리포지토리 레이어: DB 쿼리 실행")
    // DB 쿼리 시 Context 전달 (실제로는 db.QueryContext(ctx, ...))
}

func main() {
    // HTTP 핸들러를 흉내낸 예시
    baseCtx := context.Background()

    // 요청 메타데이터 주입 (실제로는 HTTP 미들웨어에서 수행)
    meta := RequestMetadata{
        RequestID: "req-a1b2c3d4",
        UserID:    42,
        UserRole:  "admin",
        TraceID:   "trace-xyz-789",
    }
    ctx := enrichContext(baseCtx, meta)

    ContextLogger(ctx, "핸들러: 요청 처리 시작")
    serviceLayer(ctx)
    ContextLogger(ctx, "핸들러: 요청 처리 완료")

    // WithValue로 값을 꺼낼 때 타입 단언 주의
    fmt.Println("\n=== 값 추출 예시 ===")
    fmt.Printf("요청 ID: %s\n", getRequestID(ctx))
    fmt.Printf("사용자 ID: %d\n", getUserID(ctx))

    // 없는 키 접근 시 nil 반환 (패닉 없음)
    missing := ctx.Value(contextKey("nonexistent"))
    fmt.Printf("존재하지 않는 키: %v\n", missing)
}
```

실행 결과는 다음과 같습니다.

```
2009/11/10 23:00:00 [reqID=req-a1b2c3d4] [userID=42] [trace=trace-xyz-789] 핸들러: 요청 처리 시작
2009/11/10 23:00:00 [reqID=req-a1b2c3d4] [userID=42] [trace=trace-xyz-789] 서비스 레이어: 비즈니스 로직 실행
2009/11/10 23:00:00 [reqID=req-a1b2c3d4] [userID=42] [trace=trace-xyz-789] 리포지토리 레이어: DB 쿼리 실행
2009/11/10 23:00:00 [reqID=req-a1b2c3d4] [userID=42] [trace=trace-xyz-789] 핸들러: 요청 처리 완료

=== 값 추출 예시 ===

사용자 ID: 42
```

## 4.12 WithoutCancel — 취소로부터 격리 (Go 1.21+)

때로는 부모 Context가 취소되더라도 특정 작업은 반드시 완료되어야 할 때가 있습니다. 예를 들어 HTTP 요청이 취소되었더라도 감사 로그(audit log)는 반드시 DB에 기록되어야 하는 경우입니다. `context.WithoutCancel()`은 부모의 취소 신호로부터 격리된 Context를 생성합니다. 단, 부모의 값(Value)은 그대로 상속됩니다.

```go
package main

import (
    "context"
    "fmt"
    "time"
)

type contextKey string

func main() {
    // 5초 타임아웃을 가진 요청 Context (요청 ID 포함)
    reqCtx, cancel := context.WithTimeout(
        context.WithValue(context.Background(), contextKey("reqID"), "req-001"),
        5*time.Second,
    )

    // 요청을 즉시 취소 (클라이언트 연결 끊김 시뮬레이션)
    cancel()

    fmt.Printf("reqCtx 취소됨: %v\n", reqCtx.Err())

    // ★ WithoutCancel: 부모 취소에 영향받지 않는 격리된 Context 생성
    auditCtx := context.WithoutCancel(reqCtx)

    fmt.Printf("auditCtx 취소 여부: %v\n", auditCtx.Err())            // nil
    fmt.Printf("auditCtx 값 상속: %v\n", auditCtx.Value(contextKey("reqID"))) // req-001

    // 감사 로그는 부모 취소와 무관하게 실행
    writeAuditLog(auditCtx, "사용자 req-001의 데이터 조회 시도")
}

func writeAuditLog(ctx context.Context, message string) {
    reqID := ctx.Value(contextKey("reqID"))
    // 실제로는 DB나 로그 서비스에 기록
    fmt.Printf("[감사 로그] reqID=%v | %s\n", reqID, message)
    fmt.Println("감사 로그 기록 완료 ✓")
}
```

실행 결과는 다음과 같습니다.

```
reqCtx 취소됨: context canceled
auditCtx 취소 여부: <nil>
auditCtx 값 상속: req-001
[감사 로그] reqID=req-001 | 사용자 req-001의 데이터 조회 시도
감사 로그 기록 완료 ✓
```

## 4.13 Context 전파 패턴 — 실전 레이어드 아키텍처

실제 Go 서버 애플리케이션에서 Context가 어떻게 계층을 타고 흐르는지 다이어그램으로 살펴봅니다.

```
HTTP Request 수신
      │
      ▼
┌──────────────────────────────────────────────┐
│  Middleware Layer                            │
│  ctx = r.Context()           (클라이언트 끊김 시 자동 취소)  │
│  ctx = context.WithValue(ctx, "reqID", id)               │
│  ctx, cancel = context.WithTimeout(ctx, 10s)             │
│  defer cancel()                                          │
└──────────────────┬───────────────────────────┘
                   │ ctx 전달
                   ▼
┌──────────────────────────────────────────────┐
│  Handler Layer                               │
│  func handleUser(ctx context.Context, ...)   │
│  → ctx 그대로 전달                            │
└──────────────────┬───────────────────────────┘
                   │ ctx 전달
                   ▼
┌──────────────────────────────────────────────┐
│  Service Layer                               │
│  func (s *UserService) GetUser(ctx, id)      │
│  ctx, cancel = context.WithTimeout(ctx, 3s)  │  ← 더 엄격한 서브 타임아웃
│  defer cancel()                              │
└──────────────────┬───────────────────────────┘
                   │ ctx 전달
                   ▼
┌──────────────────────────────────────────────┐

│  func (r *UserRepo) Find(ctx, id)            │
│  db.QueryRowContext(ctx, query, id)          │  ← DB 드라이버가 ctx 존중
└──────────────────────────────────────────────┘

[어느 단계에서도 ctx.Done() 발생 시 모든 하위 작업 취소]
```

## 4.14 Context 사용의 안티패턴과 모범 사례

**안티패턴 1: 구조체에 Context 저장**

Context는 값이 아닌 요청의 흐름과 함께 살아야 합니다. 구조체 필드에 저장하면 Context의 생명주기 관리가 불투명해집니다.

```go
// ❌ 잘못된 사용: 구조체에 Context 저장
type UserService struct {
    ctx context.Context // 절대 이렇게 하지 마세요
    db  *sql.DB
}

// ✅ 올바른 사용: 함수의 첫 번째 파라미터로 전달
type UserService struct {
    db *sql.DB
}

func (s *UserService) GetUser(ctx context.Context, id int) (*User, error) {
    return nil, nil
}
```

**안티패턴 2: nil Context 전달**

nil Context는 런타임 패닉의 원인이 됩니다. 불확실한 경우에는 `context.TODO()`를 사용합니다.

```go
// ❌ 잘못된 사용
doWork(nil)

// ✅ 올바른 사용
doWork(context.TODO())
```

**안티패턴 3: cancel() 호출 누락**

`cancel()` 미호출은 Context 누수(context leak)로 이어지며, 장기 실행 서비스에서는 메모리 누수로 이어집니다.

```go
// ❌ 잘못된 사용: cancel 호출 없음
func fetchData() {
    ctx, _ := context.WithTimeout(context.Background(), 5*time.Second)
    doFetch(ctx) // cancel이 호출되지 않으면 타임아웃 전까지 리소스 유지
}

// ✅ 올바른 사용: defer cancel()
func fetchData() {
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel() // 함수 종료 시 반드시 호출
    doFetch(ctx)
}
```

**안티패턴 4: WithValue로 선택적 파라미터 전달**

Context의 Value는 요청을 횡단하는 메타데이터에만 사용해야 합니다. 함수의 선택적 인자를 WithValue로 전달하는 것은 API 설계를 불투명하게 만듭니다.

```go
// ❌ 잘못된 사용: 비즈니스 파라미터를 Context에 저장
ctx = context.WithValue(ctx, "pageSize", 20)
ctx = context.WithValue(ctx, "sortBy", "name")

// ✅ 올바른 사용: 명시적 파라미터 또는 구조체 사용
type ListOptions struct {
    PageSize int
    SortBy   string
}
func ListUsers(ctx context.Context, opts ListOptions) ([]*User, error) {
    // ...
    return nil, nil
}
```

모범 사례들을 정리하면 다음과 같습니다.

```
┌──────────────────────────────────────────────────────────┐
│              Context 모범 사례 요약                        │
├──────────────────────────────────────────────────────────┤
│ ✅ ctx는 항상 함수의 첫 번째 파라미터로 전달               │
│ ✅ 생성 직후 defer cancel() 호출                          │
│ ✅ ctx.Done()을 루프 내에서 주기적으로 확인               │
│ ✅ 에러 처리 시 errors.Is(err, context.Canceled) 사용    │
│ ✅ WithValue 키는 패키지 전용 커스텀 타입 사용            │
│ ✅ 불확실할 때는 context.TODO() 사용                      │
│ ❌ 구조체 필드에 ctx 저장 금지                            │
│ ❌ nil Context 전달 금지                                  │
│ ❌ cancel() 미호출 금지                                   │
│ ❌ 비즈니스 로직 파라미터를 WithValue로 전달 금지          │
└──────────────────────────────────────────────────────────┘
```

## 4.15 HTTP 서버에서의 Context 활용

실제 HTTP 서버에서는 `net/http` 패키지가 각 요청에 대한 Context를 자동으로 생성합니다. 클라이언트가 연결을 끊으면 이 Context가 자동으로 취소됩니다.

```go
package main

import (
    "context"
    "encoding/json"
    "fmt"
    "log"
    "net/http"
    "time"
)

type contextKey string

const keyRequestID contextKey = "requestID"

// requestIDMiddleware는 각 요청에 고유 ID를 부여합니다.
func requestIDMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        reqID := r.Header.Get("X-Request-ID")
        if reqID == "" {
            reqID = fmt.Sprintf("req-%d", time.Now().UnixNano())
        }
        ctx := context.WithValue(r.Context(), keyRequestID, reqID)
        w.Header().Set("X-Request-ID", reqID)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

// timeoutMiddleware는 요청에 전체 타임아웃을 설정합니다.
func timeoutMiddleware(timeout time.Duration) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            ctx, cancel := context.WithTimeout(r.Context(), timeout)
            defer cancel()
            next.ServeHTTP(w, r.WithContext(ctx))
        })
    }
}

// simulateSlowDB는 느린 DB 쿼리를 시뮬레이션합니다.
func simulateSlowDB(ctx context.Context, userID int) (map[string]interface{}, error) {
    resultCh := make(chan map[string]interface{}, 1)

    go func() {
        time.Sleep(500 * time.Millisecond) // DB 처리 시간
        resultCh <- map[string]interface{}{
            "id":    userID,
            "name":  "Alice",
            "email": "alice@example.com",
        }
    }()

    select {
    case result := <-resultCh:
        return result, nil
    case <-ctx.Done():
        return nil, ctx.Err()
    }
}

// userHandler는 사용자 정보를 반환하는 핸들러입니다.
func userHandler(w http.ResponseWriter, r *http.Request) {
    ctx := r.Context()
    reqID, _ := ctx.Value(keyRequestID).(string)

    log.Printf("[%s] 사용자 조회 요청", reqID)

    // DB 쿼리 실행 (ctx 전달)
    user, err := simulateSlowDB(ctx, 42)
    if err != nil {
        log.Printf("[%s] DB 쿼리 실패: %v", reqID, err)

        switch {
        case err == context.DeadlineExceeded:
            http.Error(w, "요청 타임아웃", http.StatusGatewayTimeout)
        case err == context.Canceled:
            // 클라이언트가 연결을 끊음 - 응답 불필요
            log.Printf("[%s] 클라이언트 연결 끊김", reqID)
        default:
            http.Error(w, "서버 오류", http.StatusInternalServerError)
        }
        return
    }

    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(user)
    log.Printf("[%s] 사용자 조회 성공", reqID)
}

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("/user", userHandler)

    // 미들웨어 체인 적용
    handler := requestIDMiddleware(
        timeoutMiddleware(2 * time.Second)(mux),
    )

    log.Println("서버 시작: :8080")
    log.Fatal(http.ListenAndServe(":8080", handler))
}
```

## 4.16 Chapter 04 종합 응용 프로그램

이번 챕터에서 학습한 Context의 모든 핵심 개념(취소 전파, 타임아웃, WithCancelCause, AfterFunc, WithValue)을 종합하여 **병렬 작업 오케스트레이터(Parallel Task Orchestrator)**를 구현합니다. 이 프로그램은 여러 비동기 작업을 동시에 실행하고, 취소 전파와 타임아웃을 통해 전체 작업을 조율합니다.

```go
package main

import (
    "context"
    "errors"
    "fmt"
    "log"
    "math/rand"
    "sync"
    "time"
)

// ──────────────────────────────────────
// 타입 정의
// ──────────────────────────────────────

type contextKey string

const (
    keyJobID     contextKey = "jobID"
    keyRequestID contextKey = "requestID"
)

// TaskStatus는 작업 상태를 나타냅니다.
type TaskStatus string

const (
    StatusPending   TaskStatus = "PENDING"
    StatusRunning   TaskStatus = "RUNNING"
    StatusDone      TaskStatus = "DONE"
    StatusCanceled  TaskStatus = "CANCELED"
    StatusFailed    TaskStatus = "FAILED"
)

// TaskResult는 개별 작업의 결과를 담습니다.
type TaskResult struct {
    Name     string
    Status   TaskStatus
    Value    interface{}
    Err      error
    Duration time.Duration
}

// Task는 실행할 작업의 명세를 나타냅니다.
type Task struct {
    Name     string
    Duration time.Duration // 작업 처리 시간 시뮬레이션
    FailRate float32       // 실패 확률 (0.0~1.0)
}

// ──────────────────────────────────────
// 도메인 에러 정의
// ──────────────────────────────────────

var (
    ErrTaskFailed   = errors.New("태스크 처리 중 오류 발생")
    ErrOrchestratorTimeout = errors.New("오케스트레이터 전체 타임아웃")
)

// ──────────────────────────────────────
// Orchestrator
// ──────────────────────────────────────

// Orchestrator는 병렬 작업을 조율하는 구조체입니다.
type Orchestrator struct {
    jobID      string
    totalTimeout time.Duration
    taskTimeout  time.Duration
}

// NewOrchestrator는 새로운 Orchestrator를 생성합니다.
func NewOrchestrator(jobID string, total, perTask time.Duration) *Orchestrator {
    return &Orchestrator{
        jobID:        jobID,
        totalTimeout: total,
        taskTimeout:  perTask,
    }
}

// runTask는 단일 작업을 Context를 존중하며 실행합니다.
func (o *Orchestrator) runTask(ctx context.Context, task Task) TaskResult {
    start := time.Now()

    // 개별 작업에 대한 타임아웃 Context 생성
    taskCtx, taskCancel := context.WithTimeout(ctx, o.taskTimeout)
    defer taskCancel()

    jobID, _ := ctx.Value(keyJobID).(string)
    log.Printf("[Job:%s] [Task:%s] 시작 (예상 소요: %v)", jobID, task.Name, task.Duration)

    resultCh := make(chan interface{}, 1)
    errCh := make(chan error, 1)

    go func() {
        // 작업 처리 시뮬레이션
        time.Sleep(task.Duration)

        // 실패 확률 적용
        if rand.Float32() < task.FailRate {
            errCh <- fmt.Errorf("%w: %s에서 랜덤 오류 발생", ErrTaskFailed, task.Name)
            return
        }
        resultCh <- fmt.Sprintf("%s 처리 결과 데이터", task.Name)
    }()

    select {
    case val := <-resultCh:
        duration := time.Since(start)
        log.Printf("[Job:%s] [Task:%s] 완료 (%v)", jobID, task.Name, duration.Round(time.Millisecond))
        return TaskResult{
            Name:     task.Name,
            Status:   StatusDone,
            Value:    val,
            Duration: duration,
        }

    case err := <-errCh:
        duration := time.Since(start)
        log.Printf("[Job:%s] [Task:%s] 실패: %v", jobID, task.Name, err)
        return TaskResult{
            Name:     task.Name,
            Status:   StatusFailed,
            Err:      err,
            Duration: duration,
        }

    case <-taskCtx.Done():
        duration := time.Since(start)
        cause := context.Cause(taskCtx)
        log.Printf("[Job:%s] [Task:%s] 취소됨 - 원인: %v", jobID, task.Name, cause)
        return TaskResult{
            Name:     task.Name,
            Status:   StatusCanceled,
            Err:      cause,
            Duration: duration,
        }
    }
}

// Run은 모든 작업을 병렬로 실행하고 결과를 수집합니다.
func (o *Orchestrator) Run(ctx context.Context, tasks []Task) []TaskResult {
    // 전체 작업에 대한 타임아웃 + 원인 추적 Context 생성
    jobCtx, jobCancel := context.WithCancelCause(ctx)

    // 전체 타임아웃 적용
    timeoutCtx, timeoutCancel := context.WithTimeoutCause(
        jobCtx,
        o.totalTimeout,
        ErrOrchestratorTimeout,
    )
    defer timeoutCancel()
    defer jobCancel(nil)

    // Context에 Job ID 주입
    jobCtx2 := context.WithValue(timeoutCtx, keyJobID, o.jobID)

    // AfterFunc: 전체 작업 취소 시 정리 로그 기록
    context.AfterFunc(jobCtx2, func() {
        cause := context.Cause(jobCtx2)
        log.Printf("[Job:%s] ◆ 전체 작업 종료 이벤트 - 원인: %v", o.jobID, cause)
    })

    log.Printf("[Job:%s] ▶ 오케스트레이터 시작 (총 타임아웃: %v, 태스크 타임아웃: %v)",
        o.jobID, o.totalTimeout, o.taskTimeout)
    log.Printf("[Job:%s] ▶ 실행할 작업 수: %d개", o.jobID, len(tasks))

    // 결과 수집 채널
    resultCh := make(chan TaskResult, len(tasks))

    var wg sync.WaitGroup

    // 모든 작업을 병렬로 실행
    for _, task := range tasks {
        wg.Add(1)
        task := task // 루프 변수 캡처

        go func() {
            defer wg.Done()
            result := o.runTask(jobCtx2, task)
            resultCh <- result
        }()
    }

    // 모든 goroutine이 완료되면 채널 닫기
    go func() {
        wg.Wait()
        close(resultCh)
    }()

    // 결과 수집
    var results []TaskResult
    for result := range resultCh {
        results = append(results, result)
    }

    return results
}

// ──────────────────────────────────────
// 결과 보고서 출력
// ──────────────────────────────────────

func printReport(jobID string, results []TaskResult, totalDuration time.Duration) {
    fmt.Printf("\n")
    fmt.Println("╔══════════════════════════════════════════════════════════╗")
    fmt.Printf( "║          작업 실행 보고서 [Job: %-26s]  ║\n", jobID)
    fmt.Println("╠══════════════════════════════════════════════════════════╣")
    fmt.Printf( "║  전체 소요 시간: %-40v║\n", totalDuration.Round(time.Millisecond))
    fmt.Println("╠══════════════════╦════════════╦══════════════════════════╣")
    fmt.Println("║  작업명          ║  상태      ║  결과/오류               ║")
    fmt.Println("╠══════════════════╬════════════╬══════════════════════════╣")

    var doneCount, failCount, cancelCount int

    for _, r := range results {
        statusIcon := map[TaskStatus]string{
            StatusDone:     "✅ DONE    ",
            StatusFailed:   "❌ FAILED  ",
            StatusCanceled: "⚠️  CANCELED",
        }[r.Status]

        detail := ""
        if r.Err != nil {
            detail = r.Err.Error()
            if len(detail) > 24 {
                detail = detail[:21] + "..."
            }
        } else if r.Value != nil {
            detail = fmt.Sprintf("%v", r.Value)
            if len(detail) > 24 {
                detail = detail[:21] + "..."
            }
        }

        fmt.Printf("║  %-16s║  %s  ║  %-24s║\n",
            r.Name, statusIcon, detail)

        switch r.Status {
        case StatusDone:
            doneCount++
        case StatusFailed:
            failCount++
        case StatusCanceled:
            cancelCount++
        }
    }

    fmt.Println("╠══════════════════╩════════════╩══════════════════════════╣")
    fmt.Printf( "║  ✅ 완료: %-3d  ❌ 실패: %-3d  ⚠️  취소: %-3d              ║\n",
        doneCount, failCount, cancelCount)
    fmt.Println("╚══════════════════════════════════════════════════════════╝")
}
```

## Chapter 04 정리

이번 챕터에서는 Go Context 패키지의 핵심 메커니즘을 심도 있게 살펴보았습니다. Context는 단순한 취소 도구를 넘어 Go의 동시성 프로그래밍 전반에 걸쳐 신뢰성과 예측 가능성을 부여하는 핵심 추상화입니다.

배운 내용을 정리하면 다음과 같습니다. `context.WithCancel()`은 외부 신호에 의한 수동 취소를 가능하게 하며, `context.WithTimeout()`과 `context.WithDeadline()`은 시간 기반 자동 취소를 제공합니다. Context 트리에서 부모의 취소는 모든 자식에게 전파되며, 더 엄격한 타임아웃이 항상 우선됩니다. Go 1.20의 `WithCancelCause()`는 취소 원인을 추적할 수 있게 해주며, Go 1.21의 `AfterFunc()`는 취소 시 콜백을 비침투적으로 등록할 수 있게 합니다. `WithValue()`는 요청 범위의 메타데이터를 전달하되, 반드시 패키지 전용 키 타입을 사용해야 하며 비즈니스 로직 파라미터 전달에는 사용하지 않아야 합니다.

다음 Chapter 05에서는 이 Context를 `net/http` 표준 라이브러리와 함께 활용하여 실전적인 웹 서버를 구축하는 방법을 배웁니다.
