CHAPTER 04

RIO 버퍼 관리

3장에서는 세션마다 버퍼를 new로 새로 만들었습니다. 연결이 수백 개만 되어도 등록·해제가 그만큼 반복된다는 뜻입니다. 이번 장에서는 큰 메모리 풀 하나를 미리 등록해두고, 그 안을 작은 조각으로 쪼개 재사용하는 버퍼 링(ring)과 오브젝트 풀을 만듭니다. 그리고 3장에서 "완전한 제로 카피는 아니다"라고 짚었던 애플리케이션 측 복사를 줄이는 방법과, 그 한계를 함께 다룹니다.

이 장에서 배우는 것

  • 큰 메모리 풀을 한 번만 등록하고 재사용하는 RIOBufferManager
  • 등록된 풀을 작은 청크로 나눠 순환 재사용하는 버퍼 링(RIOBufferRing)
  • RIO 버퍼의 실제 등록 조건과, 정렬을 별도 요구사항으로 다뤄야 하는 경우
  • placement new를 이용한 범용 오브젝트 풀(ObjectPool)
  • 연결 수를 기준으로 필요한 메모리를 미리 계산해 할당하는 전략
  • 메모리 맵 파일을 등록 버퍼로 활용할 때의 이점과 수명·성능상 주의점

4.1 버퍼 등록 및 관리

등록·해제를 매번 반복하지 않도록, 큰 풀 하나를 서버 시작 시 한 번만 등록합니다.

버퍼 등록 방법

RIOBufferManager는 지정한 크기의 메모리 풀을 한 번만 RIORegisterBuffer()로 등록하고, 소멸 시점에 RIODeregisterBuffer()로 해제하는 RAII 래퍼입니다 — 3장에서 남겨두었던 "등록만 하고 해제하지 않는" 문제를 이번에는 처음부터 바로잡습니다. 

#include <winsock2.h>   // windows.h보다 먼저 포함해야 Winsock.h와 충돌하지 않습니다.
#include <windows.h>
#include <mswsock.h>
#include <algorithm>
#include <array>
#include <atomic>
#include <cstddef>
#include <cstring>
#include <iostream>
#include <limits>
#include <vector>
#include <memory>
#include <thread>
#include <mutex>
#include <new>
#include <optional>
#include <span>
#include <stdexcept>
#include <string>
#include <utility>

#pragma comment(lib, "ws2_32.lib")
#pragma comment(lib, "mswsock.lib")

class RIOBufferManager {
private:
    RIO_EXTENSION_FUNCTION_TABLE& rio_fn_table_;   // 함수 테이블의 수명은 이 객체보다 길어야 합니다.
    std::vector<char> buffer_pool_;                 // 실제 버퍼 메모리 풀
    RIO_BUFFERID buffer_id_ = RIO_INVALID_BUFFERID;
    size_t buffer_size_;
    size_t chunk_size_;
    std::mutex mutex_;

public:
    RIOBufferManager(RIO_EXTENSION_FUNCTION_TABLE& rio_fn_table, size_t total_size, size_t chunk_size)
        : rio_fn_table_(rio_fn_table), buffer_size_(total_size), chunk_size_(chunk_size) {
        // RIORegisterBuffer와 RIO_BUF의 길이·오프셋은 DWORD/ULONG입니다.
        if (total_size == 0 || total_size > (std::numeric_limits<DWORD>::max)() ||
            chunk_size == 0 || chunk_size > total_size) {
            throw std::invalid_argument("유효하지 않은 RIO 버퍼 풀 크기");
        }
        buffer_pool_.resize(total_size);

        buffer_id_ = rio_fn_table_.RIORegisterBuffer(buffer_pool_.data(), static_cast<DWORD>(buffer_pool_.size()));
        if (buffer_id_ == RIO_INVALID_BUFFERID) {
            throw std::runtime_error("RIO 버퍼 등록 실패: " + std::to_string(WSAGetLastError()));
        }

        std::cout << "RIO 버퍼 등록 성공 - 총 크기: " << total_size << ", 청크 크기: " << chunk_size << std::endl;
    }

    ~RIOBufferManager() {
        // 이 시점에는 이 버퍼를 참조하는 모든 RIO 요청이 완료되어 있어야 합니다.
        // RIO 문서는 outstanding 요청이 있는 동안 deregister하지 말 것을 요구합니다.
        if (buffer_id_ != RIO_INVALID_BUFFERID) {
            rio_fn_table_.RIODeregisterBuffer(buffer_id_);
        }
    }

    RIOBufferManager(const RIOBufferManager&) = delete;
    RIOBufferManager& operator=(const RIOBufferManager&) = delete;

    RIO_BUFFERID GetBufferId() const { return buffer_id_; }
    char* GetBuffer() { return buffer_pool_.data(); }         // 버퍼 링이 실제 메모리 위치를 계산할 때 필요
    size_t GetSize() const { return buffer_size_; }
};

3장의 미해결 과제, 여기서 해결됩니다

3장에서 RioBuffer는 소멸자 주석에 "등록 해제는 서버가 담당"이라고만 적어놓고 실제로는 아무도 RIODeregisterBuffer()를 호출하지 않았습니다. RIOBufferManager는 함수 테이블 참조를 직접 멤버로 들고 있어, 자기 소멸자 안에서 스스로 등록을 해제할 수 있습니다. 단, 서버 종료 시에는 요청 큐를 먼저 중지하고 완료를 모두 회수한 다음 이 객체를 파괴해야 합니다. 진행 중인 요청이 있는 버퍼를 해제하면 안 됩니다.

버퍼 크기와 정렬

RIO의 필수 조건은 유효한 주소와 0보다 큰 DWORD 범위의 길이입니다. 등록하면 해당 가상 메모리 페이지가 물리 메모리에 고정되므로, 성능과 메모리 사용량에는 개별 청크 정렬보다 작은 버퍼를 여러 번 등록하지 않고 큰 연속 풀 하나를 등록하는 것이 더 직접적으로 중요합니다.

정렬을 RIO의 전제 조건으로 오해하지 마세요

64바이트나 4KB 정렬은 특정 SIMD 처리, 캐시 설계, 또는 FILE_FLAG_NO_BUFFERING 파일 I/O에서 별도로 필요할 수 있습니다. 하지만 RIO 자체가 그런 정렬을 요구하거나 DMA 성능을 보장한다고 말할 근거는 없습니다. 실제 프로파일링이나 다른 API의 요구사항이 있을 때만, 그 요구사항에 맞는 정렬 할당자를 적용합니다.

4.2 RIO 버퍼 링 구현

등록된 큰 풀을 고정 크기 청크로 나눠, "빈 칸을 찾아 쓰고 반납하는" 순환 방식으로 재사용합니다.

버퍼 링(ring buffer)은 이름 그대로 청크들을 원형으로 배치했다고 "생각하는" 자료구조입니다. next_index_가 마지막 칸을 지나면 다시 0번으로 돌아오는 것을 나머지 연산자 (%)로 구현하며, 이렇게 하면 매번 new/delete를 호출하지 않고도 청크를 계속 빌리고 반납할 수 있습니다.

그림 4-1. next_index_가 빈 칸을 찾아 이동하다가 마지막 칸(7) 다음에는 다시 0번으로 순환합니다

순환 버퍼 구현

BufferSegment는 "등록된 풀 중 어느 구간을 빌렸는지"를 나타내는 작은 값 타입입니다. 2장의 RIO_BUF와 거의 같은 정보(버퍼 ID, 오프셋, 길이)를 담지만, 실제 메모리 포인터(data)까지 함께 들고 있어 애플리케이션 코드에서 바로 memcpy 대상으로 쓸 수 있습니다. 

class RIOBufferRing {
private:
    RIOBufferManager& buffer_manager_;
    size_t base_offset_;
    size_t chunk_size_;
    size_t buffer_count_;
    std::vector<bool> in_use_;
    std::mutex mutex_;
    size_t next_index_ = 0;

public:
    struct BufferSegment {
        RIO_BUFFERID buffer_id;
        char* data;
        size_t offset;
        size_t size;
    };

    RIOBufferRing(RIOBufferManager& buffer_manager, size_t chunk_size, size_t buffer_count)
        : buffer_manager_(buffer_manager), base_offset_(0),
          chunk_size_(chunk_size), buffer_count_(buffer_count) {
        if (chunk_size == 0 || buffer_count == 0 ||
            buffer_count > buffer_manager_.GetSize() / chunk_size) {
            throw std::invalid_argument("RIO 버퍼 링의 범위가 등록된 풀을 벗어납니다");
        }
        in_use_.resize(buffer_count, false);
    }

    // 서버 초기화 중, Allocate()가 호출되기 전에 링에 전용 범위를 배정합니다.
    void SetBaseOffset(size_t base_offset) {
        std::lock_guard<std::mutex> lock(mutex_);
        if (base_offset > buffer_manager_.GetSize() ||
            buffer_count_ > (buffer_manager_.GetSize() - base_offset) / chunk_size_) {
            throw std::invalid_argument("RIO 버퍼 링의 범위가 등록된 풀을 벗어납니다");
        }
        if (std::any_of(in_use_.begin(), in_use_.end(), [](bool used) { return used; })) {
            throw std::logic_error("사용 중인 RIO 버퍼 링의 시작 위치는 바꿀 수 없습니다");
        }
        base_offset_ = base_offset;
        next_index_ = 0;
    }

    // 사용 가능한 청크 하나를 빌림 — 모두 사용 중이면 std::nullopt
    std::optional<BufferSegment> Allocate() {
        std::lock_guard<std::mutex> lock(mutex_);

        size_t count = 0;
        while (in_use_[next_index_] && count < buffer_count_) {
            next_index_ = (next_index_ + 1) % buffer_count_;   // 순환: 마지막 칸 다음은 다시 0
            count++;
        }
        if (count == buffer_count_) {
            return std::nullopt;   // 모든 청크가 사용 중
        }

        in_use_[next_index_] = true;
        BufferSegment segment;
        segment.buffer_id = buffer_manager_.GetBufferId();
        segment.offset = base_offset_ + next_index_ * chunk_size_;
        segment.size = chunk_size_;
        segment.data = buffer_manager_.GetBuffer() + segment.offset;

        next_index_ = (next_index_ + 1) % buffer_count_;
        return segment;
    }

    // 완료 통지를 받은 뒤에만 호출합니다. 잘못된 세그먼트·중복 반납은 false로 거절합니다.
    bool Release(const BufferSegment& segment) {
        std::lock_guard<std::mutex> lock(mutex_);
        if (segment.buffer_id != buffer_manager_.GetBufferId() ||
            segment.size != chunk_size_ || segment.offset < base_offset_) return false;
        const size_t relative_offset = segment.offset - base_offset_;
        if (relative_offset % chunk_size_ != 0) return false;
        const size_t index = relative_offset / chunk_size_;
        if (index >= buffer_count_ || !in_use_[index]) return false;
        in_use_[index] = false;
        return true;
    }
};

이 탐색은 O(N)입니다

Allocate()는 빈 칸을 찾을 때까지 한 칸씩 순서대로 검사합니다. 청크 수가 수백 개 정도면 문제없지만, 수만 개로 늘어나고 대부분이 사용 중인 상황이 잦다면 이 선형 탐색이 병목이 될 수 있습니다. 그런 경우 "사용 가능한 인덱스만 모아둔 별도의 큐"를 유지하는 방식으로 O(1) 탐색이 가능하도록 개선할 수 있습니다.

멀티스레드 환경에서의 동기화

3장의 워커 스레드 여러 개가 동시에 버퍼를 요청할 수 있으므로, in_use_ 배열 접근은 std::mutex로 보호했습니다. Release(segment)는 다른 링의 오프셋, 중복 반납, 청크 중간 주소를 거절합니다. 특히 송신 버퍼는 RIO 완료 통지를 받은 뒤에만 반납해야 합니다. RIOSend()가 TRUE를 반환한 것은 요청이 접수됐다는 뜻일 뿐, 네트워크 I/O가 끝났다는 뜻은 아닙니다.

락프리 구현은 별도 설계가 필요합니다

std::atomic<bool> 배열과 compare_exchange_weak 몇 줄만으로는 안전한 락프리 풀을 만들 수 없습니다. 반환 경로, ABA 방지, 메모리 순서, 종료 시점까지 함께 설계해야 합니다. 워커 스레드가 4~8개 수준이라면 std::mutex 기반으로 시작하고, 프로파일링에서 이 락이 병목으로 확인된 경우에만 검증된 동시 큐나 전용 락프리 free-list를 검토하는 편이 낫습니다.

4.3 효율적인 메모리 할당 전략

버퍼뿐 아니라, 버퍼를 감싸는 C++ 객체 자체도 재사용할 수 있습니다.

메모리 풀 구현

RIOBufferRing이 원시 메모리 청크를 재사용했다면, ObjectPool은 C++ 객체(생성자·소멸자가 있는 타입) 자체를 재사용하는 범용 템플릿입니다. 핵심은 placement new입니다 — 이미 확보해둔 메모리 위에 객체를 "새로 생성"하는 문법으로, 메모리 할당과 객체 생성을 분리할 수 있게 해줍니다. 

template <typename T, size_t PoolSize>
class ObjectPool {
private:
    struct PoolItem {
        alignas(T) std::byte storage[sizeof(T)];   // T 하나가 들어갈 만큼의 미가공 메모리
        bool in_use = false;
    };

    std::array<PoolItem, PoolSize> pool_;
    std::mutex mutex_;

public:
    static_assert(PoolSize > 0, "ObjectPool의 크기는 1 이상이어야 합니다");

    ObjectPool(const ObjectPool&) = delete;
    ObjectPool& operator=(const ObjectPool&) = delete;

    ~ObjectPool() {
        // 풀보다 먼저 모든 사용자가 객체를 반납하도록 서버 종료 순서를 보장해야 합니다.
        for (auto& item : pool_) {
            if (item.in_use) {
                std::launder(reinterpret_cast<T*>(item.storage))->~T();
            }
        }
    }

    template <typename... Args>
    T* Allocate(Args&&... args) {
        std::lock_guard<std::mutex> lock(mutex_);

        for (auto& item : pool_) {
            if (!item.in_use) {
                T* object = new (item.storage) T(std::forward<Args>(args)...); // placement new
                item.in_use = true;  // 생성자가 예외를 던지면 슬롯은 여전히 비어 있습니다.
                return object;
            }
        }
        return nullptr;   // 풀이 모두 사용 중
    }

    bool Deallocate(T* ptr) {
        std::lock_guard<std::mutex> lock(mutex_);

        for (auto& item : pool_) {
            if (reinterpret_cast<T*>(item.storage) == ptr) {
                if (!item.in_use) return false;  // 중복 반납
                ptr->~T();          // 소멸자를 직접 호출 (메모리 자체는 해제하지 않음)
                item.in_use = false;
                return true;
            }
        }
        return false;  // 이 풀이 소유하지 않는 포인터
    }
};

placement new란?

일반적인 new T(...)는 "메모리를 새로 할당하면서 동시에 객체를 생성"합니다. new (주소) T(...) 형태의 placement new는 이미 존재하는 메모리 위에 객체만 생성합니다 — malloc/new의 비용(힙 탐색, 시스템 호출 가능성)을 매번 치르지 않고, 미리 확보해둔 슬롯 위에 생성자만 호출하는 셈입니다. 반대로 소멸시킬 때는 delete 대신 소멸자를 ptr->~T()처럼 직접 호출해야 하고, 메모리 자체는 풀이 계속 소유합니다. "메모리 확보"와 "객체 생성"을 분리하는 이 기법은 이후 6장의 RIO 래퍼 클래스에서도 다시 등장합니다.

미리 할당을 통한 성능 향상

서버 시작 시점에 "최대 연결 수 × 연결당 동시 버퍼 상한"을 계산해 필요한 메모리를 한 번에 확보해두면, 운영 중에는 추가 할당이 거의 일어나지 않습니다. 상한은 실제 피크 트래픽과 완료 지연을 반영해 정해야 합니다. 

class RIOServer {
private:
    RIO_EXTENSION_FUNCTION_TABLE& rio_fn_table_;
    std::unique_ptr<RIOBufferManager> buffer_manager_;
    std::unique_ptr<RIOBufferRing> send_buffer_ring_;
    std::unique_ptr<RIOBufferRing> recv_buffer_ring_;

public:
    explicit RIOServer(RIO_EXTENSION_FUNCTION_TABLE& rio_fn_table)
        : rio_fn_table_(rio_fn_table) {}

    void Initialize(size_t max_connections) {
        if (buffer_manager_) {
            throw std::logic_error("RIO 서버는 종료 후에만 다시 초기화할 수 있습니다");
        }
        constexpr size_t send_buffer_per_conn = 4;  // 연결당 동시 송신 상한
        constexpr size_t recv_buffer_per_conn = 2;  // 연결당 동시 수신 상한
        constexpr size_t buffer_size = 4096;
        constexpr size_t buffers_per_conn = send_buffer_per_conn + recv_buffer_per_conn;

        if (max_connections == 0 ||
            max_connections > (std::numeric_limits<DWORD>::max)() / (buffers_per_conn * buffer_size)) {
            throw std::invalid_argument("최대 연결 수에 비해 RIO 버퍼 풀이 너무 큽니다");
        }

        size_t total_send_buffers = max_connections * send_buffer_per_conn;
        size_t total_recv_buffers = max_connections * recv_buffer_per_conn;
        size_t total_memory_size = (total_send_buffers + total_recv_buffers) * buffer_size;

        buffer_manager_ = std::make_unique<RIOBufferManager>(rio_fn_table_, total_memory_size, buffer_size);

        send_buffer_ring_ = std::make_unique<RIOBufferRing>(*buffer_manager_, buffer_size, total_send_buffers);
        recv_buffer_ring_ = std::make_unique<RIOBufferRing>(*buffer_manager_, buffer_size, total_recv_buffers);
        // 두 링이 같은 등록 풀을 쓰되, 서로 겹치지 않는 구간을 사용하게 합니다.
        recv_buffer_ring_->SetBaseOffset(total_send_buffers * buffer_size);

        std::cout << "서버 메모리 초기화 완료 - 최대 연결: " << max_connections
                  << ", 총 메모리: " << total_memory_size / (1024 * 1024) << "MB" << std::endl;
    }
};

눈여겨볼 점은 send_buffer_ring_과 recv_buffer_ring_이 같은 buffer_manager_가 등록한 하나의 큰 풀을 서로 다른 구간으로 나눠 쓴다는 것입니다 — 등록은 한 번만, 재사용은 두 개의 독립된 링으로. "얼마나 미리 할당할지"는 결국 send_buffer_per_conn·recv_buffer_per_conn 값을 얼마나 현실적으로 추정하느냐에 달려 있으며, 이 값은 실제 게임의 트래픽을 측정하며 조정해야 합니다.

4.4 복사 최소화 기법 활용

등록된 버퍼에 직접 데이터를 만들고, 불필요한 애플리케이션 측 복사를 줄입니다.

제로 카피의 개념

전통적인 소켓 I/O에서 데이터가 애플리케이션 버퍼·Winsock 공급자·네트워크 장치를 거치는 방식과 실제 복사 횟수는 운영체제, 공급자, NIC에 따라 달라집니다. "제로 카피"는 그 경로의 복사 또는 애플리케이션이 수행하는 중간 복사를 줄이려는 기법의 총칭이며, API 이름만으로 복사 횟수가 0이라고 보장되지는 않습니다.

등록 버퍼에 직접 작성하기

아래 함수는 버퍼 링에서 빌린 세그먼트에 데이터를 담아 송신 요청을 넣습니다. RIOSend()는 BOOL을 반환하며, FALSE면 요청 자체가 접수되지 않은 것입니다. 요청이 접수된 뒤의 실제 I/O 성공 여부는 완료 큐에서 얻는 RIORESULT::Status로 확인해야 합니다. 

struct SendOperation {
    RIOBufferRing::BufferSegment segment;
    // 이 객체는 완료 큐에서 RequestContext를 회수할 때까지 주소가 바뀌거나 파괴되면 안 됩니다.
};

bool QueueSend(RIO_EXTENSION_FUNCTION_TABLE& rio_fn_table, RIO_RQ request_queue,
               std::span<const std::byte> data, SendOperation& operation) {
    const auto& segment = operation.segment;
    if (data.size() > segment.size) {
        return false;   // 버퍼 크기 부족
    }

    // 애플리케이션 데이터를 등록된 버퍼로 복사 — 이 한 번의 복사는 여전히 필요합니다
    std::memcpy(segment.data, data.data(), data.size());

    RIO_BUF rio_buffer{};
    rio_buffer.BufferId = segment.buffer_id;
    rio_buffer.Offset = static_cast<ULONG>(segment.offset);
    rio_buffer.Length = static_cast<ULONG>(data.size());

    BOOL result = rio_fn_table.RIOSend(request_queue, &rio_buffer, 1, 0, &operation);
    if (!result) {
        std::cerr << "RIOSend 실패: " << WSAGetLastError() << std::endl;
        return false;  // 요청이 큐에 들어가지 않았으므로 호출자가 segment를 즉시 Release할 수 있습니다.
    }
    return true;
}

요청 컨텍스트와 버퍼의 수명을 함께 관리합니다

성공적으로 큐에 넣은 SendOperation은 완료 큐에서 RIORESULT::RequestContext로 다시 받을 때까지 안정된 주소에 보관합니다. 완료 결과가 성공이든 실패든, 그 시점에 operation->segment를 해당 링에 반납하고 operation을 폐기합니다. 반대로 QueueSend()가 false를 반환하면 완료 통지는 오지 않으므로 호출자가 즉시 세그먼트를 반납해야 합니다.

RIO를 절대적 의미의 "제로 카피"라고 부르면 안 됩니다

애플리케이션이 원래 갖고 있던 데이터(예: 직렬화된 패킷)는 등록되지 않은 임의의 메모리에 있으므로, RIO로 보내려면 등록된 버퍼로 한 번은 옮겨야 합니다. RIO가 없애는 것은 매 요청마다 메모리를 등록하는 비용입니다. 실제 네트워크 경로에 복사가 있는지와 NIC가 DMA를 어떻게 사용하는지는 Winsock 공급자와 하드웨어 구현에 달려 있으므로, RIO가 모든 복사를 보장 없이 제거한다고 단정할 수는 없습니다. 애초에 데이터를 등록 버퍼 위에 직접 직렬화하면 이 함수의 memcpy는 없앨 수 있습니다.

메모리 맵 파일을 송신 버퍼로 활용하기

게임 에셋(패치 파일, 다운로드 가능한 리소스)처럼 읽기 전용이고 변하지 않는 큰 데이터는 애초에 애플리케이션 버퍼로 복사할 필요 없이, 운영체제의 메모리 맵 파일 기능으로 파일을 프로세스 주소 공간에 매핑한 뒤 그 영역을 송신용 RIO 버퍼로 등록해볼 수 있습니다. 이 방법은 애플리케이션 코드의 별도 읽기·복사를 줄이지만, 페이지 폴트·파일 시스템 캐시·네트워크 공급자 내부 동작까지 없애는 것은 아닙니다. 지원 환경에서 반드시 부하 테스트로 확인해야 합니다.

API역할
CreateFileW()파일을 열어 핸들을 얻습니다.
CreateFileMappingW()그 파일에 대한 "매핑 객체"를 만듭니다 — 아직 메모리에 올라오지는 않습니다.
MapViewOfFile()매핑 객체의 일부(또는 전체)를 실제 프로세스 주소 공간에 배치해, 포인터로 접근 가능하게 합니다.
 
class MappedFileBuffer {
private:
    HANDLE file_handle_ = INVALID_HANDLE_VALUE;
    HANDLE mapping_handle_ = NULL;
    void* mapped_view_ = nullptr;
    size_t file_size_ = 0;
    RIO_BUFFERID buffer_id_ = RIO_INVALID_BUFFERID;
    RIO_EXTENSION_FUNCTION_TABLE& rio_fn_table_;

public:
    MappedFileBuffer(RIO_EXTENSION_FUNCTION_TABLE& rio_fn_table, const std::wstring& file_path)
        : rio_fn_table_(rio_fn_table) {
        file_handle_ = CreateFileW(file_path.c_str(), GENERIC_READ, FILE_SHARE_READ,
                                    NULL, OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, NULL);
        if (file_handle_ == INVALID_HANDLE_VALUE) {
            throw std::runtime_error("파일 열기 실패: " + std::to_string(GetLastError()));
        }

        LARGE_INTEGER file_size;
        if (!GetFileSizeEx(file_handle_, &file_size)) {
            CloseHandle(file_handle_);
            throw std::runtime_error("파일 크기 얻기 실패: " + std::to_string(GetLastError()));
        }
        if (file_size.QuadPart <= 0 ||
            static_cast<ULONGLONG>(file_size.QuadPart) > (std::numeric_limits<DWORD>::max)()) {
            CloseHandle(file_handle_);
            throw std::invalid_argument("RIO로 등록할 수 없는 파일 크기입니다");
        }
        file_size_ = static_cast<size_t>(file_size.QuadPart);

        mapping_handle_ = CreateFileMappingW(file_handle_, NULL, PAGE_READONLY, 0, 0, NULL);
        if (mapping_handle_ == NULL) {
            CloseHandle(file_handle_);
            throw std::runtime_error("파일 매핑 생성 실패: " + std::to_string(GetLastError()));
        }

        mapped_view_ = MapViewOfFile(mapping_handle_, FILE_MAP_READ, 0, 0, 0);
        if (mapped_view_ == nullptr) {
            CloseHandle(mapping_handle_);
            CloseHandle(file_handle_);
            throw std::runtime_error("파일 뷰 매핑 실패: " + std::to_string(GetLastError()));
        }

        // 읽기 전용 뷰이므로 송신 전용입니다. 이 매핑을 RIOReceive에 사용하면 안 됩니다.
        buffer_id_ = rio_fn_table_.RIORegisterBuffer(static_cast<char*>(mapped_view_), static_cast<DWORD>(file_size_));
        if (buffer_id_ == RIO_INVALID_BUFFERID) {
            UnmapViewOfFile(mapped_view_);
            CloseHandle(mapping_handle_);
            CloseHandle(file_handle_);
            throw std::runtime_error("RIO 버퍼 등록 실패: " + std::to_string(WSAGetLastError()));
        }
    }

    ~MappedFileBuffer() {
        // RIODeregisterBuffer와 UnmapViewOfFile 이전에 관련 송신 완료를 모두 회수해야 합니다.
        if (buffer_id_ != RIO_INVALID_BUFFERID) rio_fn_table_.RIODeregisterBuffer(buffer_id_);
        if (mapped_view_) UnmapViewOfFile(mapped_view_);
        if (mapping_handle_) CloseHandle(mapping_handle_);
        if (file_handle_ != INVALID_HANDLE_VALUE) CloseHandle(file_handle_);
    }

    MappedFileBuffer(const MappedFileBuffer&) = delete;
    MappedFileBuffer& operator=(const MappedFileBuffer&) = delete;

    // 파일의 일부 구간을 송신합니다. context 역시 완료 통지를 받을 때까지 유효해야 합니다.
    bool SendFilePart(RIO_RQ request_queue, size_t offset, size_t size, void* context) {
        if (size == 0 || offset > file_size_ || size > file_size_ - offset) return false;

        RIO_BUF rio_buffer{};
        rio_buffer.BufferId = buffer_id_;
        rio_buffer.Offset = static_cast<ULONG>(offset);
        rio_buffer.Length = static_cast<ULONG>(size);

        BOOL result = rio_fn_table_.RIOSend(request_queue, &rio_buffer, 1, 0, context);
        if (!result) {
            std::cerr << "RIOSend 실패: " << WSAGetLastError() << std::endl;
            return false;
        }
        return true;
    }

    RIO_BUFFERID GetBufferId() const { return buffer_id_; }
    size_t GetFileSize() const { return file_size_; }
    void* GetMappedView() const { return mapped_view_; }
};

애플리케이션 복사는 줄어들지만, "진짜 제로 카피"는 아닙니다

SendFilePart()에는 memcpy가 전혀 없습니다. 운영체제가 파일을 프로세스 주소 공간에 매핑해준 뒤 그 영역을 등록했으므로, 애플리케이션이 파일 내용을 별도 패킷 버퍼에 옮기는 단계는 없습니다. 다만 파일 페이지를 메모리에 준비하는 비용과 공급자 내부의 데이터 이동 여부는 남습니다. 이 기법은 읽기 전용이며 파일 시스템에서 바로 서빙 가능한 데이터에만 적합합니다. 실시간으로 값이 바뀌는 게임 상태에는 쓰지 않습니다.

4.5 효율적인 RIO 버퍼 관리 전략

  1. 버퍼 크기 최적화 — 애플리케이션의 평균 메시지 크기에 맞게 청크 크기를 조정합니다. 너무 크면 메모리가 낭비되고, 너무 작으면 큰 메시지가 여러 청크에 걸쳐 단편화됩니다.
  2. 대용량/소용량 버퍼 분리 — 크기가 크게 다른 메시지가 섞여 있다면, 청크 크기가 다른 버퍼 링을 두 개(예: 256바이트용, 4KB용) 따로 운영하는 편이 한 크기로 통일하는 것보다 메모리 효율이 좋습니다.
  3. 등록 단위 최소화 — RIO가 요구하는 특별한 정렬을 추측하기보다, 작은 버퍼를 여러 번 등록하지 말고 큰 연속 풀을 한 번 등록합니다. 다른 API가 정렬을 요구할 때만 그 조건을 별도로 적용합니다.
  4. 버퍼 재사용 — 이 장에서 만든 RIOBufferRing·ObjectPool처럼, 할당/해제 대신 재사용 구조를 기본값으로 삼아 메모리 단편화와 할당 오버헤드를 방지합니다.
  5. 비동기 처리와의 연계 — 5장에서 다룰 완료 큐 처리 로직에서, 송신 요청의 완료 결과를 받은 뒤 세그먼트를 Release(segment)로 반납해야 합니다. 큐 등록 직후 반납하면 아직 진행 중인 I/O가 같은 메모리를 덮어쓸 수 있고, 반납을 잊으면 링이 고갈됩니다.

4.6 요약

  1. RIOBufferManager — 큰 메모리 풀을 한 번만 등록·해제하는 RAII 래퍼로, 3장에서 남았던 등록 해제 누락 문제를 해결했습니다.
  2. RIOBufferRing — 등록된 풀을 고정 크기 청크로 나눠 순환 재사용하며, Allocate()/Release(segment)로 빌리고 완료 후 반납합니다.
  3. ObjectPool — placement new로 메모리 할당과 객체 생성을 분리해, C++ 객체 자체도 재사용할 수 있습니다.
  4. 미리 할당 전략 — 최대 연결 수를 기준으로 필요한 메모리를 시작 시점에 한 번에 계산·확보합니다.
  5. 복사 최소화 — 일반 데이터는 등록된 버퍼로 복사하거나 처음부터 그 버퍼에 직렬화합니다. 메모리 맵 파일은 애플리케이션 측 복사를 줄일 수 있지만, 전체 경로의 복사가 없다고 보장하지는 않습니다.
