CHAPTER 01

네트워크 프로그래밍 기초

RIO(Registered I/O)는 결국 "소켓으로 데이터를 더 빠르게 주고받는 방법"입니다. 그 최적화의 의미를 제대로 이해하려면 먼저 일반적인 소켓 프로그래밍이 어떻게 동작하고, 무엇이 느린지를 알아야 합니다. 이번 장에서는 TCP/UDP의 차이, Winsock 소켓 API의 기본 사용법, 블로킹·논블로킹 I/O의 차이를 실제로 동작하는 에코 서버를 만들어보며 익힙니다.

이 장에서 배우는 것

  • TCP와 UDP의 차이, 그리고 게임 서버에서 무엇을 언제 쓸지 판단하는 기준
  • Winsock 소켓 생성부터 연결, 송수신까지 API 하나하나의 역할과 파라미터
  • 블로킹 I/O가 왜 대규모 동시접속에서 한계에 부딪히는지, 논블로킹은 무엇을 바꾸는지
  • Windows가 제공하는 5가지 비동기 I/O 모델의 큰 그림과 RIO가 그중 어디에 있는지
  • C++23의 std::expected·std::span·std::jthread로 네트워크 코드를 더 안전하게 쓰는 법
  • 블로킹 소켓 기반의 멀티스레드 에코 서버를 직접 빌드하고 실행해보기

1.1 TCP/IP와 UDP 프로토콜 이해

게임 서버가 데이터를 "어떻게" 보낼지 결정하는 가장 근본적인 선택입니다.

온라인 게임 서버는 성격이 전혀 다른 두 종류의 데이터를 동시에 다룹니다. "캐릭터가 아이템을 구매했다"는 정보는 단 한 바이트도 유실되면 안 되고, 순서가 뒤바뀌어도 안 됩니다. 반면 "캐릭터가 지금 이 좌표에 있다"는 정보는 0.1초 뒤에 더 최신 값이 도착할 예정이라면, 지금 값 하나쯤 유실돼도 크게 문제가 되지 않습니다. 이 둘을 같은 방식으로 전송하면 둘 중 하나는 반드시 손해를 봅니다. TCP와 UDP는 바로 이 두 가지 요구사항에 각각 최적화된 전송 계층(Transport Layer) 프로토콜입니다.

TCP (Transmission Control Protocol)

TCP는 연결 지향적(connection-oriented) 프로토콜입니다. 데이터를 보내기 전에 먼저 상대방과 "이제부터 통신을 시작하자"는 합의 과정을 거치고, 그렇게 만들어진 가상의 통로(연결)를 통해 데이터를 순서대로, 빠짐없이 전달하는 것을 스스로 보장합니다. 이 보장을 프로그래머가 직접 구현할 필요가 없다는 것이 TCP의 가장 큰 가치입니다.

3-way 핸드셰이크: 연결은 어떻게 시작되는가

TCP 연결은 클라이언트와 서버가 총 3번 메시지를 주고받으며 시작됩니다. 이렇게 3번을 주고받는 이유는 "나도 준비됐고, 너도 준비된 걸 확인했다"는 사실을 양쪽 모두가 알아야 하기 때문입니다. 2번만 주고받으면 서버는 클라이언트가 자신의 응답(SYN-ACK)을 실제로 받았는지 알 방법이 없습니다.

그림 1-1. TCP 3-way 핸드셰이크 — SYN → SYN-ACK → ACK 순서로 연결이 수립됩니다

이 과정은 애플리케이션 코드가 직접 다루지 않습니다. 뒤에서 살펴볼 connect()와 accept() 호출 뒤에서 운영체제(정확히는 TCP/IP 스택)가 대신 처리해 줍니다. 다만 이 과정을 알고 있어야 "왜 connect()가 즉시 반환되지 않고 잠깐 대기하는가", "왜 방화벽에서 SYN 패킷이 막히면 연결이 타임아웃으로 실패하는가" 같은 실전 문제를 진단할 수 있습니다.

참고 · 연결을 끝낼 때도 순서가 있다

연결을 맺을 때 3-way 핸드셰이크가 있듯, 끊을 때도 양쪽이 각자 FIN 패킷을 보내고 상대의 ACK를 받는 절차(보통 4-way)가 있습니다. 서버를 종료하는 코드를 작성할 때 소켓을 그냥 닫아버리면(강제 종료, RST) 상대방에게 아직 전송 중이던 데이터가 유실될 수 있습니다. 7장에서 안전한 종료 처리를 다룰 때 이 내용을 다시 짚습니다.

TCP의 나머지 특징: 신뢰성 · 순서 보장 · 흐름/혼잡 제어

  • 신뢰성(Reliability) — 보낸 패킷마다 확인응답(ACK)을 받고, 일정 시간 안에 ACK가 오지 않으면 자동으로 재전송합니다. 프로그래머는 "패킷이 도착했는지" 걱정하지 않고 send()만 호출하면 됩니다.
  • 순서 보장(Ordering) — 인터넷은 패킷마다 다른 경로로 전달될 수 있어 보낸 순서와 도착 순서가 다를 수 있습니다. TCP는 각 패킷에 순번(sequence number)을 매겨, 수신 측에서 순서가 어긋난 패킷은 버퍼에 잠시 보관했다가 올바른 순서로 애플리케이션에 전달합니다.
  • 흐름 제어(Flow Control) — 수신 측 버퍼가 가득 찼는데 송신 측이 계속 보내면 데이터가 버려집니다. TCP는 수신 윈도우 크기를 상대에게 알려주어, 받을 수 있는 만큼만 보내도록 조절합니다.
  • 혼잡 제어(Congestion Control) — 네트워크 경로 어딘가가 막히기 시작하면 전송 속도를 스스로 줄였다가, 여유가 생기면 다시 늘립니다. 회선 하나를 여러 연결이 나눠 쓸 때 특정 연결이 대역폭을 독점하지 않게 하는 효과도 있습니다.

게임 서버 활용

계정 인증, 인벤토리/재화 변경, 거래, 길드 관리, 채팅 등 "틀리면 안 되는" 데이터는 TCP로 처리합니다.

UDP (User Datagram Protocol)

UDP는 TCP와 정반대의 철학을 가진 비연결 지향적(connectionless) 프로토콜입니다. 핸드셰이크도 없고, 재전송도 없고, 순서 보장도 없습니다. 소켓 하나로 그냥 상대 주소를 지정해서 데이터그램(datagram)을 던지듯 보낼 뿐입니다. 우편에 비유하면 TCP가 반드시 받는 사람 서명을 받는 등기우편이라면, UDP는 우체통에 넣기만 하고 끝인 일반 엽서에 가깝습니다.

  • 비연결성 — 연결 설정 과정 자체가 없어 connect() 없이도(또는 형식적으로만) 바로 sendto()로 데이터를 보낼 수 있습니다.
  • 낮은 오버헤드, 빠른 전송 — 헤더가 TCP(20바이트+)보다 훨씬 작고(8바이트), ACK·재전송·혼잡제어 로직이 없어 지연 시간이 짧습니다.
  • 비신뢰성 — 패킷이 유실돼도 UDP 계층은 알려주지 않습니다. 신뢰성이 필요하면 애플리케이션이 직접 구현해야 합니다.
  • 순서 보장 없음 — 늦게 보낸 패킷이 먼저 도착할 수 있습니다. 캐릭터 이동 패킷처럼 "가장 최신 값만 의미 있는" 데이터에는 오히려 문제가 되지 않습니다.

게임 서버 활용

실시간 위치 동기화, FPS의 조준/이동 입력, 음성 채팅처럼 "늦게 정확한 것보다 지금 대략 맞는 게 나은" 데이터는 UDP로 처리합니다. 다만 완전히 날것으로 쓰기보다, 시퀀스 번호를 붙여 오래된 패킷을 걸러내거나 중요한 패킷만 선택적으로 재전송하는 자체 신뢰성 계층을 얹는 경우가 많습니다.

프로토콜 선택 기준

실무에서는 "TCP냐 UDP냐"를 이분법으로 정하기보다, 데이터 종류별로 나누어 선택합니다.

1.2 소켓 프로그래밍 기본 개념

소켓은 "네트워크 통신을 위한 파일 핸들"입니다 — 전화를 걸기 전에 수화기를 드는 것과 같습니다.

소켓(socket)은 애플리케이션이 네트워크로 데이터를 주고받기 위해 운영체제로부터 받는 통신 끝점(endpoint)입니다. 파일을 다루기 전에 fopen()으로 파일 핸들을 얻는 것처럼, 네트워크 통신을 하기 전에는 항상 소켓이라는 핸들을 먼저 만들어야 합니다. Windows에서 소켓 API의 모음을 Winsock이라고 부르며, 이 책 전체에서 사용할 모든 네트워크 함수는 Winsock이 제공합니다.

1) Winsock 초기화와 소켓 생성

Windows에서 소켓 함수를 하나라도 호출하기 전에, 반드시 Winsock 라이브러리를 초기화해야 합니다. 이 초기화를 건너뛰면 이후의 모든 소켓 함수 호출이 실패합니다.

APIWSAStartup()

프로세스에서 Winsock을 사용하겠다고 운영체제에 등록하고, 요청한 버전의 Winsock DLL을 로드합니다. 프로그램당 한 번, main() 맨 앞에서 호출하는 것이 일반적입니다.

매개변수의미
wVersionRequested요청할 Winsock 버전. MAKEWORD(2, 2)는 2.2 버전을 뜻하며, 사실상 모든 최신 코드가 이 값을 씁니다.
lpWSAData실제 로드된 버전 정보를 돌려받을 WSADATA 구조체 포인터.

반환값이 0이 아니면 초기화에 실패한 것이며, 이 경우 이후의 모든 소켓 함수를 호출해서는 안 됩니다.

APIWSASocketW()

소켓을 생성합니다. 표준 C의 socket() 함수와 같은 역할을 하지만, 확장 플래그를 지정할 수 있어 이 책에서는 대부분 이 함수를 사용합니다. 특히 마지막 플래그에 WSA_FLAG_REGISTERED_IO를 주면 이 소켓을 RIO API와 함께 쓸 수 있게 됩니다 — 2장부터 사용할 핵심 플래그이니 지금부터 눈에 익혀두면 좋습니다.

매개변수의미
af주소 체계. IPv4는 AF_INET.
type소켓 종류. TCP는 SOCK_STREAM, UDP는 SOCK_DGRAM.
protocol구체적 프로토콜. TCP는 IPPROTO_TCP, UDP는 IPPROTO_UDP.
lpProtocolInfo보통 nullptr.
g소켓 그룹 ID. 보통 0.
dwFlagsWSA_FLAG_OVERLAPPED(비동기 I/O 허용), WSA_FLAG_REGISTERED_IO(RIO 사용) 등을 비트 OR로 조합.

실패하면 INVALID_SOCKET을 반환하며, 자세한 원인은 WSAGetLastError()로 확인합니다.

코드 조각 1 — Winsock 초기화

WSADATA wsaData;
int result = WSAStartup(MAKEWORD(2, 2), &wsaData);
if (result != 0) {
    std::cerr << std::format("WSAStartup 실패: {}\n", result);
    return 1;
}

코드 조각 2 — TCP/UDP 소켓 생성

SOCKET tcpSocket = WSASocketW(
    AF_INET, SOCK_STREAM, IPPROTO_TCP,
    nullptr, 0, WSA_FLAG_REGISTERED_IO   // RIO 사용 플래그
);
if (tcpSocket == INVALID_SOCKET) {
    std::cerr << std::format("소켓 생성 실패: {}\n", WSAGetLastError());
    WSACleanup();
    return 1;
}

SOCKET udpSocket = WSASocketW(
    AF_INET, SOCK_DGRAM, IPPROTO_UDP,
    nullptr, 0, WSA_FLAG_REGISTERED_IO
);
// udpSocket도 동일하게 실패를 검사합니다 (아래 전체 코드 참고)

왜 매 호출마다 오류를 검사하는가

네트워크 API는 로컬 함수와 달리 운영체제·드라이버·방화벽 등 통제할 수 없는 요소에 의해 실패할 가능성이 항상 있습니다. 게임 서버는 한 번 크래시하면 수천 명의 접속이 동시에 끊기므로, "실패할 수 있다"고 가정하고 모든 반환값을 검사하는 습관이 처음부터 몸에 배어야 합니다.

2) 소켓 주소 구조체 — 어디로 보낼지 지정하기

소켓을 만들었다고 바로 통신할 수 있는 것은 아닙니다. "어느 IP, 어느 포트와 통신할 것인가"를 별도의 구조체에 담아 전달해야 합니다. IPv4에서는 sockaddr_in을 사용합니다.

STRUCTsockaddr_in
필드의미
sin_family주소 체계. 항상 AF_INET.
sin_port포트 번호. 반드시 htons()로 변환해서 대입해야 합니다.
sin_addrIP 주소(in_addr 구조체). inet_pton()으로 문자열 IP를 바이너리로 변환해 채웁니다.

htons()(host to network short)가 필요한 이유: CPU마다 정수를 메모리에 저장하는 바이트 순서(엔디언)가 다를 수 있는데, 네트워크 프로토콜은 항상 "빅 엔디언(네트워크 바이트 순서)"을 기준으로 통일합니다. htons()는 현재 CPU의 순서를 네트워크 순서로 맞춰주는 변환 함수입니다. 포트·주소 값을 다룰 때마다 습관적으로 붙여야 하는 이유가 여기에 있습니다.

코드 조각 3 — 서버 주소 채우기

sockaddr_in serverAddr{};
serverAddr.sin_family = AF_INET;
serverAddr.sin_port = htons(27015);                      // 호스트 바이트 순서 → 네트워크 바이트 순서
inet_pton(AF_INET, "127.0.0.1", &serverAddr.sin_addr);   // 문자열 IP → 바이너리 IP

3) 서버 소켓 설정 3단계 — bind, listen, accept

서버는 클라이언트의 연결을 받아들이기 전에 세 단계를 거칩니다.

그림 1-2. 서버는 socket→bind→listen→accept, 클라이언트는 socket→connect 순서로 호출하며, 두 accept()·connect()가 만나는 순간이 곧 그림 1-1의 핸드셰이크입니다

APIbind()

생성한 소켓을 특정 IP·포트에 결합합니다. 서버는 클라이언트가 "이 포트로 오면 된다"는 걸 알 수 있도록 반드시 알려진 포트에 바인딩해야 합니다. (클라이언트는 보통 생략하며, 이 경우 OS가 임시 포트를 자동으로 골라줍니다.)

매개변수의미
s바인딩할 소켓.
namesockaddr*로 캐스팅한 sockaddr_in 주소.
namelen주소 구조체 크기, 보통 sizeof(serverAddr).
APIlisten()

소켓을 "연결을 받아들이는 모드"로 전환합니다. 이 호출 이후부터 이 소켓으로 connect() 요청이 들어올 수 있습니다.

매개변수의미
s리스닝할 소켓.
backlogaccept()가 아직 처리하지 못한, 대기 중인 연결을 몇 개까지 큐에 쌓아둘지. SOMAXCONN을 주면 OS가 적절한 최댓값을 사용합니다.
APIaccept()

대기 큐에 쌓인 연결 요청을 하나 꺼내, 그 클라이언트 전용의 새 소켓을 만들어 반환합니다. 리스닝 소켓 자체는 이후에도 계속 다른 연결을 받기 위해 살아있고, 실제 데이터 송수신은 이 새 소켓으로 합니다. 이 함수는 대기 중인 연결이 없으면 하나가 들어올 때까지 블로킹됩니다 — 이 "블로킹"이 무엇을 뜻하는지는 바로 다음 절에서 다룹니다.

4) 클라이언트 연결 — connect()

APIconnect()

클라이언트 소켓에서 서버로 연결을 시도합니다. 내부적으로 그림 1-1의 3-way 핸드셰이크를 수행하며, 성공적으로 완료되어야 함수가 반환됩니다.

코드 조각 4 — 서버 설정과 클라이언트 연결

// [서버] 바인딩 → 리스닝 → 수락
bind(serverSocket, reinterpret_cast<sockaddr*>(&serverAddr), sizeof(serverAddr));
listen(serverSocket, SOMAXCONN);

sockaddr_in clientAddr{};
int clientAddrSize = sizeof(clientAddr);
SOCKET clientSocket = accept(serverSocket, reinterpret_cast<sockaddr*>(&clientAddr), &clientAddrSize);

// [클라이언트] 연결 시도
connect(clientSocket, reinterpret_cast<sockaddr*>(&serverAddr), sizeof(serverAddr));

5) 데이터 송수신 — send(), recv()

APIsend() / recv()

연결이 맺어진 소켓으로 바이트 스트림을 주고받는 가장 기본적인 함수입니다. send()는 실제로 전송한 바이트 수를 반환하는데, 요청한 크기 전체가 한 번에 전송된다는 보장이 없습니다 — 반환값이 요청 크기보다 작을 수 있어, 실전 코드에서는 남은 만큼 반복 전송하는 로직이 필요합니다(6~7장에서 다룹니다). recv()는 데이터를 받으면 받은 바이트 수를, 상대가 정상적으로 연결을 종료하면 0을, 오류가 나면 SOCKET_ERROR를 반환합니다.

코드 조각 5 — 송수신

const char* message = "Hello, Game Server!";
int bytesSent = send(clientSocket, message, static_cast<int>(strlen(message)), 0);

char buffer[1024];
int bytesReceived = recv(clientSocket, buffer, sizeof(buffer), 0);
if (bytesReceived > 0) {
    buffer[bytesReceived] = '\0';
    std::cout << std::format("수신된 데이터: {}\n", buffer);
} else if (bytesReceived == 0) {
    std::cout << "연결이 종료되었습니다.\n";
} else {
    std::cerr << std::format("수신 실패: {}\n", WSAGetLastError());
}

recv()의 세 가지 반환값을 반드시 구분하라

recv()는 양수(받은 바이트 수), 0(정상 종료), 음수/SOCKET_ERROR(오류) 세 가지를 완전히 다르게 처리해야 합니다. 이 셋을 구분하지 않고 "0 이하면 실패"로 뭉뚱그리면, 클라이언트가 정상적으로 연결을 끊은 상황과 네트워크 오류를 같은 코드로 처리하게 되어 원인 파악이 어려워집니다.

1.3 블로킹 vs 논블로킹 I/O

동시접속자 100명과 100만 명의 서버를 가르는 가장 근본적인 설계 선택입니다.

앞 절의 accept()와 recv()는 사실 조용히 한 가지를 가정하고 있었습니다. "데이터가 올 때까지 함수가 기다려준다"는 가정입니다. 이런 방식을 블로킹(blocking) I/O라고 부릅니다. 사람 한 명이 손님 한 명을 상대로 응대가 끝날 때까지 다른 손님을 받지 않는 창구와 같습니다. 손님이 한두 명일 땐 문제없지만, 수천 명이 동시에 줄을 서면 창구(스레드) 수만큼만 동시에 처리할 수 있다는 한계가 바로 드러납니다.

블로킹 I/O

recv()를 블로킹 소켓에서 호출하면, 데이터가 도착하거나 오류가 발생할 때까지 그 스레드는 다른 어떤 일도 하지 못한 채 멈춰 있습니다. 구현은 매우 직관적이지만("코드가 위에서 아래로 순서대로 실행된다"는 상식이 그대로 통합니다), 문제는 동시접속자 수만큼 스레드가 필요하다는 점입니다. 앞서 만든 에코 서버가 클라이언트마다 std::jthread를 하나씩 띄운 것도 이 때문입니다. 스레드는 공짜가 아닙니다 — 스레드 하나마다 스택 메모리(기본 1MB)를 차지하고, 스레드 간 컨텍스트 스위칭 비용도 발생합니다. 접속자가 수만 명 단위로 늘어나면 이 비용이 서버 전체를 잠식합니다. 

// 블로킹 소켓에서의 데이터 수신
char buffer[1024];
int bytesReceived = recv(clientSocket, buffer, sizeof(buffer), 0);
// recv()는 데이터가 도착하거나 오류가 발생할 때까지 반환되지 않습니다

논블로킹 I/O

논블로킹(non-blocking) I/O는 데이터가 아직 없어도 함수가 즉시 반환되도록 소켓의 동작 방식 자체를 바꿉니다. 스레드는 "지금 데이터 없음"이라는 답을 받고 즉시 다른 일을 할 수 있습니다. 대신 "데이터가 준비됐는지"를 스스로 계속 확인(polling)해야 하므로 구현이 복잡해집니다.

APIioctlsocket()

소켓의 동작 모드를 제어하는 범용 함수입니다. FIONBIO 명령과 함께 쓰면 소켓을 블로킹/논블로킹 모드로 전환할 수 있습니다.

매개변수의미
s대상 소켓.
cmdFIONBIO — 블로킹 모드 설정 명령.
argpu_long*. 가리키는 값이 0이면 블로킹, 0이 아니면(보통 1) 논블로킹.

코드 조각 6 — 논블로킹 모드 전환과 사용

u_long mode = 1;  // 1: 논블로킹, 0: 블로킹
ioctlsocket(clientSocket, FIONBIO, &mode);

// 논블로킹 소켓에서의 수신 — 반환값을 반드시 3갈래로 분기
char buffer[1024];
int bytesReceived = recv(clientSocket, buffer, sizeof(buffer), 0);

if (bytesReceived > 0) {
    // 데이터 처리
} else if (bytesReceived == SOCKET_ERROR) {
    int error = WSAGetLastError();
    if (error == WSAEWOULDBLOCK) {
        // 아직 데이터 없음 — 정상 상황, 다른 작업 수행 가능
    } else {
        // 진짜 오류
    }
}

WSAEWOULDBLOCK은 오류가 아니다

논블로킹 소켓에서 recv()가 SOCKET_ERROR를 반환했다고 바로 실패로 취급하면 안 됩니다. WSAGetLastError()가 WSAEWOULDBLOCK이면 "지금 당장 처리할 데이터가 없다"는 정상적인 신호일 뿐입니다. 이 구분을 놓치는 것은 논블로킹 코드를 처음 작성할 때 가장 흔한 실수입니다.

그림 1-3. 같은 대기 시간이라도 논블로킹 스레드는 폴링 사이사이 다른 클라이언트의 작업을 처리할 수 있습니다

다만 그림의 논블로킹 쪽을 "무한 반복문으로 계속 recv()를 찔러본다"는 식으로 구현하면 CPU를 100% 낭비하는 바쁜 대기(busy waiting)가 되어 버립니다. 실전에서는 "지금 어떤 소켓에 데이터가 준비됐는지"를 운영체제에게 물어보고, 준비된 소켓만 골라서 처리하는 방식을 씁니다. 이게 바로 다음에 설명할 비동기 I/O 모델들의 역할입니다.

Windows 비동기 I/O 모델의 계보

Windows는 "논블로킹 + 폴링"의 비효율을 해결하기 위해 지난 수십 년간 여러 세대의 비동기 I/O API를 내놓았습니다. 각 세대는 이전 세대의 한계(대부분 "동시접속자가 늘어날수록 성능이 어떻게 저하되는가")를 해결하는 방향으로 발전했습니다. RIO는 이 계보의 가장 최신 지점에 있습니다.

그림 1-4. 블로킹 I/O에서 RIO까지 — 오른쪽으로 갈수록 커널 모드 전환과 메모리 복사가 줄어들고, 더 많은 동시 연결을 적은 스레드로 처리할 수 있습니다

  1. 이벤트 기반 — WSAEventSelect()로 소켓에 이벤트 객체를 연결하고, WSAWaitForMultipleEvents()로 여러 소켓의 상태 변화를 한 번에 기다립니다.
  2. 콜백 기반 — WSAAsyncSelect()로 소켓 이벤트를 윈도우 메시지로 받습니다. GUI 애플리케이션과는 잘 맞지만 서버에는 잘 쓰이지 않습니다.
  3. 중첩 I/O(Overlapped I/O) — WSASend()/WSARecv()에 OVERLAPPED 구조체를 넘겨, 작업을 커널에 등록만 해두고 완료되면 통보받는 방식입니다.
  4. 완료 포트(IOCP) — CreateIoCompletionPort()로 여러 개의 중첩 I/O 완료 통지를 소수의 워커 스레드가 몰아서 처리하도록 묶는 구조입니다. 오랫동안 Windows 고성능 서버의 표준으로 쓰였습니다.
  5. 등록된 I/O(RIO) — IOCP보다 한 단계 더 나아가, 버퍼를 미리 커널에 등록해두고 요청·완료를 배치(batch) 단위로 처리함으로써 시스템 콜 횟수와 메모리 복사를 더욱 줄인 최신 API입니다.

RIO가 잘하는 것

  • 메모리 복사를 최소화하는 제로 카피(zero-copy) 전송에 가까운 처리
  • 유저 모드 ↔ 커널 모드 전환(모드 스위칭) 횟수 감소
  • 미리 등록한 버퍼를 재사용하는 최적화된 버퍼 관리
  • 초당 수만~수십만 건의 소규모 패킷을 처리해야 하는 게임 서버에 특히 효율적

이 다섯 모델의 자세한 동작 방식, 특히 IOCP와 RIO의 구체적인 차이는 2장에서 본격적으로 다룹니다. 지금은 "RIO는 갑자기 등장한 특수한 기술이 아니라, 블로킹 I/O의 한계를 하나씩 극복해 온 자연스러운 다음 단계"라는 큰 그림만 기억하면 충분합니다.

1.4 C++23 네트워킹 관련 기능

C++23에는 아직 표준 네트워킹 라이브러리가 없지만, 네트워크 코드를 훨씬 안전하게 만들어주는 언어 기능들이 생겼습니다.

C++ 표준 위원회의 Networking TS(Technical Specification)는 아직 정식 표준에 포함되지 않았습니다. 그래서 이 책에서도 Winsock API를 직접 호출합니다. 다만 C++23의 세 가지 기능 — std::expected, std::span, std::jthread — 을 활용하면 그 위에 훨씬 안전한 래퍼를 씌울 수 있습니다. 이 세 가지는 이후 6장의 "모던 C++ RIO 래퍼 클래스"에서 본격적으로 사용하므로, 지금 기본 사용법을 익혀두면 뒤에서 훨씬 수월합니다.

std::expected — "실패할 수 있는 함수"를 타입으로 표현하기

지금까지의 예제 코드는 실패를 INVALID_SOCKET이나 SOCKET_ERROR 같은 "특별한 값"으로 표현했습니다. 이 방식의 문제는, 함수 시그니처만 봐서는 그 함수가 실패할 수 있다는 사실 자체를 알 수 없다는 점입니다. std::expected<T, E>는 "성공하면 T, 실패하면 E(보통 오류 메시지나 오류 코드)"라는 두 가지 결과를 타입 시스템 차원에서 명시적으로 표현합니다. 호출하는 쪽은 반환값을 if (result)로 검사하지 않으면 컴파일러 경고 없이도 실수하기 쉽지만, *result로 값을 꺼내려면 먼저 성공 여부를 인지하고 있어야 한다는 점에서 예외(exception)보다 흐름이 명확하고, 예외 처리 비용도 없습니다. 

std::expected<int, std::string> sendMessage(SOCKET socket, const std::string& message) {
    int result = send(socket, message.c_str(), static_cast<int>(message.length()), 0);
    if (result == SOCKET_ERROR) {
        return std::unexpected(std::format("전송 오류: {}", WSAGetLastError()));
    }
    return result;   // 성공 시 전송한 바이트 수를 담아 반환
}

void useExpected(SOCKET socket) {
    auto result = sendMessage(socket, "Hello");
    if (result) {
        std::cout << std::format("전송된 바이트: {}\n", *result);
    } else {
        std::cerr << result.error() << '\n';   // 실패 이유가 문자열로 담겨 있음
    }
}

std::span — 소유하지 않고 "바라보는" 버퍼 뷰

네트워크 코드는 버퍼를 함수 간에 계속 넘겨야 합니다. 이때 std::vector<std::byte>를 통째로 복사해서 넘기면 성능이 낭비되고, (포인터, 길이) 두 개를 따로 넘기면 둘이 어긋날 위험이 있습니다. std::span은 "이미 존재하는 메모리를 소유권 없이 가리키는 뷰"로, 포인터와 길이를 하나로 묶어 안전하게 전달합니다. 특히 "수신 버퍼는 1024바이트지만 실제로 받은 건 512바이트뿐"인 상황에서, 실제로 유효한 범위만 골라 넘길 때 유용합니다. 

void processPacket(std::span<const std::byte> buffer) {
    // 패킷 데이터 처리 — buffer.size()만큼만 유효
}

void handleNetworkData() {
    std::vector<std::byte> receivedData(1024);   // 수신 버퍼(용량 1024)
    size_t bytesReceived = 512;                   // 실제로 recv()가 받은 바이트 수

    // 실제 수신된 데이터만큼만 잘라서 전달 — 복사 없음
    processPacket(std::span(receivedData.begin(), bytesReceived));
}

std::jthread — 스스로 정리되는 스레드

기존 std::thread는 소멸되기 전에 반드시 join()이나 detach()를 직접 호출해줘야 하며, 이를 잊으면 프로그램이 즉시 std::terminate()로 종료됩니다. 서버처럼 스레드를 계속 생성·소멸하는 코드에서는 이 실수가 치명적입니다. std::jthread는 소멸자에서 자동으로 join()을 호출하고, std::stop_token을 통해 "이제 그만 멈춰라"는 신호를 스레드 내부로 깔끔하게 전달할 수 있습니다. 

class NetworkHandler {
public:
    void start() {
        _worker = std::jthread([this](std::stop_token stoken) {
            while (!stoken.stop_requested()) {
                processNetworkEvents();
                std::this_thread::sleep_for(std::chrono::milliseconds(10));
            }
            cleanup();
        });
    }
    // 소멸자를 따로 작성하지 않아도 _worker가 소멸되며 자동으로 join() 수행
private:
    std::jthread _worker;
    void processNetworkEvents() { /* ... */ }
    void cleanup() { /* ... */ }
};

세 기능을 조합한 RAII 래퍼 클래스

이제 위 세 기능을 조합해 RIO 소켓을 감싸는 작은 래퍼 클래스 RioSocket을 만들어봅니다. RAII(Resource Acquisition Is Initialization) 패턴 — 생성자에서 자원을 얻고 소멸자에서 반드시 해제하는 원칙 — 을 적용해, 소켓을 close()하는 걸 깜빡해서 발생하는 리소스 누수를 원천적으로 막습니다. (6장에서 이 클래스를 훨씬 더 완성된 형태로 확장합니다.)

코드 조각 7 — 정적 초기화/정리 함수

코드 조각 8 — 소켓 생성과 RIO 함수 테이블 조회

std::expected<void, std::string> create(int type = SOCK_STREAM, int protocol = IPPROTO_TCP) {
    _socket = WSASocketW(AF_INET, type, protocol, nullptr, 0, WSA_FLAG_REGISTERED_IO);
    if (_socket == INVALID_SOCKET) {
        return std::unexpected(std::format("소켓 생성 실패: {}", WSAGetLastError()));
    }

    // RIO 함수들은 일반 함수가 아니라, 소켓마다 WSAIoctl()로 "함수 포인터 테이블"을
    // 가져와야 호출할 수 있습니다 — 자세한 이유는 2장에서 다룹니다.
    GUID functionTableId = WSAID_MULTIPLE_RIO;
    DWORD dwBytes = 0;
    int result = WSAIoctl(_socket, SIO_GET_MULTIPLE_EXTENSION_FUNCTION_POINTER,
                           &functionTableId, sizeof(GUID),
                           &_rioFunctions, sizeof(_rioFunctions),
                           &dwBytes, NULL, NULL);
    if (result == SOCKET_ERROR) {
        close();
        return std::unexpected(std::format("RIO 함수 테이블 초기화 실패: {}", WSAGetLastError()));
    }
    return {};
}

코드 조각 9 — RAII 소멸자

void close() {
    if (_socket != INVALID_SOCKET) {
        closesocket(_socket);
        _socket = INVALID_SOCKET;
    }
}
~RioSocket() { close(); }   // 예외가 나든, 함수를 일찍 return하든 항상 호출됨

1.5 실전 연습 — 간단한 에코 서버

지금까지 배운 API를 모두 모아, 블로킹 소켓 기반의 멀티스레드 에코 서버를 직접 완성합니다.

"에코(echo) 서버"는 클라이언트가 보낸 데이터를 그대로 되돌려주는 가장 단순한 서버입니다. 기능은 사소하지만, 소켓 생성부터 연결 수락, 멀티스레드 처리, 정리까지 서버 프로그램의 뼈대가 모두 들어있어 네트워크 프로그래밍의 "Hello, World"로 자주 쓰입니다. 이번 절에서 만드는 이 서버는 3장부터 RIO 버전으로 다시 만들 것이므로, 지금 구조를 잘 익혀두면 뒤에서 "무엇이 RIO로 바뀌었는지"를 비교하며 이해하기 훨씬 쉬워집니다.

1) 클라이언트 하나를 전담하는 함수

연결마다 스레드 하나를 붙이는 가장 단순한 동시성 모델입니다. 클라이언트가 데이터를 보내면 받은 그대로 돌려보내고, 연결이 끊기거나 오류가 나면 소켓을 닫고 스레드를 종료합니다. 

void handleClient(SOCKET clientSocket) {
    char buffer[1024];
    int bytesReceived;

    while (true) {
        bytesReceived = recv(clientSocket, buffer, sizeof(buffer), 0);
        if (bytesReceived <= 0) {
            if (bytesReceived == 0) {
                std::cout << "클라이언트가 연결을 종료했습니다.\n";
            } else {
                std::cerr << std::format("recv 실패: {}\n", WSAGetLastError());
            }
            break;
        }

        buffer[bytesReceived] = '\0';
        std::cout << std::format("수신: {}\n", buffer);

        int bytesSent = send(clientSocket, buffer, bytesReceived, 0);
        if (bytesSent == SOCKET_ERROR) {
            std::cerr << std::format("send 실패: {}\n", WSAGetLastError());
            break;
        }
    }
    closesocket(clientSocket);
}

2) 리스닝 소켓 준비

main()은 Winsock을 초기화하고, 앞서 배운 bind()·listen()으로 27015번 포트에서 연결을 기다릴 준비를 합니다. 

WSADATA wsaData;
WSAStartup(MAKEWORD(2, 2), &wsaData);

SOCKET listenSocket = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);

sockaddr_in serverAddr{};
serverAddr.sin_family = AF_INET;
serverAddr.sin_port = htons(27015);
serverAddr.sin_addr.s_addr = INADDR_ANY;   // 모든 네트워크 인터페이스에서 연결 수락

bind(listenSocket, reinterpret_cast<sockaddr*>(&serverAddr), sizeof(serverAddr));
listen(listenSocket, SOMAXCONN);

INADDR_ANY의 의미

서버 PC에 네트워크 인터페이스가 여러 개(예: 유선 랜, 무선 랜, 가상 어댑터) 있을 수 있습니다. INADDR_ANY는 특정 IP 하나로 제한하지 않고, 이 PC로 들어오는 모든 IP 주소의 연결 요청을 받겠다는 뜻입니다. 서버는 거의 항상 이 값을 사용합니다.

3) 연결 수락 루프 — 클라이언트마다 스레드 생성

accept()가 반환하는 즉시 새 스레드를 띄워 그 클라이언트를 전담시키고, 메인 스레드는 바로 다음 accept()로 돌아가 또 다른 클라이언트를 기다립니다. 이렇게 해야 한 클라이언트를 처리하는 동안 다른 클라이언트의 연결 요청이 밀리지 않습니다. 

std::vector<std::jthread> clientThreads;

while (true) {
    sockaddr_in clientAddr{};
    int clientAddrSize = sizeof(clientAddr);
    SOCKET clientSocket = accept(listenSocket, reinterpret_cast<sockaddr*>(&clientAddr), &clientAddrSize);
    if (clientSocket == INVALID_SOCKET) {
        std::cerr << std::format("연결 수락 실패: {}\n", WSAGetLastError());
        continue;
    }

    char clientIP[INET_ADDRSTRLEN];
    inet_ntop(AF_INET, &clientAddr.sin_addr, clientIP, INET_ADDRSTRLEN);
    std::cout << std::format("새 클라이언트 연결: {}\n", clientIP);

    clientThreads.emplace_back(handleClient, clientSocket);   // 스레드마다 클라이언트 하나 전담
}

이 모델의 한계 — 그래서 RIO가 필요합니다

"연결마다 스레드 하나"는 이해하기 쉽지만, 접속자가 수천 명만 되어도 스레드 수천 개가 대부분 recv()에서 블로킹된 채 잠들어 있는 상태가 됩니다. 각 스레드가 차지하는 스택 메모리와 OS 스케줄러의 컨텍스트 스위칭 비용이 접속자 수에 비례해 계속 늘어나므로, 이 구조로는 대규모 동시접속을 감당할 수 없습니다. 2장부터는 소수의 스레드로 수만 개의 연결을 처리하는 RIO 기반 구조로 바꿔 나갑니다.

전체 코드 — 블로킹 소켓 기반 에코 서버

#include <winsock2.h>
#include <ws2tcpip.h>
#include <iostream>
#include <format>
#include <string>
#include <thread>
#include <vector>

#pragma comment(lib, "ws2_32.lib")

void handleClient(SOCKET clientSocket) {
    char buffer[1024];
    int bytesReceived;

    while (true) {
        bytesReceived = recv(clientSocket, buffer, sizeof(buffer), 0);
        if (bytesReceived <= 0) {
            if (bytesReceived == 0) {
                std::cout << "클라이언트가 연결을 종료했습니다.\n";
            } else {
                std::cerr << std::format("recv 실패: {}\n", WSAGetLastError());
            }
            break;
        }

        buffer[bytesReceived] = '\0';
        std::cout << std::format("수신: {}\n", buffer);

        int bytesSent = send(clientSocket, buffer, bytesReceived, 0);
        if (bytesSent == SOCKET_ERROR) {
            std::cerr << std::format("send 실패: {}\n", WSAGetLastError());
            break;
        }
    }

    closesocket(clientSocket);
}

int main() {
    WSADATA wsaData;
    int result = WSAStartup(MAKEWORD(2, 2), &wsaData);
    if (result != 0) {
        std::cerr << std::format("WSAStartup 실패: {}\n", result);
        return 1;
    }

    SOCKET listenSocket = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
    if (listenSocket == INVALID_SOCKET) {
        std::cerr << std::format("소켓 생성 실패: {}\n", WSAGetLastError());
        WSACleanup();
        return 1;
    }

    sockaddr_in serverAddr{};
    serverAddr.sin_family = AF_INET;
    serverAddr.sin_port = htons(27015);
    serverAddr.sin_addr.s_addr = INADDR_ANY;

    result = bind(listenSocket, reinterpret_cast<sockaddr*>(&serverAddr), sizeof(serverAddr));
    if (result == SOCKET_ERROR) {
        std::cerr << std::format("바인드 실패: {}\n", WSAGetLastError());
        closesocket(listenSocket);
        WSACleanup();
        return 1;
    }

    result = listen(listenSocket, SOMAXCONN);
    if (result == SOCKET_ERROR) {
        std::cerr << std::format("리슨 실패: {}\n", WSAGetLastError());
        closesocket(listenSocket);
        WSACleanup();
        return 1;
    }

    std::cout << "에코 서버가 시작되었습니다. 포트: 27015\n";

    std::vector<std::jthread> clientThreads;

    while (true) {
        sockaddr_in clientAddr{};
        int clientAddrSize = sizeof(clientAddr);

        SOCKET clientSocket = accept(listenSocket, reinterpret_cast<sockaddr*>(&clientAddr), &clientAddrSize);
        if (clientSocket == INVALID_SOCKET) {
            std::cerr << std::format("연결 수락 실패: {}\n", WSAGetLastError());
            continue;
        }

        char clientIP[INET_ADDRSTRLEN];
        inet_ntop(AF_INET, &clientAddr.sin_addr, clientIP, INET_ADDRSTRLEN);
        std::cout << std::format("새 클라이언트 연결: {}\n", clientIP);

        clientThreads.emplace_back(handleClient, clientSocket);
    }

    closesocket(listenSocket);
    WSACleanup();
    return 0;
}

  1. 빌드 후 실행하면 콘솔에 에코 서버가 시작되었습니다. 포트: 27015가 출력됩니다.
  2. Windows에 텔넷 클라이언트 기능이 꺼져 있다면, "Windows 기능 켜기/끄기"에서 "텔넷 클라이언트"를 체크해 설치합니다.
  3. 새 명령 프롬프트를 열고 telnet 127.0.0.1 27015로 접속한 뒤 아무 문자열이나 입력하면, 서버가 그대로 되돌려주는 것을 확인할 수 있습니다.
  4. 명령 프롬프트를 여러 개 더 열어 동시에 접속해보면, 서버 콘솔에 클라이언트마다 별도의 "새 클라이언트 연결" 로그가 찍히는 것을 볼 수 있습니다 — 클라이언트마다 스레드가 하나씩 만들어지고 있다는 증거입니다.

telnet이 번거롭다면

1.6 요약

  1. TCP와 UDP — TCP는 3-way 핸드셰이크로 신뢰성 있는 연결을 제공하고, UDP는 연결 없이 빠르게 보냅니다. 게임 서버는 데이터의 성격(정확성 vs 실시간성)에 따라 둘을 함께 씁니다.
  2. 소켓 프로그래밍의 기본 흐름 — 서버는 소켓 생성 → bind() → listen() → accept(), 클라이언트는 소켓 생성 → connect() 순서로 호출하며, 이후 send()/recv()로 데이터를 주고받습니다.
  3. 블로킹 vs 논블로킹 — 블로킹은 구현이 쉽지만 접속자 수만큼 스레드가 필요해 확장성이 떨어지고, 논블로킹은 스레드를 아끼는 대신 폴링 로직이 필요합니다. Windows는 이벤트 기반, Overlapped I/O + IOCP, 그리고 RIO까지 이어지는 비동기 I/O 모델을 세대별로 발전시켜 왔습니다.
  4. C++23 기능 — std::expected로 명시적인 오류 처리를, std::span으로 안전한 버퍼 뷰를, std::jthread로 자동 정리되는 스레드를 사용해 더 안전한 네트워크 코드를 작성할 수 있습니다.
  5. 직접 만든 에코 서버 — 연결마다 스레드를 하나씩 붙이는 가장 단순한 동시성 모델을 직접 빌드하고 실행해봤습니다. 이 구조의 한계(스레드 수 = 접속자 수)가 바로 RIO가 해결하려는 문제입니다.
