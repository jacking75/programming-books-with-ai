CHAPTER 02

Windows Registered I/O(RIO) 소개

1장에서 만든 "스레드 하나당 연결 하나" 에코 서버는 접속자가 늘어날수록 스레드 비용이 그대로 늘어난다는 한계가 있었습니다. RIO는 이 한계를 정면으로 겨냥한 API입니다. 버퍼를 미리 등록해두고, 요청과 완료를 큐 단위로 몰아서 처리함으로써 커널 모드 전환과 메모리 복사를 최소화합니다. 이번 장에서는 RIO가 "왜" 빠른지, 그리고 RIO를 구성하는 핵심 개념들(함수 테이블, 버퍼 등록, 완료 큐, 요청 큐)을 실제 API 시그니처와 함께 살펴봅니다.

이 장에서 배우는 것

  • RIO가 등장한 배경과, 전통적인 소켓 프로그래밍 대비 무엇이 다른지
  • 제로 카피 전송이 실제로 무엇을 생략하는 것인지 메모리 경로로 이해하기
  • RIO 아키텍처의 4대 구성요소: 함수 테이블 · 버퍼 등록 · 완료 큐 · 요청 큐
  • RIORegisterBuffer, RIOCreateRequestQueue, RIOSend/RIOReceive, RIODequeueCompletion 등 주요 RIO 함수의 시그니처와 파라미터
  • 이 함수들을 조합해 RIO 서버의 골격을 이루는 예제 코드 읽는 법
  • 버퍼 크기, 큐 크기, 통지 전략 등 RIO 성능 튜닝의 기본 체크리스트

2.1 RIO의 개념과 장점

RIO는 "커널이 대신 복사해주는 한 단계"를 없애버리는 API입니다.

RIO란?

Windows Registered I/O(RIO)는 Windows 8 / Windows Server 2012부터 도입된 고성능 네트워크 프로그래밍 API입니다. 이름 그대로 "등록(Registered)"이 핵심입니다 — 데이터를 주고받을 메모리 버퍼를 미리 커널에 등록해두고, 이후의 모든 송수신 요청은 그 등록된 버퍼를 가리키는 가벼운 참조만 주고받습니다. 대규모 동시 접속과 대량의 소규모 패킷을 처리해야 하는 온라인 게임 서버는 RIO가 상정하는 워크로드와 정확히 일치합니다.

RIO의 주요 장점

1) 메모리 복사 최소화 (제로 카피에 가까운 처리)

전통적인 소켓 I/O에서 데이터는 애플리케이션이 만든 버퍼에서 시작해, 커널이 관리하는 시스템 버퍼를 거쳐야 네트워크 카드로 나갑니다. 이 "거쳐가는" 단계마다 CPU가 메모리를 한 번씩 복사(memcpy)해야 합니다. RIO는 애플리케이션 버퍼를 커널에 미리 등록해둠으로써, 커널이 그 버퍼의 위치를 이미 알고 있는 상태로 만듭니다. 그 결과 중간 복사 단계 없이 등록된 버퍼에서 곧바로 네트워크 카드로 전달할 수 있습니다.

그림 2-1. 전통적인 방식은 두 번 복사하지만, RIO는 등록해둔 버퍼에서 곧바로 네트워크 카드로 전달합니다

코드 조각 1 — 버퍼를 한 번만 등록하고 계속 재사용

// RIO에서는 버퍼를 미리 등록하고 재사용합니다
RIO_BUFFERID bufferId = _rioFunctions->RIORegisterBuffer(buffer, bufferSize);
// 이후 수천 번의 송수신 요청에서 이 bufferId를 계속 재사용 — 매번 새로 등록하지 않습니다

2) 향상된 버퍼 관리

버퍼를 미리 등록해두면, 매 요청마다 반복되던 메모리 할당·해제(그리고 그에 따르는 커널의 페이지 잠금/검증 작업)를 생략할 수 있습니다.

3) 커널 모드 전환 감소

시스템 호출(system call) 한 번은 유저 모드에서 커널 모드로 전환했다가 다시 돌아오는 비용을 수반합니다. 연결 하나당 recv()를 계속 개별 호출하는 대신, RIO는 여러 요청을 큐에 모아두고 완료도 배치로 가져오기 때문에 이 전환 횟수 자체가 줄어듭니다.

4) 효율적인 멀티코어 활용

RIO 완료 큐는 특정 CPU 코어와의 친화성(affinity)을 설정할 수 있어, 네트워크 처리를 특정 코어에 집중시켜 CPU 캐시 적중률을 높이는 구성이 가능합니다. (구체적인 설정 방법은 5장에서 다룹니다.)

5) 대량의 소규모 패킷 처리 최적화

온라인 게임은 "이동 좌표 갱신"처럼 수십~수백 바이트짜리 패킷을 초당 수만 건씩 주고받는 경우가 많습니다. RIO는 바로 이런 워크로드 — 크지만 드문 전송이 아니라, 작지만 매우 빈번한 전송 — 에 최적화되어 있습니다.

게임 서버에서의 RIO 활용 시나리오

소셜/카드 게임적은 서버 리소스로 훨씬 많은 동시 플레이어 지원

2.2 전통적인 소켓 프로그래밍과의 차이점

"무엇을 어떻게 부르는가"가 아니라 "언제, 얼마나 자주 커널과 대화하는가"가 근본적으로 다릅니다.

1) 버퍼 관리 방식

1장의 블로킹 에코 서버는 매 recv()마다 스택 버퍼를 그대로 재사용했지만, 힙 버퍼를 쓰는 흔한 패턴이라면 아래처럼 요청마다 할당·해제를 반복합니다. RIO는 처음부터 이 패턴을 금지하듯, 버퍼를 "등록"이라는 별도 절차로 커널에 딱 한 번 알려주고 프로그램이 끝날 때까지 재사용합니다.

전통적인 방식 — 매 요청마다 할당/해제

char* buffer = new char[1024];
recv(socket, buffer, 1024, 0);
// 데이터 처리
delete[] buffer;   // 다음 요청이 오면 또 new/delete를 반복

RIO 방식 — 한 번 등록하고 계속 재사용

char* buffer = new char[1024];
RIO_BUFFERID bufferId = _rioFunctions->RIORegisterBuffer(buffer, 1024);

// 여러 요청에서 같은 bufferId를 계속 재사용
RIO_BUF rioBuf;
rioBuf.BufferId = bufferId;
rioBuf.Offset = 0;
rioBuf.Length = 1024;
_rioFunctions->RIOReceive(requestQueue, &rioBuf, 1, 0, nullptr);

// 프로그램 종료 시점에만 해제
_rioFunctions->RIODeregisterBuffer(bufferId);
delete[] buffer;

2) 결과 통지 방식

RIO 이전까지 Windows 고성능 서버의 표준이었던 IOCP(완료 포트)는 GetQueuedCompletionStatus()를 호출해 완료된 I/O를 한 번에 하나씩 꺼내옵니다. RIO는 RIODequeueCompletion()으로 완료된 여러 결과를 배열에 한 번에 담아 꺼내온다는 점이 다릅니다 — 시스템 호출 한 번으로 열 건, 백 건의 완료를 동시에 처리할 수 있다는 뜻입니다.

API (비교)GetQueuedCompletionStatus()

IOCP 방식에서 완료 포트로부터 완료된 I/O 작업을 하나 꺼내옵니다. 완료된 작업이 없으면 호출한 스레드가 블로킹되어 대기합니다 (RIO는 5장에서 다룰 별도의 통지 방식을 사용합니다).

전통적인 IOCP 방식 — 한 번에 하나씩

DWORD bytesTransferred;
OVERLAPPED* pOverlapped;
ULONG_PTR completionKey;

GetQueuedCompletionStatus(
    hCompletionPort,
    &bytesTransferred,
    &completionKey,
    &pOverlapped,
    INFINITE
);

RIO 방식 — 여러 건을 배열로 한 번에

RIORESULT results[10];
ULONG numResults = _rioFunctions->RIODequeueCompletion(
    completionQueue,
    results,
    10
);

for (ULONG i = 0; i < numResults; i++) {
    DWORD bytesTransferred = results[i].BytesTransferred;
    ULONG_PTR completionKey = results[i].RequestContext;
    // 결과 구조체에서 직접 정보를 추출해 데이터 처리
}

그렇다고 IOCP가 나쁜 선택은 아닙니다

IOCP는 여전히 안정적이고 검증된 선택지이며, 대부분의 상용 서버 프레임워크가 IOCP 기반입니다. RIO는 "초당 처리해야 할 소규모 패킷 수"가 매우 크고, 커널 전환 자체가 병목이 되는 극단적인 고성능 시나리오에서 그 차이가 의미 있게 드러납니다. 일반적인 규모의 서버라면 IOCP만으로도 충분한 경우가 많으니, RIO 도입은 실제 병목을 측정한 뒤 판단하는 것이 안전합니다.

2.3 RIO 아키텍처 및 구성 요소

RIO를 쓰려면 매번 다섯 가지 준비물이 필요합니다 — 함수 테이블, 등록된 버퍼, 완료 큐, 요청 큐, 그리고 그 조각을 가리키는 RIO_BUF.

1) RIO 함수 테이블 — RIO API의 진입점

RIO 함수들은 winsock2.h가 기본 제공하는 일반 함수가 아니라, 소켓 확장 함수입니다. 그래서 RIORegisterBuffer()를 코드에서 바로 호출할 수 없고, 소켓마다 WSAIoctl()로 "이 소켓에서 쓸 RIO 함수들의 포인터 모음(함수 테이블)"을 먼저 받아와야 합니다. 1장 마지막에 만든 RioSocket::create()에서 이미 이 과정을 한 번 다뤘는데, 이번 장에서 그 이유를 정확히 짚고 넘어갑니다 — RIO는 Winsock 확장 기능이라 함수 주소가 빌드 시점이 아니라 런타임에 결정되기 때문입니다. 

GUID functionTableId = WSAID_MULTIPLE_RIO;
RIO_EXTENSION_FUNCTION_TABLE rioFunctions;
DWORD dwBytes = 0;

int result = WSAIoctl(
    socket,
    SIO_GET_MULTIPLE_EXTENSION_FUNCTION_POINTER,
    &functionTableId, sizeof(GUID),
    &rioFunctions, sizeof(rioFunctions),
    &dwBytes, NULL, NULL
);

2) 버퍼 등록 (Buffer Registration)

APIRIORegisterBuffer()

지정한 메모리 영역을 RIO 시스템에 등록하고, 이후 모든 요청에서 이 메모리를 가리키는 데 쓸 식별자 RIO_BUFFERID를 반환합니다.

RIO_BUFFERID RIORegisterBuffer(
    _In_ PCHAR DataBuffer,
    _In_ DWORD DataLength
);
매개변수의미
DataBuffer등록할 메모리의 시작 주소.
DataLength등록할 메모리의 전체 크기(바이트).

실패하면 RIO_INVALID_BUFFERID를 반환합니다.

char* dataBuffer = new char[65536]; // 64KB 버퍼
RIO_BUFFERID bufferId = rioFunctions.RIORegisterBuffer(dataBuffer, 65536);

3) 완료 큐 (Completion Queue)

APIRIOCreateCompletionQueue()

네트워크 작업이 끝났을 때 그 결과를 쌓아두는 큐를 만듭니다. IOCP의 완료 포트와 비슷한 역할이지만, 결과를 배열 단위로 한꺼번에 꺼낼 수 있도록 설계되어 있습니다.

RIO_CQ RIOCreateCompletionQueue(
    _In_ DWORD QueueSize,
    _In_opt_ PRIO_NOTIFICATION_COMPLETION NotificationCompletion
);
매개변수의미
QueueSize큐에 동시에 쌓일 수 있는 최대 완료 항목 수.
NotificationCompletion완료 발생을 어떻게 통지받을지(이벤트 기반 등) 지정. 5장에서 자세히 다룹니다.
RIO_NOTIFICATION_COMPLETION completionType = {};
completionType.Type = RIO_EVENT_COMPLETION;
completionType.Event.EventHandle = CreateEvent(NULL, FALSE, FALSE, NULL);
completionType.Event.NotifyReset = TRUE;

RIO_CQ completionQueue = rioFunctions.RIOCreateCompletionQueue(1000, &completionType);

4) 요청 큐 (Request Queue)

APIRIOCreateRequestQueue()

소켓 하나마다 만드는 큐로, 그 소켓의 송신·수신 요청이 실제로 쌓이는 곳입니다. 생성할 때 이 요청들의 완료를 어느 완료 큐로 보낼지도 함께 지정합니다.

RIO_RQ RIOCreateRequestQueue(
    _In_ SOCKET Socket,
    _In_ ULONG MaxOutstandingReceive,
    _In_ ULONG MaxReceiveDataBuffers,
    _In_ ULONG MaxOutstandingSend,
    _In_ ULONG MaxSendDataBuffers,
    _In_ RIO_CQ ReceiveCQ,
    _In_ RIO_CQ SendCQ,
    _In_ PVOID SocketContext
);
매개변수의미
Socket이 요청 큐가 속할 소켓.
MaxOutstandingReceive동시에 미완료 상태로 걸어둘 수 있는 최대 수신 요청 수.
MaxReceiveDataBuffers수신 요청 하나에 사용할 버퍼 조각 수(보통 1).
MaxOutstandingSend / MaxSendDataBuffers송신에 대한 동일한 의미의 값.
ReceiveCQ / SendCQ수신·송신 완료를 각각 어느 완료 큐로 보낼지. 같은 큐를 지정해도 됩니다.
SocketContext이 큐를 식별하기 위해 애플리케이션이 자유롭게 붙이는 값(포인터/정수 캐스팅). 완료 결과에서 그대로 돌려받습니다.
RIO_RQ requestQueue = rioFunctions.RIOCreateRequestQueue(
    socket, 100, 1, 100, 1, completionQueue, completionQueue, NULL
);

5) RIO_BUF 구조체 — 등록된 버퍼의 "일부분"을 가리키는 뷰

STRUCTRIO_BUF

등록된 버퍼 전체가 아니라, 그중 어느 구간을 이번 요청에 사용할지 지정하는 작은 구조체입니다. 1장의 std::span과 비슷한 역할을 하지만, RIO 요청 함수에 직접 전달하는 전용 타입입니다.

필드의미
BufferIdRIORegisterBuffer()가 반환한 등록된 버퍼의 식별자.
Offset등록된 버퍼의 시작으로부터 이 요청이 사용할 구간의 오프셋(바이트).
Length이 요청이 사용할 구간의 길이(바이트).
RIO_BUF sendBuffer = {};
sendBuffer.BufferId = bufferId;
sendBuffer.Offset = 0;
sendBuffer.Length = dataSize;

비유로 정리하면

등록된 버퍼(RIO_BUFFERID)는 "미리 빌려둔 큰 창고"이고, RIO_BUF는 "그 창고의 몇 번째 칸, 어디부터 어디까지를 쓰겠다"는 전표입니다. 요청 큐는 그 전표를 들고 줄을 서는 창구이고, 완료 큐는 처리가 끝난 전표들이 쌓이는 수거함입니다.

RIO 작업 흐름도

이 다섯 구성요소가 실제로 어떤 순서로 상호작용하는지 정리하면 다음과 같습니다. 앞의 넷(함수 테이블 조회~요청 큐 생성)은 연결을 맺을 때 한 번만 준비하면 되고, 이후 "요청 → 완료 통지" 사이클만 연결이 끊길 때까지 계속 반복됩니다.

그림 2-2. ①준비는 연결마다 한 번, ②③ 요청·완료 사이클은 데이터가 오갈 때마다 계속 반복됩니다

2.4 RIO 함수 및 API 개요

앞서 다룬 4가지 준비물 외에, 실제로 데이터를 주고받고 정리할 때 쓰는 나머지 함수들입니다.

데이터 송수신 함수

APIRIOReceive()

요청 큐에 비동기 수신 요청을 등록합니다. 함수는 즉시 반환되며, 실제 데이터가 도착하면 결과가 완료 큐에 쌓입니다 — 1장에서 본 논블로킹 recv()의 사상을 그대로 이어받되, 폴링 대신 완료 큐라는 통지 메커니즘을 씁니다.

BOOLEAN RIOReceive(
    _In_ RIO_RQ SocketQueue,
    _In_reads_(DataBufferCount) PRIO_BUF pData,
    _In_ ULONG DataBufferCount,
    _In_ DWORD Flags,
    _In_ PVOID RequestContext
);
매개변수의미
SocketQueue수신을 요청할 요청 큐.
pData수신에 사용할 RIO_BUF 배열.
DataBufferCountpData 배열의 원소 수(보통 1).
Flags추가 옵션 플래그(보통 0).
RequestContext이 요청을 식별할 값 — 완료 결과에서 RequestContext로 그대로 돌려받습니다. "어느 클라이언트의 요청이었는지" 추적하는 용도로 씁니다.
APIRIOSend()

요청 큐에 비동기 송신 요청을 등록합니다. 매개변수 구성은 RIOReceive()와 동일합니다.

BOOLEAN RIOSend(
    _In_ RIO_RQ SocketQueue,
    _In_reads_(DataBufferCount) PRIO_BUF pData,
    _In_ ULONG DataBufferCount,
    _In_ DWORD Flags,
    _In_ PVOID RequestContext
);

결과 처리 함수

앞서 2.2절에서 RIODequeueCompletion()으로 완료 결과를 배열로 꺼내오는 것까지 살펴봤습니다. 다만 RIODequeueCompletion()은 "지금 큐에 있는 걸 꺼내오기"만 할 뿐, "완료되면 나에게 알려달라"는 통지 자체는 별도로 요청해야 합니다 — 그 역할이 RIONotify()입니다.

APIRIONotify()

완료 큐에 새 완료가 생기면 (생성 시 지정한 이벤트 핸들 등을 통해) 통지해달라고 요청합니다. 이 호출은 "한 번 통지받을 권리"를 예약하는 것이라, 통지를 받은 뒤에는 다음 완료를 받기 위해 다시 호출해야 합니다 — 자세한 사용 패턴은 5장에서 다룹니다.

int RIONotify(
    _In_ RIO_CQ CQ
);

정리 함수

연결이 끊기거나 서버를 종료할 때 등록했던 리소스를 되돌려주는 함수들입니다.

APIRIODeregisterBuffer()
void RIODeregisterBuffer(
    _In_ RIO_BUFFERID BufferId
);

등록된 버퍼를 해제합니다. 이 버퍼를 참조하는 요청이 더 이상 없을 때 호출해야 합니다.

APIRIOCloseCompletionQueue()

    _In_ RIO_CQ CQ

완료 큐를 닫습니다. 이 큐를 참조하는 요청 큐가 모두 정리된 뒤에 호출합니다.

APIRIOResizeCompletionQueue() / RIOResizeRequestQueue()
BOOL RIOResizeCompletionQueue(
    _In_ RIO_CQ CQ,
    _In_ DWORD QueueSize
);

BOOL RIOResizeRequestQueue(
    _In_ RIO_RQ RQ,

운영 중에 트래픽이 예상보다 몰려 큐 용량을 늘려야 할 때, 큐를 새로 만들지 않고 크기만 조정할 수 있습니다. 접속자 수가 급증하는 이벤트 기간 등에 유용합니다.

RIO 사용 예제: 기본 구조

지금까지 소개한 함수들을 모두 조합하면 RIO 서버의 골격이 만들어집니다. 아래 RioServer 클래스를 통해 "어느 함수가 어느 시점에 호출되는지" 전체 그림을 따라가 봅니다. (버퍼 하나로 여러 연결을 관리하는 이 단순화된 구조의 한계와, 3~4장에서 이를 어떻게 개선하는지는 다음 장부터 본격적으로 다룹니다.)

1) 초기화 — Winsock, 소켓, 함수 테이블까지는 1장과 동일

    WSAStartup(MAKEWORD(2, 2), &wsaData);

    _listenSocket = WSASocketW(AF_INET, SOCK_STREAM, IPPROTO_TCP,
                                nullptr, 0, WSA_FLAG_REGISTERED_IO);

    GUID functionTableId = WSAID_MULTIPLE_RIO;

    // ...

2) 초기화 — 이번 장에서 새로 추가되는 부분: 버퍼 등록과 완료 큐

    // 모든 연결이 공유해서 쓸 하나의 큰 버퍼를 미리 등록
    _dataBuffer = new char[_bufferSize * maxConnections];
    _bufferId = _rioFunctions.RIORegisterBuffer(_dataBuffer, _bufferSize * maxConnections);

    // 완료 큐 생성 — 이벤트 핸들은 별도 멤버에도 저장해 둡니다 (아래 실전 팁 참고)
    RIO_NOTIFICATION_COMPLETION completionType{};
    completionType.Type = RIO_EVENT_COMPLETION;
    completionType.Event.EventHandle = CreateEvent(NULL, FALSE, FALSE, NULL);
    completionType.Event.NotifyReset = TRUE;
    _completionEvent = completionType.Event.EventHandle;

    _completionQueue = _rioFunctions.RIOCreateCompletionQueue(maxConnections * 2, &completionType);
    return {};
}

실전 팁 — 완료 큐 핸들(RIO_CQ)을 다시 캐스팅해서 쓰지 않기

RIO_CQ는 내부 구조를 알 수 없는 불투명(opaque) 핸들입니다. 완료 큐를 만들 때 넘긴 RIO_NOTIFICATION_COMPLETION 구조체의 내용을 나중에 다시 쓰고 싶다면, RIO_CQ 값을 그 구조체 포인터로 캐스팅해서 되돌리려 하지 말고 (구조가 다르므로 미정의 동작입니다), 위 코드처럼 이벤트 핸들 자체를 별도 멤버 변수에 따로 저장해 두는 편이 안전합니다.

3) start() — 두 개의 작업 스레드 시작

1장에서 배운 std::jthread를 그대로 활용해, 연결을 받는 스레드와 I/O 완료를 처리하는 스레드를 분리합니다. 이렇게 역할을 나누면 한쪽이 바쁘더라도 다른 쪽이 영향을 받지 않습니다. 

void start() {
    _acceptThread = std::jthread([this](std::stop_token stoken) { acceptLoop(stoken); });
    _ioThread = std::jthread([this](std::stop_token stoken) { ioProcessingLoop(stoken); });
}

4) acceptLoop() — 연결마다 요청 큐를 만들고 첫 수신을 예약

1장의 accept() 루프와 겉모습은 비슷하지만, 클라이언트 소켓을 얻은 뒤 곧바로 스레드를 만들지 않고 대신 그 소켓 전용 RIOCreateRequestQueue()를 호출한다는 점이 핵심적인 차이입니다. 이후 이 클라이언트의 모든 송수신은 스레드가 아니라 이 요청 큐를 통해 5)의 I/O 스레드가 처리합니다. 

void acceptLoop(std::stop_token stoken) {
    while (!stoken.stop_requested()) {
        sockaddr_in clientAddr{};
        int clientAddrSize = sizeof(clientAddr);
        SOCKET clientSocket = accept(_listenSocket, reinterpret_cast<sockaddr*>(&clientAddr), &clientAddrSize);
        if (clientSocket == INVALID_SOCKET) continue;

        RIO_RQ requestQueue = _rioFunctions.RIOCreateRequestQueue(
            clientSocket, 100, 1, 100, 1,
            _completionQueue, _completionQueue,
            reinterpret_cast<PVOID>(static_cast<uintptr_t>(_requestQueues.size()))
        );

        _requestQueues.push_back(requestQueue);
        postReceive(requestQueue, _requestQueues.size() - 1);   // 첫 수신 요청을 미리 걸어둠
    }
}

5) ioProcessingLoop() — 완료를 기다렸다가 배치로 처리

RIO의 핵심이 드러나는 부분입니다. RIONotify()로 통지를 예약하고, WaitForSingleObject()로 완료 이벤트를 기다린 뒤, RIODequeueCompletion()으로 한 번에 최대 10건까지 결과를 꺼내와 반복 처리합니다. 

void ioProcessingLoop(std::stop_token stoken) {
    RIORESULT results[10];

    while (!stoken.stop_requested()) {
        if (_rioFunctions.RIONotify(_completionQueue) != ERROR_SUCCESS) {
            std::this_thread::sleep_for(std::chrono::milliseconds(10));
            continue;
        }

        DWORD waitResult = WaitForSingleObject(_completionEvent, 100);
        if (waitResult == WAIT_TIMEOUT) continue;

        ULONG numResults = _rioFunctions.RIODequeueCompletion(_completionQueue, results, 10);
        if (numResults == 0 || numResults == RIO_CORRUPT_CQ) continue;

        for (ULONG i = 0; i < numResults; i++) {
            ULONG_PTR index = results[i].RequestContext;
            DWORD bytesTransferred = results[i].BytesTransferred;

            if (bytesTransferred == 0) {           // recv() == 0과 같은 의미: 상대가 연결 종료
                std::cout << std::format("클라이언트 {} 연결 종료\n", index);
                continue;
            }

            postSend(_requestQueues[index], index, bytesTransferred);   // 받은 그대로 에코
            postReceive(_requestQueues[index], index);                  // 다음 수신을 또 예약
        }
    }
}

bytesTransferred == 0의 의미, 여기서도 동일합니다

1장에서 강조했던 "recv()가 0을 반환하면 정상 종료"라는 규칙이 RIO 완료 결과에서도 그대로 적용됩니다. RIORESULT::BytesTransferred가 0이면 상대가 연결을 정상적으로 끊었다는 뜻입니다.

6) postReceive() / postSend() — RIO_BUF를 채워 요청 걸기

앞서 등록해둔 하나의 큰 _dataBuffer를 클라이언트 인덱스별로 _bufferSize만큼 나눠 쓰는 방식입니다. Offset 계산이 곧 "이 클라이언트의 몫은 버퍼의 몇 번째 구간인가"를 가리킵니다. 

void postReceive(RIO_RQ requestQueue, ULONG_PTR index) {
    RIO_BUF receiveBuffer{};
    receiveBuffer.BufferId = _bufferId;
    receiveBuffer.Offset = index * _bufferSize;
    receiveBuffer.Length = _bufferSize;
    _rioFunctions.RIOReceive(requestQueue, &receiveBuffer, 1, 0, reinterpret_cast<PVOID>(index));
}

void postSend(RIO_RQ requestQueue, ULONG_PTR index, DWORD dataSize) {
    RIO_BUF sendBuffer{};
    sendBuffer.BufferId = _bufferId;
    sendBuffer.Offset = index * _bufferSize;   // 방금 수신한 것과 같은 구간을 그대로 재전송(에코)
    sendBuffer.Length = dataSize;
    _rioFunctions.RIOSend(requestQueue, &sendBuffer, 1, 0, reinterpret_cast<PVOID>(index));
}

전체 코드 — RioServer 클래스

#include <winsock2.h>
#include <mswsock.h>
#include <ws2tcpip.h>
#include <iostream>
#include <format>
#include <thread>
#include <vector>
#include <span>
#include <expected>
#include <string>

#pragma comment(lib, "ws2_32.lib")

class RioServer {
public:
    RioServer() = default;
    ~RioServer() { cleanup(); }

    std::expected<void, std::string> initialize(uint16_t port, int maxConnections = 1000) {
        WSADATA wsaData;
        int result = WSAStartup(MAKEWORD(2, 2), &wsaData);
        if (result != 0) {
            return std::unexpected(std::format("WSAStartup 실패: {}", result));
        }

        _listenSocket = WSASocketW(AF_INET, SOCK_STREAM, IPPROTO_TCP, nullptr, 0, WSA_FLAG_REGISTERED_IO);
        if (_listenSocket == INVALID_SOCKET) {
            return std::unexpected(std::format("소켓 생성 실패: {}", WSAGetLastError()));
        }

        GUID functionTableId = WSAID_MULTIPLE_RIO;
        DWORD dwBytes = 0;
        result = WSAIoctl(_listenSocket, SIO_GET_MULTIPLE_EXTENSION_FUNCTION_POINTER,
                           &functionTableId, sizeof(GUID), &_rioFunctions, sizeof(_rioFunctions),
                           &dwBytes, NULL, NULL);
        if (result == SOCKET_ERROR) {
            return std::unexpected(std::format("RIO 함수 테이블 초기화 실패: {}", WSAGetLastError()));
        }

        sockaddr_in serverAddr{};
        serverAddr.sin_family = AF_INET;
        serverAddr.sin_port = htons(port);
        serverAddr.sin_addr.s_addr = INADDR_ANY;

        result = bind(_listenSocket, reinterpret_cast<sockaddr*>(&serverAddr), sizeof(serverAddr));
        if (result == SOCKET_ERROR) {
            return std::unexpected(std::format("바인드 실패: {}", WSAGetLastError()));
        }

        result = listen(_listenSocket, SOMAXCONN);
        if (result == SOCKET_ERROR) {
            return std::unexpected(std::format("리슨 실패: {}", WSAGetLastError()));
        }

        _dataBuffer = new char[_bufferSize * maxConnections];
        _bufferId = _rioFunctions.RIORegisterBuffer(_dataBuffer, _bufferSize * maxConnections);
        if (_bufferId == RIO_INVALID_BUFFERID) {
            return std::unexpected(std::format("버퍼 등록 실패: {}", WSAGetLastError()));
        }

        RIO_NOTIFICATION_COMPLETION completionType{};
        completionType.Type = RIO_EVENT_COMPLETION;
        completionType.Event.EventHandle = CreateEvent(NULL, FALSE, FALSE, NULL);
        completionType.Event.NotifyReset = TRUE;
        _completionEvent = completionType.Event.EventHandle;

        _completionQueue = _rioFunctions.RIOCreateCompletionQueue(maxConnections * 2, &completionType);
        if (_completionQueue == RIO_INVALID_CQ) {
            return std::unexpected(std::format("완료 큐 생성 실패: {}", WSAGetLastError()));
        }

        std::cout << std::format("RIO 서버가 초기화되었습니다. 포트: {}\n", port);
        return {};
    }

    void start() {
        _acceptThread = std::jthread([this](std::stop_token stoken) { acceptLoop(stoken); });
        _ioThread = std::jthread([this](std::stop_token stoken) { ioProcessingLoop(stoken); });
    }

private:
    SOCKET _listenSocket = INVALID_SOCKET;
    RIO_EXTENSION_FUNCTION_TABLE _rioFunctions{};
    char* _dataBuffer = nullptr;
    RIO_BUFFERID _bufferId = RIO_INVALID_BUFFERID;
    RIO_CQ _completionQueue = RIO_INVALID_CQ;
    HANDLE _completionEvent = NULL;
    const DWORD _bufferSize = 4096;
    std::jthread _acceptThread;
    std::jthread _ioThread;
    std::vector<RIO_RQ> _requestQueues;

    void acceptLoop(std::stop_token stoken) {
        while (!stoken.stop_requested()) {
            sockaddr_in clientAddr{};
            int clientAddrSize = sizeof(clientAddr);

            SOCKET clientSocket = accept(_listenSocket, reinterpret_cast<sockaddr*>(&clientAddr), &clientAddrSize);
            if (clientSocket == INVALID_SOCKET) {
                if (!stoken.stop_requested()) {
                    std::cerr << std::format("연결 수락 실패: {}\n", WSAGetLastError());
                }
                continue;
            }

            char clientIP[INET_ADDRSTRLEN];
            inet_ntop(AF_INET, &clientAddr.sin_addr, clientIP, INET_ADDRSTRLEN);
            std::cout << std::format("새 클라이언트 연결: {}\n", clientIP);

            RIO_RQ requestQueue = _rioFunctions.RIOCreateRequestQueue(
                clientSocket, 100, 1, 100, 1,
                _completionQueue, _completionQueue,
                reinterpret_cast<PVOID>(static_cast<uintptr_t>(_requestQueues.size()))
            );

            if (requestQueue == RIO_INVALID_RQ) {
                std::cerr << std::format("요청 큐 생성 실패: {}\n", WSAGetLastError());
                closesocket(clientSocket);
                continue;
            }

            _requestQueues.push_back(requestQueue);
            postReceive(requestQueue, _requestQueues.size() - 1);
        }
    }

    void ioProcessingLoop(std::stop_token stoken) {
        RIORESULT results[10];

        while (!stoken.stop_requested()) {
            int notifyResult = _rioFunctions.RIONotify(_completionQueue);
            if (notifyResult != ERROR_SUCCESS) {
                std::cerr << std::format("RIONotify 실패: {}\n", notifyResult);
                std::this_thread::sleep_for(std::chrono::milliseconds(10));
                continue;
            }

            DWORD waitResult = WaitForSingleObject(_completionEvent, 100);
            if (waitResult == WAIT_TIMEOUT) {
                continue;
            } else if (waitResult != WAIT_OBJECT_0) {
                std::cerr << std::format("이벤트 대기 실패: {}\n", GetLastError());
                std::this_thread::sleep_for(std::chrono::milliseconds(10));
                continue;
            }

            ULONG numResults = _rioFunctions.RIODequeueCompletion(_completionQueue, results, 10);
            if (numResults == 0) {
                continue;
            } else if (numResults == RIO_CORRUPT_CQ) {
                std::cerr << "완료 큐가 손상되었습니다.\n";
                break;
            }

            for (ULONG i = 0; i < numResults; i++) {
                ULONG_PTR index = results[i].RequestContext;
                DWORD bytesTransferred = results[i].BytesTransferred;

                if (bytesTransferred == 0) {
                    std::cout << std::format("클라이언트 {} 연결 종료\n", index);
                    continue;
                }

                postSend(_requestQueues[index], index, bytesTransferred);
                postReceive(_requestQueues[index], index);
            }
        }
    }

    void postReceive(RIO_RQ requestQueue, ULONG_PTR index) {
        RIO_BUF receiveBuffer{};
        receiveBuffer.BufferId = _bufferId;
        receiveBuffer.Offset = index * _bufferSize;
        receiveBuffer.Length = _bufferSize;

        BOOL receiveResult = _rioFunctions.RIOReceive(requestQueue, &receiveBuffer, 1, 0, reinterpret_cast<PVOID>(index));
        if (!receiveResult) {
            std::cerr << std::format("RIOReceive 실패: {}\n", WSAGetLastError());
        }
    }

    void postSend(RIO_RQ requestQueue, ULONG_PTR index, DWORD dataSize) {
        RIO_BUF sendBuffer{};
        sendBuffer.BufferId = _bufferId;
        sendBuffer.Offset = index * _bufferSize;
        sendBuffer.Length = dataSize;

        BOOL sendResult = _rioFunctions.RIOSend(requestQueue, &sendBuffer, 1, 0, reinterpret_cast<PVOID>(index));
        if (!sendResult) {
            std::cerr << std::format("RIOSend 실패: {}\n", WSAGetLastError());
        }
    }

    void cleanup() {
        if (_bufferId != RIO_INVALID_BUFFERID) {
            _rioFunctions.RIODeregisterBuffer(_bufferId);
        }
        if (_completionQueue != RIO_INVALID_CQ) {
            _rioFunctions.RIOCloseCompletionQueue(_completionQueue);
        }
        if (_listenSocket != INVALID_SOCKET) {
            closesocket(_listenSocket);
        }
        delete[] _dataBuffer;
        WSACleanup();
    }
};

int main() {
    RioServer server;

    auto result = server.initialize(27015);
    if (!result) {
        std::cerr << "서버 초기화 실패: " << result.error() << std::endl;
        return 1;
    }

    server.start();

    std::cout << "서버가 실행 중입니다. 종료하려면 Enter 키를 누르세요...\n";
    std::cin.get();

    return 0;
}

이 구조의 한계

이 예제는 개념을 보여주기 위해 단순화되어 있습니다. 모든 연결이 하나의 거대한 버퍼를 인덱스로 나눠 쓰기 때문에 maxConnections를 넘어서는 연결을 받을 수 없고, 클라이언트가 끊어져도 그 슬롯을 재활용하는 로직이 없습니다. 3장에서는 이런 실전 이슈를 하나씩 보완하며 훨씬 견고한 구조로 다시 만듭니다.

2.5 RIO 성능 최적화 고려사항

API를 안다고 빠른 서버가 저절로 나오지는 않습니다 — 아래 다섯 가지는 4~5장에서 실제로 손을 대며 다시 등장할 주제들입니다.

  1. 버퍼 크기 최적화 — 게임의 평균 패킷 크기에 맞춰 버퍼를 잡아야 합니다. 너무 크면(예: 모든 연결에 64KB씩) 동시접속자 수만큼 메모리가 낭비되고, 너무 작으면 큰 패킷이 여러 조각으로 나뉘어 처리 로직이 복잡해집니다. (4장에서 자세히 다룹니다.)
  2. 큐 크기 최적화 — 완료 큐·요청 큐 크기를 예상 동시접속자 수와 트래픽 패턴에 맞게 설정해야 합니다. 너무 작으면 큐가 꽉 차 요청이 실패하는 병목이 생기고, 너무 크면 그만큼 커널 메모리를 낭비합니다. (5장에서 자세히 다룹니다.)
  3. 완료 통지 전략 — 이 장의 예제처럼 이벤트 기반으로 대기할 수도 있고, 짧은 간격으로 계속 RIODequeueCompletion()을 찔러보는 폴링 방식을 쓸 수도 있습니다. 지연 시간이 극도로 중요하다면(예: 격투 게임의 입력 동기화) 폴링이 유리할 수 있지만 CPU를 더 많이 씁니다. 트래픽 패턴에 따라 선택해야 합니다.
  4. 메모리 정렬 — 등록할 버퍼를 캐시 라인 크기(대부분의 x86-64 CPU에서 64바이트)에 맞춰 정렬하면, 여러 스레드가 인접한 메모리에 접근할 때 발생하는 캐시 라인 튀기기(false sharing)를 줄일 수 있습니다.
  5. CPU 친화성 설정 — I/O 처리 스레드를 특정 CPU 코어에 고정(affinity)하면, 그 스레드가 다른 코어로 옮겨 다니며 캐시를 다시 채우는 비용을 줄일 수 있습니다. 코어 수가 많은 서버에서 워커 스레드를 코어별로 분산 배치하는 전략과 함께 자주 사용됩니다.

2.6 요약

  1. RIO의 핵심 아이디어 — 버퍼를 미리 등록해 중간 복사를 없애고(제로 카피에 가까운 처리), 요청·완료를 큐 단위 배치로 처리해 커널 모드 전환 횟수를 줄이는 것이 RIO 성능의 근본 원리입니다.
  2. 전통적인 방식과의 차이 — 버퍼는 요청마다 할당하지 않고 한 번만 등록하며, 완료 결과는 GetQueuedCompletionStatus()처럼 하나씩이 아니라 RIODequeueCompletion()으로 여러 건을 한 번에 꺼내옵니다.
  3. 4대 구성요소 — 함수 테이블(진입점), 등록된 버퍼(RIO_BUFFERID), 완료 큐(RIO_CQ), 요청 큐(RIO_RQ)가 서로 맞물려 동작하며, RIO_BUF는 등록된 버퍼의 특정 구간을 가리키는 뷰입니다.
  4. 핵심 API — 초기화(RIORegisterBuffer, RIOCreateCompletionQueue, RIOCreateRequestQueue), 송수신(RIOReceive, RIOSend), 결과 처리(RIONotify, RIODequeueCompletion), 정리(RIODeregisterBuffer, RIOCloseCompletionQueue) 함수의 역할과 시그니처를 살펴봤습니다.
  5. 성능 튜닝 체크리스트 — 버퍼 크기, 큐 크기, 통지 전략, 메모리 정렬, CPU 친화성 — 이 다섯 가지는 앞으로의 장에서 하나씩 실제로 구현하며 다시 다룹니다.
